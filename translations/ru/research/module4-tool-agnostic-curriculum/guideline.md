<a id="working-title"></a>
## Рабочее название

**Эксплуатируем созданное с ИИ приложение: наблюдаемость, агенты и аудит безопасности** [PROPOSAL]

Название описывает систему, которую будут эксплуатировать учащиеся. Названия продуктов должны находиться внутри примеров реализации, а не определять структуру модуля. [HUMAN]

<a id="audience-and-promise"></a>
## Аудитория и обещанный результат

У учащегося есть приложение из Модуля 2: фронтенд на React, бэкенд на FastAPI, Postgres, контейнеры, публичное развёртывание и CI/CD. [FACT current-module-4,syllabus-proposal]

За 90 минут учащийся превратит просто развёрнутое приложение в систему с минимально необходимыми средствами эксплуатации. Он сможет:

1. проследить один неудачный запрос к бэкенду через метрику, трассировку, структурированный лог и версию развёртывания;
2. создать один алерт, отражающий длительное воздействие на пользователей и содержащий достаточно контекста для действий;
3. вызвать Codex, Claude или другого терминального агента без интерактивного интерфейса в роли системы первичного реагирования только для чтения;
4. вне модели обеспечить соблюдение правила: можно ли выполнить известный откат или управление должен взять человек;
5. запустить повторяемый аудит безопасности, сочетающий детерминированные свидетельства, рассуждения модели и проверку человеком. [INFERENCE observability-pipeline,alerting-sre,safe-remediation,agent-security-review]

Необязательные дополнительные 30 минут углубляют одну-две меры контроля; они не должны быть необходимы для завершения основной истории. [HUMAN]

<a id="central-idea"></a>
## Центральная идея

Модуль учит одному циклу обратной связи:

Изменение → наблюдение воздействия на пользователей → алерт с контекстом → расследование на основе свидетельств → разрешение ограниченного реагирования или эскалация → проверка восстановления → аудит кода и истории реагирования.

Исходная схема:

```text
change
→ observe user impact
→ alert with context
→ investigate from evidence
→ authorize a bounded response or escalate
→ verify recovery
→ audit the code and the response trail
```

Развёртывание не завершает поставку. Пригодная для эксплуатации система должна показывать воздействие на пользователей, сохранять свидетельства, ограничивать автоматизацию, проверять восстановление и позволять человеку восстановить важные решения. [INFERENCE nist-incident-response,alerting-sre,safe-remediation]

<a id="why-this-is-problem-first-rather-than-tool-first"></a>
## Почему сначала проблема, а не инструмент

Исходные инструменты отражают реальные проблемы, но 90-минутный каталог даст непрочные знания. Поэтому план начинается с проблемы, а продукты добавляются только после того, как небольшая самостоятельная реализация продемонстрирует подход. [HUMAN]

| Проблема | Изучаемое понятие | Самостоятельная реализация | Продукты, упоминаемые после |
| --- | --- | --- | --- |
| Мы не можем объяснить неудачный запрос | Связанные метрики, трассировки, логи и идентификатор развёртывания | Инструментировать один путь FastAPI; экспортировать через OTLP | OpenTelemetry, Collector, Prometheus, Loki, Tempo, Grafana |
| Алерты шумные или лишены контекста | Симптомы воздействия на пользователей, длительность, возможность действовать, ответственный, инструкция реагирования | Один алерт по длительным ошибкам 5xx со структурированным webhook | Prometheus/Alertmanager и аналогичные платформы |
| Люди под давлением собирают одни и те же свидетельства | Адаптеры свидетельств только для чтения и структурированный пакет инцидента | Оркестратор на shell/Python вызывает универсального неинтерактивного агента | HolmesGPT, K8sGPT, коммерческие AI-SRE-продукты |
| Уверенность агента принимается за полномочия | Внешняя политика, минимальные привилегии, обратимость, проверка, эскалация | Разрешить один версионируемый откат; заблокировать всё остальное | Агентные платформы и движки политик |
| Рецензии моделей убедительны, но ошибаются | Детерминированные проверки + независимые рассуждения + решение человека | JSON сканера, одна рецензия модели и ручная проверка | Semgrep MCP, PR-Agent, проверки безопасности Codex и Claude |
| Расширения агента становятся цепочкой поставок | Инвентаризация возможностей, происхождение, область чтения/записи/сети/секретов | Небольшой перечень состава возможностей агента | Snyk Agent Scan и другие сканеры MCP/агентов |
| Вызовам модели нужны правила размещения и управления | Независимый от поставщика интерфейс, политика данных, идентификация, бюджет, аудит | Маленький CLI-адаптер и запись метаданных модели | LiteLLM, Ollama, API размещённых у поставщика моделей |

[INFERENCE problem-first-tool-landscape] K8sGPT, Agent Scan, шлюзы и локальный инференс подходят как примеры, но не всё это нужно включать в основную практическую сборку.

<a id="concrete-teaching-architecture"></a>
## Конкретная учебная архитектура

Приложение Модуля 2 с CI/CD передаёт данные через OpenTelemetry SDK в OpenTelemetry Collector. Метрики, логи и трассировки доступны в Grafana: дашборд и один алерт. Webhook инцидента запускает сбор свидетельств и неинтерактивного агента. Предложенное действие проверяется внешней политикой: разрешённый откат либо пакет эскалации человеку. После отката выполняется проверка восстановления и добавляется неизменяемая запись инцидента. Отдельный путь: детерминированная проверка безопасности → рецензия модели → решение человека.

Исходная схема:

```text
Module 2 app + CI/CD
        |
  OpenTelemetry SDK
        |
OpenTelemetry Collector
   /      |       \
metrics  logs    traces
   \      |       /
       Grafana
 dashboard + one alert
             |
      incident webhook
             |
   evidence collector ──→ headless agent
             |                  |
       external policy ← proposed action
          /        \
 allowlisted       escalation packet
 rollback                to human
     |
 recovery check + append-only incident record

Separate path: deterministic security check → model review → human disposition
```

Коллектор является стабильной границей телеметрии. Адаптер агента является стабильной границей рассуждений. Внешняя политика является стабильной границей полномочий. Бэкенды и поставщики моделей могут меняться независимо. [INFERENCE observability-pipeline,mcp-security,safe-remediation]

<a id="the-prepared-incident"></a>
## Подготовленный инцидент

Используйте одно намеренно неудачное развёртывание, увеличивающее число ответов 5xx в важной операции бэкенда. Оно создаёт цельную учебную историю:

- дашборд показывает видимые пользователям ошибки, начавшиеся после развёртывания;
- exemplar или ссылка на трассировку ведёт к неудачному запросу;
- связанные структурированные логи раскрывают конкретный сбой без утечки чувствительных данных;
- пакет инцидента включает активный коммит и предыдущее заведомо исправное развёртывание;
- агент предлагает версионируемую процедуру отката;
- внешняя политика распознаёт известную сигнатуру и разрешает только эту процедуру;
- запрос проверки работоспособности и запрос доли ошибок подтверждают восстановление. [PROPOSAL]

Затем преподаватель меняет один факт: убирает известную сигнатуру, создаёт противоречие в свидетельствах или затрагивает данные/безопасность. Это показывает, как тот же агент вынужден передать задачу человеку. Так демонстрируется граница участия человека без подготовки второго полноценного инцидента. [PROPOSAL]

<a id="90-minute-workshop-outline"></a>
## План 90-минутного воркшопа

<a id="010-minutes--the-operational-gap"></a>
### 0–10 минут: пробелы в эксплуатации

Начните с развёрнутого приложения Модуля 2 и вызовите подготовленную регрессию.

Вопросы:

- Возникают ли у пользователей сбои приложения?
- Какая операция затронута?
- Вызвало ли это последнее развёртывание?
- Каким свидетельствам может доверять участник реагирования?
- Что ему разрешено менять?

Оригинал учебных вопросов:

- Is the app failing for users?
- Which operation is affected?
- Did the latest deployment cause it?
- What evidence can a responder trust?
- What is the responder allowed to change?

Покажите сквозной цикл и установите три границы: телеметрии, рассуждений и полномочий. Не начинайте с команд установки. [PROPOSAL]

<a id="1030-minutes--observe-one-request-end-to-end"></a>
### 10–30 минут: наблюдаем один запрос от начала до конца

Объясните:

- трассировки описывают путь запроса;
- метрики агрегируют поведение и служат основой условий алертов;
- логи сохраняют подробности событий;
- стабильные атрибуты сервиса, окружения и версии, а также идентификаторы трассировок связывают свидетельства;
- телеметрия тоже является чувствительными и затратными данными: для неё нужны удаление конфиденциальных сведений и контроль кардинальности. [FACT observability-pipeline]

Практическая работа:

- добавить или изучить инструментацию OpenTelemetry на одном пути FastAPI;
- отправить OTLP в коллектор;
- выполнить один успешный и один неудачный запрос;
- в заранее собранном стеке Grafana перейти от метрики ошибок к трассировке, связанному логу и версии развёртывания.

Трассировка React/браузера остаётся необязательным расширением, поскольку текущая браузерная инструментация всё ещё экспериментальна. [FACT observability-pipeline]

<a id="3045-minutes--create-one-alert-worth-waking-up-for"></a>
### 30–45 минут: создаём один алерт, ради которого стоит проснуться

Объясните:

- будить дежурного нужно при устойчивых симптомах, видимых пользователю, а не при каждой внутренней причине;
- дашборды содержат диагностический контекст, алерты предполагают действие;
- порогам нужны длительность и допуски;
- алерт должен содержать сервис, серьёзность, симптом, время, ссылки на свидетельства, последнее изменение, ответственного и инструкцию реагирования;
- в зрелой системе важны группировка, устранение дубликатов, подавление зависимых алертов и метамониторинг. [FACT alerting-sre]

Практическая работа:

- создать или изучить одно правило длительного превышения доли ошибок 5xx;
- проверить его на подготовленной регрессии;
- изучить структурированную полезную нагрузку webhook.

Опыт практиков поддерживает ограничение основной части одним тщательно спроектированным алертом: команды сообщают об усталости от алертов, устаревающих наборах правил, отсутствии инструкций реагирования и дашбордах, которыми никто не пользуется. [FACT practitioner-observability]

<a id="4570-minutes--agent-as-first-responder-policy-as-authority"></a>
### 45–70 минут: агент реагирует первым, политика определяет полномочия

Объясните последовательность:

Алерт → сбор фактов → формирование и проверка гипотез → предложение действия → решение политики → действие или эскалация → проверка → запись.

Исходная схема:

```text
alert → collect facts → form/test hypotheses → propose action
      → policy decision → act or escalate → verify → record
```

Самостоятельно собранная система реагирования:

1. получает webhook алерта;
2. выполняет разрешённые запросы только для чтения: работоспособность, метрики, логи/трассировки и история развёртываний/git;
3. записывает ограниченный по объёму пакет свидетельств;
4. вызывает настроенный адаптер неинтерактивного терминального агента;
5. проверяет ответ по схеме;
6. передаёт предложенное действие на внешнюю проверку политики;
7. запускает только конкретный разрешённый скрипт отката либо записывает пакет эскалации;
8. проверяет и фиксирует результат. [PROPOSAL]

Переносимый контракт адаптера:

- вход: версионируемое задание, каталог свидетельств и схема вывода;
- выход: структурированные факты, гипотезы, предлагаемое действие и неопределённость;
- ограничения: рабочий каталог, учётные данные только для чтения, тайм-аут, лимит команд и область сетевого доступа.

Исходный контракт:

```text
input:  versioned task + evidence directory + output schema
output: structured facts, hypotheses, proposed action, uncertainty
limits: working directory, read-only credentials, timeout, command budget, network scope
```

Codex CLI и неинтерактивный режим Claude Code служат конкретными адаптерами. Промпты модели не дают полномочий; их задают shell-обёртки, учётные данные, изоляция и политика. [INFERENCE mcp-security,practitioner-ai-operations]

Уровни автономности:

| Уровень | Что происходит | Основная политика |
| --- | --- | --- |
| 0 | Обогащение алерта контекстом | Автоматически |
| 1 | Расследование только для чтения и рекомендация | Автоматически в установленных пределах |
| 2 | Протестированная, обратимая, версионируемая процедура | Только для разрешённой сигнатуры и с детерминированным постусловием |
| 3 | Патч/PR в изолированном окружении | Проверяет человек; в этом модуле никогда не сливается автоматически |
| 4 | Новое, разрушительное, широкое действие либо действие с безопасностью/данными/секретами | Требуется человек |

Автоматическое исправление требует известной сигнатуры, версионируемой процедуры, ограниченной зоны воздействия, обратимости/идемпотентности, детерминированной проверки восстановления, строгих лимитов повторов, времени и стоимости, а также полного журнала. Неизвестные причины, противоречивые свидетельства, последствия для безопасности/данных, отсутствие проверки или неудачные повторы требуют эскалации. [INFERENCE safe-remediation]

Практики считают полезными сбор свидетельств, сводки инцидентов и предлагаемые команды; сложной границей остаются ненадёжные выводы о первопричинах и доступ на запись. [FACT practitioner-ai-operations]

<a id="7087-minutes--recurring-security-audit-evidence-before-eloquence"></a>
### 70–87 минут: регулярный аудит безопасности, свидетельства важнее красноречия

Объясните три слоя:

1. детерминированные проверки известных шаблонов и зависимостей;
2. целевые рассуждения модели о контексте, сценариях злоупотребления, бизнес-логике и пропущенных взаимодействиях;
3. проверка человеком и принятие решения. [INFERENCE owasp-secure-code-review,agent-security-review]

Практическая работа:

- запустить один детерминированный сканер и сохранить структурированный вывод;
- запустить одну модель неинтерактивно с версионируемым заданием аудита на том же коммите;
- требовать для каждой находки свидетельства из кода, описание воздействия/сценария злоупотребления, неопределённость и способ проверки;
- подтвердить или отклонить одну находку и записать решение.

Текущие примеры с приоритетом качества могут включать OpenAI `gpt-5.6-sol` с усилием рассуждения `max` и Anthropic `claude-fable-5`. Более глубокий плановый аудит может запускать обе модели независимо; для 90-минутного практического упражнения нужна только одна, чтобы не зависеть от двух платных аккаунтов. ChatGPT является интерактивным интерфейсом продукта, а не независимым голосом модели, когда использует то же семейство GPT. [FACT current-audit-models] [PROPOSAL]

Semgrep MCP и PR-Agent показываются как примеры после самостоятельного рабочего процесса. Основной подход: свидетельства сканера плюс контекстная проверка, без зависимости от MCP или одного PR-бота. В обсуждениях практики отмечают и полезные находки моделей, и ложные срабатывания/пропуски, что подтверждает пользу независимых свидетельств и разделения обязанностей. [FACT practitioner-ai-security]

<a id="8790-minutes--close-the-loop"></a>
### 87–90 минут: замыкаем цикл

По коммиту или идентификатору инцидента покажите, что мы можем восстановить:

- развёрнутую версию и воздействие на пользователей;
- алерт и изученные свидетельства;
- модель/конфигурацию и предложенное действие;
- решение политики и выполненную команду;
- проверку восстановления или эскалацию;
- связанную находку безопасности и решение человека.

Завершите принципом эксплуатации: модель может рассуждать; система обязана наблюдать, разрешать, проверять и помнить. [PROPOSAL]

<a id="optional-extension-to-120-minutes"></a>
## Необязательное расширение до 120 минут

Выбирайте по аудитории; не пытайтесь выполнить все варианты.

<a id="recommended-extension-ambiguous-incident-and-capability-audit"></a>
### Рекомендуемое расширение: неоднозначный инцидент и аудит возможностей

- **90–105:** повторить инцидент с противоречивыми или чувствительными для безопасности свидетельствами; учащиеся изучают пакет эскалации и улучшают рекомендацию следующего действия.
- **105–120:** составить перечень навыков агента, MCP-серверов, shell, файловой системы, сети и учётных данных; классифицировать происхождение и область чтения/записи/сети/секретов; удалить одну небезопасную возможность или снизить её риск.

Это добавляет два понятия, которые сжатая демонстрация может показать лишь кратко: качественная эскалация в условиях неопределённости и безопасность самой системы реагирования. Затем Snyk Agent Scan показывается как продукт, автоматизирующий часть задачи инвентаризации/проверки. [PROPOSAL]

Другие расширения: второй независимый аудит моделью, инструментация фронтенда, тесты алертов или переключение адаптера модели на шлюз/локальную конечную точку. [PROPOSAL]

<a id="important-production-practices-we-acknowledge-but-do-not-teach-deeply"></a>
## Важные производственные практики, которые мы упоминаем, но не изучаем глубоко

- SLI/SLO, бюджеты ошибок и алерты скорости расходования бюджета по нескольким временным окнам;
- синтетический браузерный мониторинг, мониторинг реальных пользователей фронтенда, профилирование и ёмкость хостов/базы данных;
- семплирование, хранение, удаление персональных данных PII, изоляция арендаторов и контроль стоимости наблюдаемости;
- канареечная/постепенная поставка, флаги функций, хаос-тестирование, резервные копии и тренировки восстановления;
- ответственные дежурные, управление инцидентом, сообщения о статусе и разборы без поиска виноватых;
- сканирование секретов/зависимостей/контейнеров/IaC, SBOM, происхождение/подписание сборок, тестирование на проникновение и раскрытие уязвимостей;
- наборы оценочных тестов для обновлений модели/поставщика и измерение ложноположительных/ложноотрицательных результатов аудита;
- высокая доступность и метамониторинг системы наблюдаемости/реагирования. [INFERENCE nist-ssdf,nist-incident-response,alerting-sre,observability-pipeline]

Эти темы исключены потому, что заслонили бы главный цикл обратной связи воркшопа, а не потому, что не важны.

<a id="guardrails-and-non-goals"></a>
## Ограничители и то, что не входит в цели

- Не выдавать дашборды или успешный приём телеметрии за доказательство ценности наблюдаемости.
- Не копировать большой набор алертов и не вызывать дежурного при каждом колебании ресурсов.
- Не обещать достоверное автоматическое определение первопричины.
- Не использовать инструкции промпта или регулярные выражения команд как механизм выдачи полномочий.
- Не давать агенту неограниченные учётные данные продакшена/облака.
- Не сливать автоматически изменения, созданные моделью, и не позволять модели удостоверять собственное исправление.
- Не отправлять исходный код или телеметрию поставщику без явного решения о данных и сроках их хранения.
- Не утверждать, что локальный инференс автоматически обеспечивает приватность или готовность к продакшену.
- Не создавать заново хранилище телеметрии, статический анализ или обслуживание моделей; строить слой оркестрации, политики, свидетельств и аудита вокруг стандартных интерфейсов. [INFERENCE mcp-security,practitioner-ai-operations,practitioner-model-infrastructure]
