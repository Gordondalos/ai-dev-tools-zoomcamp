О курсе

AI Dev Tools Zoomcamp — бесплатный практический курс для разработчиков и технических специалистов по данным, которые хотят освоить дисциплинированную разработку ПО с помощью ИИ.

В основе курса лежит один рабочий процесс:

Давайте инструментам ИИ подходящий контекст, поручайте им подходящие задачи, проверяйте то, что они создают, тестируйте результат и выпускайте программное обеспечение с защитными ограничениями.

Вы сравните современные инструменты ИИ для разработчиков, создадите и развернёте full-stack-приложение, наладите его эксплуатацию с наблюдаемостью и реагированием на инциденты при помощи агентов, а также расширите возможности агентов разработки с помощью MCP и повторно используемых компонентов.

Курс не ограничивается промпт-инжинирингом и не посвящён обучению моделей или созданию RAG-систем. Главное здесь — повседневная разработка ПО с ИИ-ассистентами и агентами, тестами, CI/CD, развёртыванием, документацией и проверкой кода.

Для кого этот курс

Курс подойдёт вам, если вы:

  • Уже умеете писать простой код на Python, JavaScript, TypeScript или похожем языке.
  • Хотите профессионально использовать инструменты ИИ для программирования, а не только получать отдельные фрагменты кода.
  • Хотите выстроить воспроизводимый процесс планирования, составления запросов, проверки, тестирования, отладки и выпуска кода.
  • Заботитесь о поддерживаемости, тестах, развёртывании, документации и ревью кода.
  • Хотите создать проект, демонстрирующий практические навыки разработки с ИИ.
  • Цените общие сроки потока, поддержку сообщества, взаимное рецензирование и возможность получить сертификат.

Курс особенно полезен разработчикам ПО, ML-инженерам, MLOps-инженерам, AI-инженерам, специалистам по данным, инженерам данных, аналитикам, которые пишут код, и студентам технических специальностей, которым нужен практический проектный опыт.

Курс, вероятно, не подойдёт вам, если вы никогда не программировали, ищете нетехническое введение в ИИ или прежде всего хотите изучать обучение и дообучение моделей, LangChain, векторные базы данных либо RAG.

Предварительные знания

Опыт работы с инструментами ИИ не требуется.

Вы должны:

  • Уметь писать простой код на Python, JavaScript, TypeScript или похожем языке.
  • Уверенно пользоваться командной строкой.
  • Знать основы Git и GitHub.

Будут полезны, но не обязательны:

  • Базовые знания веб-разработки.
  • Базовое знакомство с Docker.

Не требуются:

  • Опыт работы с ИИ-ассистентами или агентами для программирования.
  • Мощный компьютер или GPU.

Программа

Модуль 1. Рабочий процесс разработчика с ИИ в основе

Узнайте, как с помощью агентов разработки превратить расплывчатую идею продукта в программное обеспечение со спецификацией, реализацией и независимой проверкой.

В этом модуле вы:

  • Превратите расплывчатую идею в спецификацию и бэклог конкретных задач.
  • Передадите агентам разработки устойчивый контекст через AGENTS.md.
  • Используете роли PM/инженер/QA, организуя работу через циклы и графы, чтобы реализовать и проверить задачи бэклога.

Результат: вы спроектируете и запустите процесс разработки с ИИ в основе, который проведёт продукт от идеи до реализации и независимой проверки качества.

Модуль 2. Создание и выпуск full-stack-приложения с помощью ИИ

Создайте full-stack-приложение с помощью ИИ-ассистентов для программирования, поочерёдно заменяя компоненты-заглушки настоящими.

Вы:

  • Превратите идею в спецификацию, затем создадите прототип фронтенда и контракт OpenAPI.
  • Реализуете бэкенд на FastAPI по этому контракту, затем соедините его с фронтендом, добавив аутентификацию и совместную работу в реальном времени.
  • Замените временное хранилище на SQLite и добавите тесты.

Результат: работающее full-stack-приложение с обновлениями в реальном времени, постоянным хранением данных, тестами и ясным API-контрактом.

Модуль 3. Тестирование, контейнеризация и развёртывание приложения, созданного с ИИ

Перенесите приложение со своего компьютера в общедоступное развёртывание, добавив тесты и проверки доставки, которые проверяют систему целиком.

Вы:

  • Контейнеризируете приложение и перейдёте с SQLite на Postgres с помощью Docker Compose.
  • Добавите интеграционные и сквозные тесты, в том числе Playwright для сценария совместной работы.
  • Развернёте приложение в AWS и настроите конвейер CI/CD в GitHub Actions.

Результат: общедоступное контейнеризированное приложение на Postgres с автоматическими тестами и CI/CD, который выполняет развёртывание только после успешного прохождения тестов.

Модуль 4. DevOps и наблюдаемость приложений, созданных с ИИ

Развёрнутое приложение всё ещё может незаметно давать сбои. Добавьте управление релизами и наблюдаемость, чтобы обнаруживать и расследовать проблемы и реагировать на них.

Вы:

  • Разделите среды разработки и эксплуатации, настроив конвейер продвижения версионированных релизов.
  • Инструментируете приложение с помощью OpenTelemetry, направив данные в Prometheus, Loki, Tempo и Grafana, и настроите оповещение, по которому можно принять меры.
  • Дадите агенту разработки ограниченную роль реагирования на инциденты с доступом только на чтение.

Результат: отдельные процессы для dev/prod, стек наблюдаемости, полезные оповещения и экспериментальный ИИ-агент дежурного реагирования.

Модуль 5. Компоненты агентов разработки: повторно используемые навыки и специализированные субагенты

Превратите повторяющиеся рабочие процессы и роли в проекте в повторно используемые возможности, которые агенты разработки смогут находить и применять.

Вы:

  • Создадите обнаруживаемые навыки с помощью SKILL.md и решите, должны ли они быть глобальными или относиться к конкретному проекту.
  • Определите узкоспециализированных субагентов, включая роли PM/инженер/QA, чтобы отделить реализацию от независимой проверки.
  • Организуете параллельное выполнение задач в изолированных Git worktree.

Результат: повторно используемые навыки, определения субагентов и схема оркестрации для последовательной или параллельной работы над проектом.

[!NOTE] В модуле 5 нет оцениваемого домашнего задания. Вместо него оценивается результат работы по модулю.

Итоговый проект

В итоговом проекте вы примените рабочий процесс курса к собственному приложению от начала до конца.

Вы:

  • Выберете проблему и опишете ожидаемое поведение системы.
  • Создадите фронтенд.
  • Создадите бэкенд.
  • Определите взаимодействие фронтенда и бэкенда с помощью контракта OpenAPI.
  • Добавите базу данных или постоянное хранилище.
  • Протестируете приложение.
  • Контейнеризируете приложение.
  • Развернёте его, чтобы другие могли им воспользоваться.
  • Задокументируете, как использовали инструменты ИИ, промпты, рабочие процессы, инструкции для агентов, MCP или автоматизацию.

Для получения сертификата в потоке проекты проходят взаимное рецензирование. Участники должны успешно сдать итоговый проект и выполнить обязательные рецензии на проекты других участников.

Сертификат

Сертификаты доступны во время обучения в потоке тем, кто завершит итоговый проект и обязательное взаимное рецензирование.

Домашние задания помогают не отставать, но сертификат зависит от выполнения требований к итоговому проекту и взаимному рецензированию. Общий порядок получения сертификата описан в разделе Certification.

При самостоятельном обучении все материалы доступны бесплатно, однако для получения сертификата необходимо участвовать в потоке.

Частые вопросы

Полный список находится в FAQ AI Dev Tools Zoomcamp.

Этот курс бесплатный?

Да. Видео, материалы, домашние задания и участие в потоке бесплатны.

Нужен ли опыт работы с ИИ?

Нет. Опыт работы с инструментами ИИ для программирования не требуется. Вы должны уметь писать простой код и работать с репозиторием проекта.

Нужно ли быть разработчиком ПО?

Нет. Курс также подходит специалистам по данным, ML-инженерам, MLOps-инженерам, инженерам данных, аналитикам, которые пишут код, и студентам технических специальностей. Базовые навыки программирования необходимы.

Есть ли занятия в прямом эфире?

Лекции записаны заранее. Обучение в потоке добавляет общие сроки, оцениваемые домашние задания, таблицу лидеров, взаимное рецензирование, поддержку сообщества и возможность получить сертификат.

Можно ли проходить курс самостоятельно?

Да. Видео и материалы репозитория доступны в любое время. При самостоятельном обучении сертификат не выдаётся, если вы не присоединитесь к потоку.

Нужен ли мощный компьютер или GPU?

Нет. Мощный компьютер или GPU не требуются.

Этот курс посвящён RAG или обучению моделей?

Нет. Курс сосредоточен на процессах разработки ПО с ИИ: ассистентах и агентах для программирования, MCP, тестировании, CI/CD, развёртывании, документации, ревью, безопасности, аудите и DevOps.

Обзор

В этом модуле вы создадите полноценное работающее приложение с помощью ИИ. Основным проектом остаётся небольшое приложение Snake Arena: оно наглядное, интерактивное и при этом требует основных составляющих реальной системы:

  • спецификации продукта
  • фронтенда
  • контракта OpenAPI
  • бэкенда
  • базы данных
  • тестов

Цель не в том, чтобы позволить ИИ-инструменту бесконтрольно создать всё приложение. Цель — отработать управляемый процесс, в котором ИИ помогает двигаться быстрее, а вы проверяете каждый шаг.

В конце модуля у вас будет приложение, которое работает на вашем компьютере: фронтенд и бэкенд взаимодействуют по определённому контракту, а данные сохраняются в SQLite. Всё необходимое, чтобы сделать приложение доступным другим людям, — интеграционные тесты, контейнеры, CI, развёртывание и CI/CD — рассматривается в модуле 3.

Вы научитесь:

  • Писать небольшую спецификацию продукта с пользовательскими историями, критериями приёмки и перечнем того, что не входит в задачи продукта, прежде чем генерировать код
  • Создавать прототип фронтенда с помощью ИИ-инструмента (Lovable, Bolt, Cursor, Claude Code, Codex и других), затем переносить его в обычный рабочий процесс с репозиторием и делать удобным для сопровождения
  • Определять контракт OpenAPI как единый источник истины для фронтенда и бэкенда
  • Реализовывать бэкенд на FastAPI по контракту, начиная с имитации базы данных и тестов для основных эндпоинтов
  • Заменять имитацию хранилища на SQLite, сохраняя независимость приложения от конкретной базы данных, чтобы впоследствии перейти на Postgres без переписывания приложения
  • Добавлять модульные тесты и тесты фронтенда, покрывающие поведение, описанное в спецификации и контракте

Обзор

Модуль 2 заканчивается приложением, которое работает на вашем компьютере. В этом модуле вы пройдёте оставшийся путь: проверите приложение тестами, задействующими реальный стек, упакуете его в контейнеры, настроите автоматические проверки каждого pull request и развернёте его для других пользователей.

Последовательность этапов:

integration tests
containerization
continuous integration
deployment
continuous delivery

Перевод схемы:

интеграционные тесты → контейнеризация → непрерывная интеграция → развёртывание → непрерывная доставка

На каждом этапе ИИ-инструменты хорошо готовят черновой вариант, но плохо справляются с ответственностью за результат. Сгенерированный Dockerfile, с которым сборка завершается успешно, не обязательно собирает то, что нужно. А зелёный пайплайн, который пропускает тесты, хуже, чем отсутствие пайплайна. Рабочий процесс остаётся таким же, как в предыдущих модулях: дайте агенту создать первую версию, затем прочитайте её, запустите и намеренно внесите поломку, чтобы проверить, обнаружат ли проверки хоть какую-нибудь проблему.

DevOps и наблюдаемость приложений, созданных с помощью ИИ

Оригинал материала

Модуль 3 заканчивается приложением, которое автоматически развёртывается после успешного прохождения тестов. Это делает его доступным в сети, но не позволяет понять, продолжает ли оно работать.

Если важный эндпоинт начинает возвращать 500, нужно узнать, что пользователи столкнулись с проблемой, найти неудачные запросы, связать их с развёртыванием, которое привело к сбою, и решить, что делать дальше. CI/CD доставляет плохой релиз столь же эффективно, как и хороший.

В этом модуле мы выстроим цикл, закрывающий этот пробел:

change
→ observe user impact
→ alert with context
→ investigate from evidence
→ authorize a bounded response or escalate
→ verify recovery
→ audit the code and the response trail

Перевод схемы:

изменение → наблюдение за влиянием на пользователей → оповещение с контекстом → расследование на основе диагностических данных → разрешение ограниченных действий по реагированию или эскалация → проверка восстановления → аудит кода и истории реагирования

Мы также включим в этот цикл агента в качестве первой линии поддержки. Он запускается автоматически по сигналу оповещения, изучает сохранённый пакет диагностических данных и код, а затем предлагает действие. При этом он не получает учётные данные с общим доступом к production. Модель оценивает уверенность в решении, а код вне модели обеспечивает соблюдение разрешений.

Конкретный стек: OpenTelemetry передаёт данные в Prometheus, Loki и Tempo, поверх которых работает Grafana, а обработчик инцидентов запускает Codex или Claude Code в режиме без интерактивного интерфейса. Эти продукты можно заменить. Главное, что стоит усвоить, — границы между диагностическими данными, рассуждением, разрешением на действие и проверкой результата.

Вы научитесь:

  • Выяснять, на какие вопросы о сбое после развёртывания у вас нет ответов, и понимать, почему одних графиков загрузки CPU недостаточно для наблюдаемости
  • Инструментировать один эндпоинт от начала до конца с помощью OpenTelemetry: собирать метрики, трассировки и структурированные логи без утечки секретов
  • Настраивать конвейер телеметрии: OpenTelemetry Collector передаёт данные в Prometheus, Loki и Tempo, а Grafana позволяет просматривать их вместе
  • Создавать одно оповещение, отражающее реальное влияние на пользователей и запускающее локальный обработчик инцидента
  • До подключения модели собирать ограниченный, воспроизводимый пакет диагностических данных с помощью разрешённых запросов только для чтения
  • Запускать по оповещению агента для программирования (Codex или Claude Code) без интерактивного интерфейса, предоставляя ему доступ к развёрнутым системам только для чтения и изолированное рабочее дерево для предлагаемого исправления
  • Разрешать развёртывание только для изменений из разрешённого списка и после успешных тестов, а затем использовать Docker Compose; передавать проблему на следующий уровень, если эти проверки не пройдены
  • Проводить регулярные проверки безопасности, сочетающие детерминированный сканер (Semgrep), проверку моделью и подтверждение человеком
  • Рассматривать сам обработчик инцидентов как поверхность атаки: учитывать его возможности, учётные данные и происхождение компонентов (Snyk Agent Scan)

Для домашнего задания используйте отдельный стартовый проект Order Tracker. Можно также выполнить упражнение на приложении, которое вы развернули в модуле 3.

Краткое содержание модуля: сопроводительная статья подготавливает развёрнутое приложение к промышленной эксплуатации: разделяет dev и prod, собирает логи, метрики и трассировки и настраивает оповещения о влиянии на пользователей. Затем она запускает небольшого экспериментального агента в роли дежурного по инцидентам: получив оповещение, он исследует первопричину, воспроизводит сбой и фиксирует исправление в коммите. В этом прототипе нет списков разрешённых действий, эскалации и проверки восстановления, необходимых для production. Уроки самого модуля добавляют эти защитные механизмы.

Место остальных инструментов

Когда проблемы определены, становится понятно, где использовать остальные инструменты:

  • HolmesGPT и K8sGPT собирают эксплуатационные данные, которые модель может объяснить. Это тот же подход, что и у нашего обработчика инцидентов, но для прохождения курса знание Kubernetes не требуется.
  • PR-Agent применяет проверку моделью на этапе pull request.
  • Semgrep MCP подключает детерминированное сканирование к агенту.
  • Snyk Agent Scan инвентаризирует цепочку поставок расширений агента.
  • LiteLLM добавляет шлюз для маршрутизации запросов к моделям, управления ключами, бюджетами и логами, когда нескольким приложениям или провайдерам нужна единая политика.
  • Ollama запускает модели локально, когда этого требуют ограничения на размещение данных.
  • garak тестирует сами LLM-приложения, к которым наше приложение не относится.

Локальная модель не делает рабочий процесс автоматически конфиденциальным: по-прежнему важны хост, сеть, история промптов, локальные логи, аутентификация эндпоинтов и качество модели. Шлюз централизует политику доступа к моделям, но не превращает слабый процесс реагирования на инциденты в надёжный.

Что не входит в модуль

В этом модуле намеренно не рассматриваются:

SLOs, error budgets, and burn-rate alerts
synthetic monitoring, real-user monitoring, and profiling
sampling, retention, and observability cost control
canary and progressive delivery, feature flags, chaos testing
on-call ownership, incident command, blameless postmortems
SBOMs, build provenance, signing, penetration testing

Перевод списка:

  • Целевые показатели уровня обслуживания (SLO), бюджеты ошибок и оповещения о скорости их расходования
  • Синтетический мониторинг, мониторинг реальных пользователей и профилирование
  • Выборочное сохранение телеметрии, сроки её хранения и контроль затрат на наблюдаемость
  • Канареечные и постепенные релизы, флаги функциональности и хаос-тестирование
  • Ответственность дежурных, координация реагирования на инциденты и разборы инцидентов без поиска виноватых
  • Перечни компонентов ПО (SBOM), сведения о происхождении сборки, подписание и тестирование на проникновение

Расположение файла конфигурации

Antigravity читает конфигурации MCP-серверов из JSON-файла. Файл конфигурации должен называться mcp.json и находиться в каталоге вашего проекта.

Базовый формат конфигурации

Создайте файл mcp.json со следующей структурой:

{
    "mcpServers": {
        "server-name": {
            "command": "command-to-run",
            "args": [
                "argument1",
                "argument2"
            ]
        }
    }
}

Пример: добавление MCP-сервера Context7

Context7 предоставляет доступ к документации библиотек и возможности поиска по коду.

Шаг 1. Создайте mcp.json

{
    "mcpServers": {
        "context7": {
            "command": "npx",
            "args": [
                "-y",
                "@upstash/context7-mcp@latest"
            ]
        }
    }
}

Шаг 2. Настройте API-ключ (если требуется)

Некоторые MCP-серверы, например Context7, требуют аутентификации:

В Windows (PowerShell):

$env:CONTEXT7_API_KEY="your-api-key-here"

В Linux/Mac:

export CONTEXT7_API_KEY="your-api-key-here"

Постоянная настройка (Windows): Добавьте настройку в свой профиль PowerShell или задайте системную переменную окружения.

Шаг 3. Перезапустите Antigravity

После добавления конфигурации MCP перезапустите Antigravity, чтобы загрузить новый MCP-сервер.

Шаг 4. Проверьте подключение к MCP-серверу

После перезапуска Antigravity проверьте, подключён ли MCP-сервер:

  1. В интерфейсе Antigravity: нажмите меню с тремя точками (⋮)
  2. Найдите «MCP Servers» или аналогичный пункт, показывающий подключённые серверы
  3. В списке должны появиться настроенные вами серверы (например, «context7»)

[!IMPORTANT] Если ваш MCP-сервер не появился: - Убедитесь, что файл mcp.json находится в правильном месте - Проверьте синтаксис JSON (используйте валидатор JSON) - Убедитесь, что Node.js и npm установлены и доступны из командной строки - Проверьте правильность имени пакета сервера (например, @upstash/context7-mcp@latest) - Просмотрите логи Antigravity на наличие сообщений об ошибках - Попробуйте вручную выполнить команду MCP в терминале, чтобы проверить её работу: powershell npx -y @upstash/context7-mcp@latest

Домашнее задание 3: Контейнеризация и развёртывание

Оригинал

В этом домашнем задании вы развернёте Agent Relay — небольшую систему обмена сообщениями между программными агентами.

Один агент отправляет задачу другому, исполнитель забирает её в работу, а затем подтверждает результат. База данных хранит сообщения и попытки их доставки. Небольшая панель мониторинга позволяет следить за жизненным циклом сообщений.

С помощью своего агента для программирования вы протестируете и контейнеризируете Agent Relay. Затем развернёте его в локальном кластере Kubernetes с помощью kind (Kubernetes in Docker).

В стартовом проекте уже есть API и панель мониторинга.

Вам не понадобятся облачный аккаунт, ключ API LLM или внешний брокер сообщений. Всё работает на вашем компьютере. По мере необходимости просите агента устанавливать и проверять каждый инструмент.

Потоки обучения

Оригинал этой страницы.

Текущая учебная программа, то есть все модули и их уроки, находится в корне репозитория, а не здесь. В cohorts/<year>/ хранится только то, что относится к конкретному запуску курса: даты, домашние задания и, для прошедшего потока, зафиксированная копия программы, по которой учили в тот год.

Текущий поток — 2026. Исправляйте учебную программу в корне репозитория, а не внутри cohorts/2026/. Это указано единожды, в машиночитаемом виде, в корне: course.yaml:current_cohort задаёт текущий поток и должен совпадать с единственным cohorts/<year>/cohort.yaml, в котором объявлено curriculum: current.

Структура

<repo root>/
├── course.yaml                   # course identity, incl. the description
├── 01-ai-native-workflow/        # the directory name IS the module slug
│   ├── module.yaml                 # module identity and unit list
│   ├── README.md                   # GitHub-facing module index, not published
│   └── 01-ai-native-developer-workflow.md  # the module's unit — the stem IS the unit slug
├── ...
└── cohorts/
    ├── README.md                  # this file
    ├── 2026/                      # the directory name IS the cohort identifier
    │   ├── cohort.yaml            # dates, curriculum: current, homework list
    │   ├── README.md              # the human-readable schedule
    │   └── homework/
    │       ├── 01-ai-native-workflow/
    │       │   ├── homework.md    # homework instructions, fixed name
    │       │   └── homework.yaml  # homework identity, due date, form, questions
    │       └── ...
    └── 2025/                      # earlier cohort: frozen, full copy

Пояснение к схеме: course.yaml хранит идентификационные данные курса, включая описание; имя каталога модуля является его URL-идентификатором (slug); module.yaml содержит данные модуля и список учебных единиц; README.md служит индексом модуля для GitHub и не публикуется как урок; имя файла урока без расширения является slug урока. Имя каталога потока является идентификатором потока. cohort.yaml содержит даты, признак curriculum: current и список домашних заданий; README потока — расписание для читателя. Фиксированное имя homework.md используется для инструкций, а homework.yaml — для идентификационных данных задания, срока сдачи, формы и вопросов. Каталог 2025 содержит полную зафиксированную копию прежней программы.

Основную роль играют два правила:

  • Имена определяют идентичность. Slug модуля — это имя его каталога. В YAML он не повторяется, а переименование каталога изменяет опубликованный URL.
  • Каталог модуля самодостаточен. Урок находится внутри него. Относительная ссылка не выходит за пределы каталога модуля, кроме переходов к соседнему модулю или в корень репозитория. Для всего, что находится дальше, используется абсолютный URL GitHub.

Текущий поток и зафиксированный архив потока

Тип потока указан в его cohort.yaml:

  • curriculum: current — поток использует ту программу, которая сейчас находится в корне репозитория. В cohorts/<year>/ хранятся только даты и домашние задания (cohorts/<year>/homework/<module>/). Содержимого модулей или уроков здесь нет, поэтому оно не дублируется и не расходится с корнем.
  • curriculum: github_archive — программа потока существенно отличалась от той, которая сейчас находится в корне, поэтому её зафиксировали: сохранили полную самостоятельную копию всех модулей этого потока. Архив предназначен только для чтения на GitHub и никогда не импортируется повторно как текущие модули или уроки. Пока единственный такой архив в этом репозитории — cohorts/2025/.
