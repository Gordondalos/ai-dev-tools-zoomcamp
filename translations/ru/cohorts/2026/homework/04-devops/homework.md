# Домашнее задание 4: DevOps и наблюдаемость приложений, созданных с ИИ

[Оригинал](https://github.com/Gordondalos/ai-dev-tools-zoomcamp/blob/b47dff65161c878d095e288e9f9e5b907f5aa3c6/cohorts/2026/homework/04-devops/homework.md)

В этом домашнем задании вы исследуете сбой в [Order Tracker](https://github.com/alexeygrigorev/order-tracker) — небольшом приложении для создания заказов и проверки их статуса. В стартовом проекте есть веб-страница, API, тесты и конфигурация Docker Compose.

Создайте форк стартового проекта на GitHub, затем клонируйте свой форк. Вы добавите средства наблюдаемости и сервис реагирования на инциденты, который срабатывает при получении оповещения. Просите агента для программирования помогать с реализацией, но проверяйте каждый результат самостоятельно.

Вам понадобятся Docker с Compose и Python с `uv` для тестов. Как запустить проект, объясняется в его README.

<a id="question-1-run-the-app"></a>

## Вопрос 1: Запустите приложение

Запустите Order Tracker:

```bash
docker compose up --build -d --wait
```

Теперь проверьте его:

```bash
curl http://localhost:8000/healthz
```

Что возвращает проверка работоспособности?

- `{"status":"ok"}`
- `{"status":"error"}`
- `{"orders":3}`
- `pong`

В этом и следующих вопросах можно попросить ассистента для программирования помочь выбрать правильный вариант.

<a id="question-2-instrument-one-endpoint"></a>

## Вопрос 2: Добавьте инструментацию для одного эндпоинта

Представьте, что клиент говорит, что не может открыть заказ. Вы проверяете сайт, и всё выглядит нормально. Нужен более надёжный способ понять, что происходит в системе. Для этого мы используем метрики, логи и трассировки.

Попросите агента добавить метрики, логи и трассировки OpenTelemetry для запросов на получение заказов. Метрика запросов должна включать маршрут и код состояния HTTP.
Пока экспортируйте сигналы в консоль, чтобы их можно было просматривать с помощью `docker compose logs app`.

После изменений, внесённых агентом, пересоберите приложение командой `docker compose up --build -d --wait`.

Затем запросите заказ `standard-1001`:

```bash
curl -i http://localhost:8000/api/orders/standard-1001
```

Найдите метрику запроса в логах приложения.

Какой код состояния HTTP записан в метрике для этого запроса?

- 200
- 301
- 404
- 500

<a id="question-3-build-the-telemetry-pipeline"></a>

## Вопрос 3: Создайте конвейер телеметрии

В вопросе 2 мы просматривали телеметрию в логах. Теперь сохраним её в специализированном хранилище.

Попросите агента добавить OpenTelemetry Collector, Prometheus, Loki, Tempo и Grafana в Docker Compose. Направьте метрики, логи и трассировки приложения через Collector и создайте панель Grafana для числа запросов и ошибок. Сохраните конфигурацию в репозитории.

Пересоберите стек командой `docker compose up --build -d --wait`, затем выполните:

```bash
curl -i http://localhost:8000/api/orders/standard-1002
```

Найдите в Grafana метрику этого запроса. Убедитесь, что его лог и трассировка тоже появились. Какой код состояния HTTP показывает метрика?

- 404
- 200
- 301
- 500

<a id="question-4-configure-the-alert"></a>

## Вопрос 4: Настройте оповещение

Панель показывает ошибки, когда вы её открываете, но сама по себе никого не уведомляет. Оповещение отслеживает метрику `5xx` и меняет состояние при возникновении серверных ошибок. Позже Grafana будет отправлять сервису реагирования HTTP-запрос, называемый вебхуком, чтобы тот автоматически начинал расследование.

Попросите агента добавить в Grafana оповещение для ответов `5xx`. Включите в него эндпоинт, временное окно и ссылку на панель, а также предусмотрите периоды без ответов `5xx`. Пока проверьте состояние оповещения в Grafana. К сервису реагирования вы подключите его в вопросе 6.

Повторите запрос из вопроса 3:

```bash
curl -i http://localhost:8000/api/orders/standard-1002
```

Дождитесь проверки условия оповещения. Какое состояние показывает Grafana?

- Normal
- Firing
- Pending
- No data

<a id="question-5-build-the-automatic-responder"></a>

## Вопрос 5: Создайте автоматический сервис реагирования

Когда срабатывает оповещение, дежурный инженер должен разобраться в проблеме и решить её. Если это не удаётся, он передаёт проблему разработчикам.

В нашем случае именно этим будет заниматься агент.

Попросите ассистента для программирования создать в `incident-response/` сервис, принимающий оповещения от Grafana через `POST /alerts` на порту `8001`. При получении оповещения сервис должен сохранять информацию, необходимую для понимания проблемы, например затронутый эндпоинт, логи и трассировки.

При получении оповещения сервис должен автоматически запускать ассистента для программирования в неинтерактивном режиме (headless).

Когда реализация будет готова, запустите сервис реагирования. Проверим его: отправьте ему оповещение:

```bash
curl -X POST http://localhost:8001/alerts \
  -H 'Content-Type: application/json' \
  -d '{"alerts":[{"status":"firing","labels":{"alertname":"ResponderTest","test":"true"},"annotations":{"summary":"Test notification; no incident to fix"}}]}'
```

Дождитесь завершения работы агента, затем прочитайте его ответ.

Что ответил агент? Приведите последнюю строку его ответа.

<a id="question-6-watch-the-agent-fix-the-incident"></a>

## Вопрос 6: Посмотрите, как агент исправляет инцидент

Теперь проверьте весь процесс с настоящим оповещением Grafana.

Подключите оповещение Grafana к сервису реагирования через вебхук.

Выполним такой запрос:

```bash
curl -i http://localhost:8000/api/orders/express-1002
```

Этот запрос вызывает проблему и должен привести к срабатыванию оповещения. Если этого не произошло, повторите его несколько раз. Затем проследите, как Grafana отправляет вебхук на `/alerts`, а сервис реагирования запускается автоматически.

Дождитесь, пока агент исправит проблему, перезапустите приложение и убедитесь, что тот же запрос больше не вызывает её.

В чём заключалась проблема?

- При расчёте даты экспресс-доставки использовался день, которого нет в соответствующем месяце.
- Не удалось разобрать временную метку заказа, потому что в ней не было часового пояса.
- Приложение отклонило статус заказа `preparing`.
- При поиске экспресс-заказов использовался неверный столбец базы данных.
