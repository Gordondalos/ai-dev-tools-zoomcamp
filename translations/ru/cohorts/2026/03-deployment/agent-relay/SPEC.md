<a id="agent-relay-specification"></a>
# Спецификация Agent Relay

Статус: стартовая версия v1. Этот документ определяет протокол и поведение,
реализованные в локальном стартовом варианте на SQLite.

SQLite выбрана намеренно, чтобы приложение работало без внешних сервисов.
В дальнейшем студенты могут перенести слой хранения на PostgreSQL как упражнение
по развёртыванию; HTTP-протокол, правила работы с учётными данными, жизненный цикл
задач и гарантии доставки должны остаться неизменными.

<a id="purpose"></a>
## Назначение

Agent Relay позволяет программным агентам регистрироваться, отправлять задачи друг
другу, брать работу и возвращать результаты через HTTP и JSON. Агенты выполняют
задачи на собственных компьютерах. Relay хранит идентичности, задачи и попытки
доставки и предоставляет панель для наблюдения за ними.

Регистрация создаёт идентичность и входящую очередь. Она не запускает процесс
агента. Агент может оставаться зарегистрированным, будучи офлайн; задачи ждут,
пока обслуживающий эту идентичность процесс не заберёт их.

V1 поддерживает одного получателя и один итоговый результат для каждой задачи.
Диалоги, потоковая передача результатов, вложения, автоматический выбор агента
и выполнение кода агента внутри relay не входят в её возможности. Самому relay
LLM не требуется.

<a id="components-and-identity"></a>
## Компоненты и идентичность

- **Relay API:** аутентифицирует вызывающую сторону и управляет регистрацией,
  отправкой задач, их получением и результатами.
- **SQLite (стартовый вариант):** постоянно хранит агентов, задачи и попытки
  доставки. Режим WAL и транзакция записи `BEGIN IMMEDIATE` координируют
  конкурентное получение задач между процессами API и воркеров. При будущем
  переносе на PostgreSQL студенты могут заменить эту транзакцию блокировкой строк,
  например `FOR UPDATE SKIP LOCKED`, не меняя протокол.
- **Процесс агента:** опрашивает очередь, выполняет задачи локально и сообщает
  результаты. Одну идентичность агента могут обслуживать несколько процессов.
- **Панель управления:** через API показывает агентов, время последней активности,
  состояния задач, результаты и историю доставки.

ID агента определяет логического получателя. ID воркера определяет запущенный
процесс для диагностики. ID воркеров не дают никаких разрешений. Каждое получение
задачи имеет собственный секретный claim token, отдельный от токена аутентификации
агента.

API и процессы агентов могут перезапускаться без потери задач в очереди. Процессы
агентов сохраняют регистрационные учётные данные локально и повторно используют
их после перезапуска.

<a id="http-conventions"></a>
## Соглашения HTTP

Все указанные ниже эндпоинты задаются относительно `/api/v1`. Тела запросов и
ответов используют JSON, кроме ответов без тела. ID — непрозрачные строки.
Временные метки имеют формат UTC RFC 3339. Размещённые на сервере установки
требуют HTTPS.

Все эндпоинты, кроме регистрации, требуют `Authorization: Bearer <agent_token>`.
Токен определяет идентичность вызывающей стороны; клиент не может выбрать
отправителя или входящую очередь, передав ID другого агента.

Ошибки имеют следующий формат:

```json
{"error": {"code": "stale_claim", "message": "This claim is no longer active."}}
```

Перевод сообщения `message`: «Это получение задачи больше не активно».

Используйте `400` для некорректных входных данных, `401` для отсутствующих или
недействительных учётных данных, `404` для отсутствующих или недоступных ресурсов,
`409` для конфликта состояния, `413` для слишком большого тела запроса и `429`
для ограничения частоты запросов. Ответы об ограничении частоты содержат `Retry-After`.

<a id="1-register-an-agent"></a>
## 1. Регистрация агента

`POST /agents`

```json
{"name": "alice-reviewer", "description": "Reviews Python code"}
```

Перевод значения `description`: «Проверяет код Python».

Возвращает `201 Created`:

```json
{"agent_id": "agent_123", "token": "<secret-agent-token>"}
```

Имена — отображаемые подписи, а не адреса, и не обязаны быть уникальными.
ID генерируются сервером и уникальны. Необязательное описание характеризует
предполагаемое поведение, но не является подтверждённой способностью.

Секретный токен возвращается только при создании. На сервере храните только его
хеш. Не включайте учётные данные в ответы панели управления, URL или логи.
В V1 нет восстановления аккаунта: потеря токена требует регистрации новой
идентичности.

На локальном экземпляре регистрация открыта. Совместная установка должна требовать
для этого эндпоинта секрет регистрации, выданный оператором, и ограничивать частоту
регистраций. Секрет регистрации отделён от токена конкретного агента.

`GET /agents` возвращает аутентифицированной стороне постраничный каталог ID,
имён, описаний, времени регистрации и последней активности агентов.
`GET /agents/me` возвращает собственную запись вызывающей стороны. Записи каталога
никогда не содержат токены.

Время последней активности фиксирует самый свежий аутентифицированный запрос
этого агента. Это наблюдение, а не доказательство того, что воркер всё ещё работает.

<a id="2-send-a-task"></a>
## 2. Отправка задачи

`POST /tasks`

```json
{
  "to": "agent_123",
  "input": "Review this Python function: ..."
}
```

Перевод учебного промпта в `input`: «Проверь эту функцию Python: ...».

Возвращает `201 Created`:

```json
{"task_id": "task_456", "status": "queued"}
```

Сервер записывает аутентифицированную вызывающую сторону как отправителя.
Получатель должен существовать, но может быть офлайн. Отправлять задачи себе
разрешено. Входные данные — непустая строка UTF-8; v1 не интерпретирует её и
не предписывает конкретный механизм выполнения.

При создании задач клиентам следует передавать заголовок `Idempotency-Key`.
Сервер ограничивает область действия ключа отправителем и хранит его весь срок
жизни задачи. Повтор того же ключа и содержимого возвращает исходную задачу,
не создавая новую. Повторное использование ключа с другим содержимым возвращает `409`.

<a id="3-claim-work"></a>
## 3. Получение работы

`POST /tasks/claim`

```json
{"worker_id": "alice-laptop-1", "wait_seconds": 30}
```

Сервер закрепляет за аутентифицированным агентом не более одной адресованной ему
задачи из очереди, отдавая предпочтение самой старой доступной задаче.
`worker_id` — необязательная диагностическая метка. `wait_seconds` — целое число
от 0 до 30, по умолчанию 30. Сервер удерживает запрос, пока не появится задача
или не истечёт ожидание.

При отсутствии работы возвращается `204 No Content`. Успешное получение
возвращает `200 OK`:

```json
{
  "task_id": "task_456",
  "from": "agent_789",
  "input": "Review this Python function: ...",
  "attempt": 1,
  "claim_token": "<secret-claim-token>",
  "lease_expires_at": "2026-09-09T12:05:00Z"
}
```

Перевод учебного промпта в `input`: «Проверь эту функцию Python: ...».

Получение атомарно переводит задачу в `processing` и создаёт попытку доставки
с новым claim token. Конкурирующие воркеры не могут успешно получить ту же задачу,
пока её аренда активна. Стартовый вариант на SQLite использует транзакцию
`BEGIN IMMEDIATE` (в SQLite нет `FOR UPDATE SKIP LOCKED`), а не блокировки внутри
отдельного процесса. При переносе хранения на PostgreSQL используйте транзакцию
и блокировку строк, например `FOR UPDATE SKIP LOCKED`.

По умолчанию аренда длится 60 секунд с момента успешного получения задачи.
Все решения об аренде опираются на время сервера или базы данных. Если ответ
на получение потерян, аренда в итоге истечёт; повтор запроса получения
не гарантирует возврат той же задачи.

<a id="4-execute-and-maintain-the-lease"></a>
## 4. Выполнение и поддержание аренды

Агент выполняет входную задачу локально. Relay никогда не исполняет отправленный
текст. Агенты считают содержимое входящих задач недоверенными данными и выполняют
их только в пределах собственных настроенных разрешений на инструменты.

Для работы, которая может длиться дольше аренды, вызывайте
`POST /tasks/{task_id}/heartbeat` примерно каждые 20 секунд:

```json
{"claim_token": "<secret-claim-token>"}
```

Корректный heartbeat возвращает `200 OK` с `lease_expires_at`, продлевая аренду
до момента через 60 секунд после текущего времени сервера. Heartbeat требует
и токен аутентификации получателя, и активный непросроченный claim token.

Просроченные, заменённые или завершённые попытки получения возвращают
`409 stale_claim`. Истёкшую аренду нельзя возобновить, даже если сменный воркер
ещё не взял задачу. Воркер, потерявший аренду, должен по возможности прекратить
выполнение и не должен считать, что его результат будет принят.

<a id="5-complete-or-fail-a-task"></a>
## 5. Успешное или неуспешное завершение задачи

`POST /tasks/{task_id}/complete`

```json
{
  "claim_token": "<secret-claim-token>",
  "output": "The function has an off-by-one error ..."
}
```

Перевод значения `output`: «В функции есть ошибка смещения на единицу ...».

Успешный запрос атомарно сохраняет строковый результат, закрывает попытку доставки
и переводит задачу в `completed`. Возвращает `200 OK` с ID и статусом задачи.

Агент, который не может выполнить задачу, может вызвать
`POST /tasks/{task_id}/fail`:

```json
{
  "claim_token": "<secret-claim-token>",
  "error": "Unsupported task: this agent only reviews Python code."
}
```

Перевод значения `error`: «Неподдерживаемая задача: этот агент проверяет только код Python».

Это сохраняет ошибку, закрывает попытку и переводит задачу в `failed`.
Явно сообщённая ошибка в v1 окончательна: автоматические повторы не запускаются.

Оба эндпоинта требуют учётные данные получателя и активный непросроченный
claim token. После успешной отправки завершающего запроса идентичный повтор
с тем же claim token и содержимым возвращает первоначальный успешный ответ,
даже после прежнего срока истечения аренды. Другой результат, конфликтующее
завершающее действие или заменённый токен возвращают `409`. Это позволяет
воркеру безопасно повторить запрос, если ответ потерян.

<a id="6-retrieve-tasks-and-results"></a>
## 6. Получение задач и результатов

`GET /tasks/{task_id}` возвращает подробности задачи отправителю или получателю:

```json
{
  "task_id": "task_456",
  "from": "agent_789",
  "to": "agent_123",
  "input": "Review this Python function: ...",
  "status": "completed",
  "output": "The function has an off-by-one error ...",
  "error": null,
  "attempt_count": 1,
  "created_at": "2026-09-09T12:03:00Z",
  "finished_at": "2026-09-09T12:04:30Z"
}
```

Переводы значений: `input` — «Проверь эту функцию Python: ...»;
`output` — «В функции есть ошибка смещения на единицу ...».

У незавершённых задач результат, ошибка и время завершения равны null.
У неуспешных задач есть ошибка, но нет результата. Другие агенты не могут
прочитать задачу или её результат.

`GET /tasks?direction=sent|received&status=...&cursor=...&limit=...` возвращает
список задач вызывающей стороны. Направление обязательно, статус необязателен.
По умолчанию списки содержат 50 записей, допускается не более 100; ответ содержит
`items` и `next_cursor`. Каталог агентов использует такую же оболочку пагинации.

`GET /tasks/{task_id}/attempts` открывает тем же авторизованным сторонам историю
доставки: номер попытки, ID воркера, время получения, истечение аренды, время
завершения и исход. Claim token никогда не раскрывается. Возможные исходы:
`processing`, `completed`, `failed` или `expired`.

Отправитель может опрашивать результат, начиная с интервала в две секунды
и увеличивая его для долгих задач. Панель управления использует те же
авторизованные эндпоинты. Общая панель не должна открывать содержимое всех задач
для публичного просмотра.

<a id="lifecycle-and-delivery-guarantees"></a>
## Жизненный цикл и гарантии доставки

```text
queued -> processing -> completed
                     -> failed       (explicit failure)
                     -> queued       (lease expired; attempts remain)
                     -> failed       (lease expired; attempt limit reached)
```

Перевод пояснений к переходам: `explicit failure` — явно сообщённая ошибка;
`lease expired; attempts remain` — аренда истекла, попытки ещё остались;
`lease expired; attempt limit reached` — аренда истекла, достигнут лимит попыток.
Статусы сохранены как идентификаторы протокола.

Фоновый цикл восстановления проверяет истёкшие аренды как минимум каждые пять
секунд. Восстановление помечает попытку как `expired` и либо возвращает задачу
в очередь, либо завершает её ошибкой `attempts_exhausted`. По умолчанию максимум
составляет пять попыток доставки на задачу. Этот лимит и длительность аренды
задаются конфигурацией сервера; клиенты используют возвращённый крайний срок,
а не предполагают фиксированную длительность.

Восстановление, heartbeat, получение и отправка завершающего результата должны
координироваться через транзакции базы данных, чтобы при гонке получался один
согласованный исход. Завершение, пришедшее после истечения аренды, отклоняется,
даже если восстановление ещё не запускалось.

Выполнение происходит как минимум один раз, с учётом лимита попыток. Если воркер
совершил действие и аварийно завершился до сообщения результата, другой воркер
может выполнить задачу повторно. Агенты с внешними побочными эффектами должны
использовать ID задачи как ключ идемпотентности, если внешняя система это
поддерживает. Relay не может гарантировать выполнение ровно один раз или
отменять побочные эффекты.

Сам по себе возраст задачи в очереди не приводит к её истечению. Если получатель
остаётся офлайн, его задачи остаются в очереди. Отмена и ручные повторы не входят
в v1; после ошибки отправитель может создать новую задачу.

<a id="client-loop-and-operational-limits"></a>
## Цикл клиента и эксплуатационные ограничения

Оригинальный псевдокод:

```text
load saved credentials (register if missing)
repeat:
    claim a task with long polling
    if no task: claim again
    execute locally while heartbeating
    complete or fail, retrying identical submissions on transient errors
```

Перевод псевдокода:

```text
загрузить сохранённые учётные данные (зарегистрироваться, если их нет)
повторять:
    получить задачу с длительным опросом
    если задачи нет: снова запросить задачу
    выполнить локально, отправляя heartbeat
    завершить успешно или с ошибкой, повторяя идентичные запросы при временных сбоях
```

При сбоях соединения, ответах `429` и `5xx` клиенты используют ограниченную
экспоненциальную задержку повторов со случайным разбросом, соблюдая `Retry-After`.
Они не повторяют вслепую ошибки валидации или устаревшие получения задач.
Штатное завершение прекращает новые получения и пытается закончить текущую
работу; при аварийном завершении используется восстановление после истечения аренды.

V1 ограничивает имена 100 символами, описания — 1,000 символами, ID воркеров —
100 символами, а тела запросов — 256 KiB. Общие установки также применяют
настраиваемые ограничения количества запросов и задач в очереди на агента.
Содержимое задач и результаты отображаются в панели управления как текст.

<a id="acceptance-scenarios"></a>
## Приёмочные сценарии

1. Зарегистрировать двух агентов. Один отправляет задачу; другой получает
   и завершает её; отправитель читает результат.
2. Зарегистрировать агента без запуска воркера. Его задача остаётся в очереди,
   пока воркер не запустится с сохранёнными учётными данными.
3. Запустить три воркера для одного агента и отправить несколько задач.
   Задачи распределяются без одновременных активных получений одной и той же задачи.
4. Завершить процесс воркера после получения задачи. После истечения аренды другой
   воркер получает задачу с иным claim token и увеличенным номером попытки.
5. Отправить результат с истёкшим токеном. Он отклоняется, в том числе до того,
   как восстановление вернуло задачу в очередь.
6. Отправлять heartbeat во время долгой задачи. Другие воркеры не могут получить
   её, пока продлённая аренда активна.
7. Повторить отправку задачи с тем же ключом идемпотентности, а затем повторить
   завершение после имитации потерянного ответа. Ни один повтор не создаёт
   дубликаты записей и не меняет принятый результат.
8. Исчерпать лимит попыток доставки. Задача получает статус failed и больше
   не выдаётся при получении задач.
9. Попытаться прочитать задачу другой пары агентов или получить задачу из входящей
   очереди другого агента. Доступ запрещён, содержимое задач и учётные данные
   не раскрываются.
10. Перезапустить relay с задачами в очереди и в обработке. Задачи в очереди
    остаются доступными, а обрабатываемые задачи с истёкшей арендой восстанавливаются
    на основе сохранённых аренд.
