## Введение

- Эта статья сжимает полный цикл разработки, развёртывания и эксплуатации в одно пошаговое руководство.
- Каждый шаг содержит одну цель и один запрос, а не обзор всех сгенерированных файлов.
- Запросы не привязаны к инструментам: заранее не предполагаются конкретные язык, фреймворк, база данных, хостинг, продукт для CI или поставщик средств наблюдаемости.
- Когда нужен реальный выбор, руководство просит агента предложить варианты и дождаться одобрения, а не делает выбор за читателя.

Через всё руководство проходит один пример: Study Relay.

Студент создаёт учебную группу для одного этапа курса — модуля, потока или нескольких недель. Другие студенты подают заявки на вступление, а организатор одобряет участников в пределах вместимости. Все подтверждают, что группа действительно начала работу. Когда этап заканчивается, организатор может передать заметки группы и накопленный рабочий импульс новому организатору следующего потока, который регистрирует свой этап как продолжение предыдущего. Это эстафета, а не разовое мероприятие.

## Разработка

- Спецификация превращает расплывчатую идею в решения ещё до появления кода.
- Сначала создайте видимый пользовательский сценарий с имитацией бэкенда, чтобы дёшево проверить идею, прежде чем вкладываться в сервер.
- Явно определите контракт (OpenAPI), чтобы у бэкенда была точная цель, а не необходимость выводить поведение из кода фронтенда.
- Добавляйте настоящее постоянное хранилище только после того, как фронтенд и бэкенд уже взаимодействуют через контракт.

Когда фронтенд, бэкенд и база данных взаимодействуют локально, приложение готово покинуть ваш компьютер.

### 1. Спецификация

- Если сначала не конкретизировать расплывчатую идею, агент заполнит пробелы собственными предположениями.
- Обсудите границы проекта в диалоге до обращения к агенту программирования: один вопрос за раз позволяет сохранить диалог, а не получить стену текста.
- Сохраните результат в файл, который агент программирования сможет прочитать позднее.

```text
I want to build a tool for weekly feedback for projects.

Help me set the scope for this project precisely. I want to brainstorm with you and understand how the tool should work. Give me options.

Ask me one question at a time and keep your output short.
```

Перевод запроса:

> Я хочу создать инструмент для еженедельной обратной связи по проектам.
>
> Помоги мне точно определить границы этого проекта. Я хочу обсудить с тобой идеи и понять, как должен работать инструмент. Предложи варианты.
>
> Задавай мне по одному вопросу за раз и отвечай кратко.

АДАПТИРОВАТЬ: «I want to build a tool for weekly feedback for projects.» → краткое описание Study Relay в одну строку. Остальная часть универсальна и не требует изменений.

Когда границы определены, передайте идею агенту программирования, чтобы воплотить её в жизнь.

### 2. Сначала фронтенд, с имитацией бэкенда

- Проверьте идею и спецификацию, прежде чем создавать остальную часть приложения.
- Если все обращения к бэкенду собраны в одном слое сервисов, позднее имитация станет единственной точкой интеграции.
- Такой инструмент, как Lovable, v0 или Bolt (либо непосредственно агент программирования), может сгенерировать весь фронтенд по одному запросу.

```text
Create a system design interview application.

[Paste the ChatGPT-generated specification here.]

Centralize every backend call in one services layer, and create a mock implementation of it so the whole app runs without a real backend.

Add tests.
```

Перевод запроса:

> Создай приложение для собеседований по проектированию систем.
>
> [Вставь сюда спецификацию, сгенерированную ChatGPT.]
>
> Сосредоточь все обращения к бэкенду в одном слое сервисов и создай его имитационную реализацию, чтобы всё приложение работало без настоящего бэкенда.
>
> Добавь тесты.

АДАПТИРОВАТЬ: «system design interview application» → описание Study Relay.

Когда фронтенд создан и по нему можно переходить, перенесите его в структуру проекта, которая будет использоваться на следующих этапах разработки.

### 3. Контракт OpenAPI

- Контракт — это явное соглашение между фронтендом и бэкендом: каждая конечная точка, запрос, ответ и правило аутентификации.
- Этот шаг можно пропустить, но тогда вы лишитесь чёткого представления о том, что именно должен делать бэкенд.
- Если генерировать контракт на основе собственного имитационного клиента фронтенда, он будет отражать реальные обращения интерфейса, а не догадки.

```text
Read the frontend's API client in frontend/

Create openapi.yaml at the repository root.

Specify the backend this frontend expects: every endpoint, method, path, request body, response body, and which endpoints need authentication.
```

Перевод запроса:

> Прочитай API-клиент фронтенда в frontend/.
>
> Создай openapi.yaml в корне репозитория.
>
> Опиши бэкенд, который ожидает этот фронтенд: каждую конечную точку, метод, путь, тело запроса, тело ответа и конечные точки, которым нужна аутентификация.

АДАПТИРОВАТЬ: ничего специфичного для приложения нет, запрос универсален без изменений.

Когда контракт определён, у бэкенда появляется точная цель реализации, но сначала нужно решить, на чём его создавать.

### 4. Выбор стека бэкенда

- Агент программирования может предложить стеки, но решение принимаете вы, исходя из реальных компромиссов.
- Явный выбор фреймворка заранее, вместо выбора агентом наиболее знакомого ему варианта по умолчанию, сохраняет независимость этого руководства от инструментов.

```text
Propose two backend stacks for this application, with the tradeoffs for each. Recommend one and wait for my approval before writing code.
```

Перевод запроса:

> Предложи два стека бэкенда для этого приложения, указав компромиссы каждого. Порекомендуй один и дождись моего одобрения, прежде чем писать код.

После одобрения стека реализуйте бэкенд в соответствии с контрактом.

### 5. Бэкенд

- Начните с хранилища в памяти, чтобы проверить связь фронтенда с бэкендом до того, как появится вопрос постоянного хранения данных.
- Аутентификация и авторизация относятся к этому шагу: их не следует прикручивать позднее.
- С самого начала разделите маршрутизацию, модели, хранение и аутентификацию на отдельные модули.

```text
Build a FastAPI backend in backend/ that implements the openapi.yaml spec.
Use an in-memory store and seed it with data so the frontend has something to show.
Add authentication with hashed passwords and bearer tokens for the endpoints that need it.
Split the code into modules - routers, models, store, auth
Write tests
```

Перевод запроса:

> Создай в backend/ бэкенд на FastAPI, реализующий спецификацию openapi.yaml.
> Используй хранилище в памяти и заполни его начальными данными, чтобы фронтенду было что показывать.
> Добавь аутентификацию с хешированными паролями и bearer-токенами для конечных точек, которым она нужна.
> Раздели код на модули: routers, models, store, auth.
> Напиши тесты.

АДАПТИРОВАТЬ: «FastAPI» → стек, одобренный после предыдущего запроса. Оставьте FastAPI только в том случае, если нужен конкретный наглядный пример, а не заполнитель.

Makefile позволяет легко запоминать и повторять команды запуска.

### 6. Makefile

- Запоминание правильной команды запуска для каждого сервиса создаёт лишние трудности, которые легко убрать автоматизацией.

```text
Create a Makefile so I can easily run it.
```

Перевод запроса:

> Создай Makefile, чтобы я мог легко это запускать.

АДАПТИРОВАТЬ: ничего специфичного для приложения нет, запрос универсален без изменений.

Когда бэкенд запущен, подключите к нему фронтенд, который до этого работал с имитациями.

### 7. Соединение фронтенда и бэкенда

- Поскольку все обращения к бэкенду уже сосредоточены в одном слое сервисов, переключение с имитации на настоящий клиент представляет собой одно изменение с небольшим риском.

```text
Switch the frontend to use the real backend client.
```

Перевод запроса:

> Переключи фронтенд на настоящий клиент бэкенда.

АДАПТИРОВАТЬ: ничего специфичного для приложения нет, запрос универсален без изменений.

Теперь приложение работает от начала до конца, но перезапуск по-прежнему стирает все данные. Это следующая задача.

### 8. База данных

- Данные должны сохраняться после перезапуска, поэтому замените хранилище в памяти постоянным.
- SQLite — хорошая отправная точка: отдельный сервер не нужен, всё состояние хранится в одном файле.
- Использование ORM и отсутствие привязки к конкретной базе данных облегчат последующий переход на Postgres.

```text
Replace the in-memory store with a database. Use SQLite and SQLAlchemy
Use an environment variable to configure which DB the server should connect to
Make it database-agnostic - later we will add support for other databases (e.g. postgres)
```

Перевод запроса:

> Замени хранилище в памяти базой данных. Используй SQLite и SQLAlchemy.
> Используй переменную окружения, чтобы задать, к какой БД должен подключаться сервер.
> Не привязывай реализацию к конкретной базе данных: позднее мы добавим поддержку других баз данных (например, postgres).

АДАПТИРОВАТЬ: «SQLite and SQLAlchemy» → средства стека бэкенда, одобренного в пункте 4. Оставьте это как наглядный пример или обобщите до «ORM».

Приложение работает локально от начала до конца. Далее нужно подготовить его к столкновению с реальным миром: к развёртыванию.

## Развёртывание

- Успех локально и успех в промышленной эксплуатации — разные задачи: настоящие сети, базы данных и инфраструктура добавляют новые варианты отказа.
- Один образ контейнера, а не два: собранный фронтенд представляет собой статические файлы, которые бэкенд может отдавать напрямую.
- SQLite подходил для разработки; Postgres — замена промышленного уровня, к которой ORM уже подготовил приложение.
- Развёртыванию можно доверять только после проверки настоящими тестами и повторения через CI, а не после единственного ручного запуска.

Даже развёрнутое и протестированное приложение нуждается в наблюдении. Здесь начинается этап эксплуатации.

### 9. Dockerfile

- В разработке фронтенд работает как отдельный процесс с отслеживанием изменений; в промышленной среде это просто статические файлы, поэтому собственный контейнер ему не нужен.
- Двухэтапная сборка компилирует фронтенд, а затем копирует в образ бэкенда только собранные файлы.

```text
Create a Dockerfile that builds the frontend with Node, then builds a Python image with the backend and the frontend static files.

Backend should serve the frontend.
```

Перевод запроса:

> Создай Dockerfile, который собирает фронтенд с помощью Node, а затем собирает образ Python с бэкендом и статическими файлами фронтенда.
>
> Бэкенд должен отдавать фронтенд.

АДАПТИРОВАТЬ: «Node»/«Python» → одобренные стеки фронтенда и бэкенда.

Соберите и запустите образ, затем проверьте, что настоящий сценарий с двумя пользователями работает внутри контейнера.

### 10. Postgres

- SQLite не требовал сервера базы данных, что упрощало локальную разработку; промышленной среде нужны гарантии надёжности и параллельной работы, которые даёт Postgres.
- Поскольку бэкенд уже использовал ORM без специфичных для SQLite возможностей, переход сводится к небольшому локальному изменению.

```text
Add Postgres support to the backend.
```

Перевод запроса:

> Добавь поддержку Postgres в бэкенд.

АДАПТИРОВАТЬ: ничего специфичного для приложения нет, запрос универсален без изменений.

Ручной запуск Postgres годится для одной команды, но приложению нужно совместное описание всех сервисов.

### 11. Docker Compose

- Один файл, запускающий приложение вместе с базой данных, удобнее жонглирования отдельными командами `docker run`.
- Проверка состояния гарантирует, что приложение дождётся фактической готовности Postgres перед запуском.

```text
Create docker-compose.yaml with two services: Postgres and the app.
```

Перевод запроса:

> Создай docker-compose.yaml с двумя сервисами: Postgres и приложением.

АДАПТИРОВАТЬ: ничего специфичного для приложения нет, запрос универсален без изменений.

Когда весь стек работает вместе, пора проверить его целиком, а не только по частям.

### 12. Интеграционные тесты

- У бэкенда уже могут быть тесты, созданные на предыдущих шагах; если их нет, теперь нужно добавить проверки его работы с настоящей базой данных.

```text
Create integration tests that run against docker-compose.yaml.
What scenarios should we test?
```

Перевод запроса:

> Создай интеграционные тесты, которые выполняются с использованием docker-compose.yaml.
> Какие сценарии следует проверить?

АДАПТИРОВАТЬ: ничего специфичного для приложения нет, запрос универсален без изменений.

Интеграционные тесты выявляют проблемы бэкенда и базы данных; сквозной тест выявляет проблемы во всём пользовательском сценарии.

### 13. Сквозной тест

- Контейнеризация и переход на Postgres — изменения, способные незаметно сломать настоящий пользовательский сценарий. Проверьте этот сценарий напрямую.
- Запуск с использованием docker-compose.yaml означает, что тест проверяет тот же стек, который действительно будет поставляться.

```text
Add an end-to-end test that runs against docker-compose.yaml.

Use Playwright to:

1. Log in as the interviewer (session 1).
2. Create an interview session.
3. Share the join link.
4. Join from a separate client as the candidate (session 2).
5. Change the canvas as the candidate (session 2).
6. Verify that the interviewer sees the change (session 1).

Put the tests in the e2e/ folder in the repository root.
```

Перевод запроса:

> Добавь сквозной тест, который выполняется с использованием docker-compose.yaml.
>
> Используй Playwright, чтобы:
>
> 1. Войти как интервьюер (сессия 1).
> 2. Создать сессию собеседования.
> 3. Поделиться ссылкой для присоединения.
> 4. Присоединиться из отдельного клиента как кандидат (сессия 2).
> 5. Изменить холст от имени кандидата (сессия 2).
> 6. Проверить, что интервьюер видит изменение (сессия 1).
>
> Помести тесты в папку e2e/ в корне репозитория.

АДАПТИРОВАТЬ: шаги 1–6 полностью специфичны для interview-canvas (интервьюер, кандидат, холст). Их нужно полностью переписать под двусторонний сценарий Study Relay: организатор публикует группу, студент подаёт заявку, организатор её одобряет, оба подтверждают начало работы. «Playwright» тоже задаёт конкретный инструмент: либо оставьте его как выбор для этого примера, либо обобщите до «инструмента автоматизации браузера».

Когда весь стек протестирован, приложение готово окончательно покинуть ваш компьютер, но целевая платформа пока не выбрана.

### 14. Выбор подхода к развёртыванию и CI/CD

- Облачный провайдер и продукт для CI требуют решения, а не выбора по умолчанию: спросите о компромиссах до создания инфраструктуры.

```text
Propose two ways to deploy and continuously deliver this application, comparing cost, complexity, and portability. Recommend one and wait for my approval before creating any infrastructure.
```

Перевод запроса:

> Предложи два способа развёртывания и непрерывной поставки этого приложения, сравнив стоимость, сложность и переносимость. Порекомендуй один и дождись моего одобрения, прежде чем создавать какую-либо инфраструктуру.

После одобрения платформы разверните на ней проверенный артефакт.

### 15. Развёртывание в AWS

- Временная учётная запись с правами администратора подходит для первого развёртывания при условии тщательного наблюдения за каждым шагом.
- После стадии проверки концепции управляемый сервис базы данных безопаснее, чем размещение базы на том же экземпляре, где работает приложение.

```text
Deploy this application to AWS. Use AWS CloudFormation.
```

Перевод запроса:

> Разверни это приложение в AWS. Используй AWS CloudFormation.

АДАПТИРОВАТЬ: запрос не универсален, он прямо называет AWS и CloudFormation. Поскольку в пункте 14 выбор теперь делается явно, переформулируйте его как «Разверни это приложение по одобренному плану» либо оставьте AWS/CloudFormation как конкретный результат выбора в примере.

Одно успешное ручное развёртывание не делает процесс воспроизводимым. Для этого нужен CI/CD.

### 16. Конвейер CI/CD

- Непрерывная интеграция выявляет поломки при каждой отправке изменений; непрерывное развёртывание превращает успешную проверку в работающий релиз.
- Краткосрочная роль, получаемая через OIDC, заменяет постоянные административные учётные данные, использованные для первого ручного развёртывания.

```text
Create a CI/CD pipeline that:

- runs backend and frontend tests in parallel
- builds the Docker Compose stack and runs integration and end-to-end tests against it
- deploys to AWS using a GitHub OIDC role
- validates that the deploy is successful by checking the health endpoint
```

Перевод запроса:

> Создай конвейер CI/CD, который:
>
> - параллельно запускает тесты бэкенда и фронтенда;
> - собирает стек Docker Compose и запускает для него интеграционные и сквозные тесты;
> - развёртывает приложение в AWS с использованием роли GitHub OIDC;
> - проверяет успешность развёртывания обращением к конечной точке проверки состояния.

АДАПТИРОВАТЬ: «AWS»/GitHub OIDC предполагают тот же конкретный выбор, что и пункт 15. Согласуйте их с результатом того запроса либо обобщите до «нашего облачного провайдера».

Теперь приложение развёртывается само. Следующая задача — поддерживать его безопасную работу для настоящих пользователей.

## Эксплуатация

- На раннем этапе допустимо сразу развёртывать каждую отправку изменений в среду, которую видят пользователи, но настоящим пользователям нужен буфер: среда разработки, принимающая риск на себя до промышленной среды.
- Однократная сборка образа и продвижение того же артефакта в промышленную среду устраняют целый класс ошибок «в dev работало, в prod сломалось».
- Телеметрия — метрики, журналы и трассировки — превращает «что-то сломалось» в «вот что именно сломалось и почему».
- Агент может расследовать и даже исправлять инциденты, но только человек решает, что попадёт в промышленную среду.

Только сквозная репетиция настоящего сбоя позволяет понять, действительно ли работает этот цикл.

### 17. Вторая среда

- Повторное использование существующей инфраструктуры как кода для второй копии позволяет напрямую перенести большую часть настройки.

```text
Create a second, independent copy of our infrastructure. We will use the copy as production, and the existing infrastructure as a dev environment.
```

Перевод запроса:

> Создай вторую, независимую копию нашей инфраструктуры. Копию мы будем использовать как промышленную среду, а существующую инфраструктуру — как среду разработки.

АДАПТИРОВАТЬ: ничего специфичного для приложения нет, запрос универсален без изменений.

При наличии двух сред CI/CD должен различать поставку в одну среду и продвижение в другую.

### 18. Ручной процесс продвижения

- В среду разработки изменения по-прежнему развёртываются автоматически при каждой отправке; промышленная среда обновляется только после явного одобрения человеком.

```text
Create a manual GitHub Actions workflow that promotes the dev version to production.
```

Перевод запроса:

> Создай запускаемый вручную процесс GitHub Actions, который продвигает версию из dev в промышленную среду.

АДАПТИРОВАТЬ: «GitHub Actions» предполагает инструмент CI/CD, выбранный в пункте 14. Сохраните согласованность либо обобщите до «ручного процесса продвижения с использованием нашей системы CI».

Прежде чем такому продвижению можно будет доверять, нужно перестать выполнять сборку и развёртывание одним объединённым шагом.

### 19. Разделение сборки и развёртывания, теги образов

- Сборка во время развёртывания означает, что неудачная сборка всё равно может запустить сломанное развёртывание, а продвижение в prod повторно собирает образ вместо использования уже проверенного в dev.
- Тег с отметкой времени и SHA коммита делает «именно эту сборку» однозначно определённым объектом, который можно продвигать.

```text
Currently we build the image during the deploy stage.

Split it into two stages:

- Build: build the image and push it to a container registry (ECR)
- Deploy: pull the image from the registry and serve it

The manual prod promotion CI/CD workflow pulls the currently deployed dev image to prod.

Tag each image using the YYYYMMDD-HHMMSS-shortsha pattern (e.g. "20260818-163457-83242da")
```

Перевод запроса:

> Сейчас мы собираем образ на этапе развёртывания.
>
> Раздели процесс на два этапа:
>
> - Build: собрать образ и отправить его в реестр контейнеров (ECR).
> - Deploy: получить образ из реестра и запустить его.
>
> Ручной процесс CI/CD для продвижения в prod переносит в prod образ, который в данный момент развёрнут в dev.
>
> Присваивай каждому образу тег по шаблону YYYYMMDD-HHMMSS-shortsha (например, «20260818-163457-83242da»).

АДАПТИРОВАТЬ: «ECR» предполагает выбор AWS в пункте 14. Сохраните согласованность либо обобщите до «реестра контейнеров».

Когда надёжный процесс выпуска настроен, следующая задача — узнавать, когда внутри него что-то ломается.

### 20. Инструментирование с OpenTelemetry

- Базовые инфраструктурные метрики (CPU, память, запросы в секунду) указывают на неполадку, но не объясняют, что произошло внутри запроса.
- OpenTelemetry — стандарт, не привязанный к поставщику, поэтому инструментирование на его основе не закрепляет приложение за конкретным бэкендом наблюдаемости.

```text
Instrument the backend with OpenTelemetry.

Include in the telemetry:

- service name
- environment
- deployed version
```

Перевод запроса:

> Инструментируй бэкенд с помощью OpenTelemetry.
>
> Включи в телеметрию:
>
> - имя сервиса;
> - среду;
> - развёрнутую версию.

АДАПТИРОВАТЬ: ничего специфичного для приложения нет, запрос универсален без изменений. Сам OpenTelemetry — стандарт, не привязанный к поставщику, а не конкретный продукт, поэтому отдельный запрос на выбор здесь не нужен.

Телеметрия полезна только тогда, когда её действительно собирают и хранят там, где её можно посмотреть.

### 21. Выбор бэкенда наблюдаемости

- Куда поступает телеметрия — в какое хранилище метрик, журналов и трассировок, на какую панель — это настоящий выбор с множеством допустимых вариантов, который стоит обсудить явно.

```text
Propose two options for storing and viewing this telemetry — metrics, logs, and traces. Recommend one and wait for my approval.
```

Перевод запроса:

> Предложи два варианта хранения и просмотра этой телеметрии: метрик, журналов и трассировок. Порекомендуй один и дождись моего одобрения.

После одобрения бэкенда подключите коллектор и использующие его панели.

### 22. Стек OTel Collector

- OpenTelemetry Collector находится между приложением и хранилищем, поэтому приложению не нужно знать, куда в конечном счёте попадает телеметрия.
- Запуск стека наблюдаемости как отдельного проекта Compose сохраняет его независимость от стека приложения.

```text
Add an OpenTelemetry Collector.

Create "observability/" directory with Docker Compose for:

- OpenTelemetry Collector
- Prometheus
- Loki
- Tempo
- Grafana

Keep this as a separate Compose project from the application stack.
```

Перевод запроса:

> Добавь OpenTelemetry Collector.
>
> Создай каталог «observability/» с Docker Compose для:
>
> - OpenTelemetry Collector;
> - Prometheus;
> - Loki;
> - Tempo;
> - Grafana.
>
> Оставь это отдельным проектом Compose, независимым от стека приложения.

АДАПТИРОВАТЬ: Prometheus/Loki/Tempo/Grafana → инструменты, одобренные в пункте 21. Оставьте как наглядный пример либо обобщите до «одобренного стека наблюдаемости».

Необработанная телеметрия становится полезной только после превращения в метрики, за которыми имеет смысл следить.

### 23. Метрики приложения

- Общие инфраструктурные метрики не показывают, работает ли сам продукт. Вместо этого отслеживайте реальные действия пользователей.
- Метки среды и версии у каждой метрики позволяют увидеть регрессию в привязке к релизу.

```text
Track these application metrics:

- interview rooms created
- active interview participants
- canvas elements created
- failures in component creation

Include the environment and deployed version.
```

Перевод запроса:

> Отслеживай следующие метрики приложения:
>
> - созданные комнаты собеседований;
> - активные участники собеседований;
> - созданные элементы холста;
> - сбои создания компонентов.
>
> Включи среду и развёрнутую версию.

АДАПТИРОВАТЬ: все четыре метрики специфичны для interview-canvas. Замените их метриками Study Relay (например, созданные группы, заявки на вступление, подтверждения начала работы, регистрации продолжений эстафеты или другие показатели, на которых мы остановимся).

Метрики помогают только тогда, когда есть место, где их действительно можно увидеть.

### 24. Панель Grafana

- Панель, которую нельзя отфильтровать по среде и версии, не отвечает на вопрос «вызвал ли это последний релиз».

```text
Add a Grafana panel with these metrics.
Make it possible to filter by environment and deployed version
```

Перевод запроса:

> Добавь панель Grafana с этими метриками.
> Сделай возможной фильтрацию по среде и развёрнутой версии.

АДАПТИРОВАТЬ: «Grafana» предполагает соответствующий результат пункта 21. Сохраните согласованность либо обобщите до «панели дашборда».

Панель работает локально. Теперь нужно развернуть сам стек наблюдаемости.

### 25. Развёртывание стека наблюдаемости

- Инфраструктура наблюдаемости развёртывается, как и любая другая: отдельно от приложения, но с доступом из обеих сред.

```text
Deploy the observability stack. It should be separate from the application stack.
Connect both development and production to it.
```

Перевод запроса:

> Разверни стек наблюдаемости. Он должен быть отделён от стека приложения.
> Подключи к нему среду разработки и промышленную среду.

АДАПТИРОВАТЬ: ничего специфичного для приложения нет, запрос универсален без изменений.

За панелями должен наблюдать человек; оповещения в этом не нуждаются.

### 26. Оповещение

- Метрика может незаметно ухудшаться часами, если никто не смотрит на панель. Именно оповещение заставляет обратить на это внимание.
- Порог, настроенный для небольшого трафика, а также указание ответственного и ссылка на панель делают оповещение полезным для действий, а не шумом.

```text
Add an actionable alert for repeated canvas component-creation failures.

Use a threshold and duration that represent real user impact. Include the service, environment, deployed version, owner, and dashboard URL in the alert.
```

Перевод запроса:

> Добавь требующее действий оповещение о повторяющихся сбоях создания компонентов холста.
>
> Используй порог и длительность, соответствующие реальному влиянию на пользователей. Включи в оповещение сервис, среду, развёрнутую версию, ответственного и URL панели.

АДАПТИРОВАТЬ: «canvas component-creation failures» → аналогичный сбой в Study Relay (например, неудачные заявки на вступление или подтверждения начала работы).

Когда оповещение может сработать, на него действительно кто-то должен реагировать.

### 27. Процесс дежурного инженера

- Опрос API оповещений и передача подробностей агенту программирования, работающему без интерактивного интерфейса, — это весь цикл дежурства в миниатюре.

```text
Add an on-call-engineer/ directory with a script that polls the observability alert API every minute.

When an alert fires, pass the alert details to a headless coding agent.
```

Перевод запроса:

> Добавь каталог on-call-engineer/ со скриптом, который каждую минуту опрашивает API оповещений системы наблюдаемости.
>
> Когда срабатывает оповещение, передавай его подробности агенту программирования, работающему без интерактивного интерфейса.

АДАПТИРОВАТЬ: ничего специфичного для приложения нет, запрос универсален без изменений.

Нужно явно определить, что этому агенту разрешено делать с оповещением.

### 28. Системный запрос для дежурного агента

- Сначала расследуйте проблему и воспроизведите сбой. Вносите исправление только в том случае, если оно небольшое, проверено тестами и закоммичено в отдельную ветку; никогда не развёртывайте его напрямую.
- Ложное срабатывание нужно объяснить, а не «исправлять» изменением кода, который на самом деле не был сломан.

```text
You are the on-call engineer for this repository. An alert just fired.

Investigate the root cause. Read the code and reproduce the failure.
If you find a real bug, make the smallest correction, run the backend tests, and commit the fix with a clear message.
If the alert is a false positive, explain why and do not change the code.
```

Перевод запроса:

> Ты дежурный инженер этого репозитория. Только что сработало оповещение.
>
> Расследуй первопричину. Прочитай код и воспроизведи сбой.
> Если обнаружишь настоящую ошибку, внеси минимальное исправление, запусти тесты бэкенда и закоммить исправление с понятным сообщением.
> Если оповещение ложное, объясни почему и не меняй код.

АДАПТИРОВАТЬ: ничего специфичного для приложения нет, запрос универсален без изменений.

Единственный способ убедиться, что это действительно работает, — намеренно что-нибудь сломать.

### 29. Внесение ошибки

- Воспроизводимая ошибка, которую не выявляет существующий набор тестов, — именно та регрессия, для обнаружения которой существует весь этот цикл.

```text
Introduce a realistic bug in canvas component creation.

For some requests, creating a component should fail even though the existing tests pass. Keep the failure reproducible so we can test that the bug causes an alert and the on-call response.
```

Перевод запроса:

> Внеси реалистичную ошибку в создание компонентов холста.
>
> Для некоторых запросов создание компонента должно завершаться неудачей, хотя существующие тесты проходят. Сохрани воспроизводимость сбоя, чтобы мы могли проверить, что ошибка вызывает оповещение и реакцию дежурного.

АДАПТИРОВАТЬ: «canvas component creation» → аналогичная операция в Study Relay (например, подтверждение начала работы).

После того как дежурный агент докажет способность активироваться и отреагировать, нужно завершить упражнение и убрать его временные ресурсы.

### 30. Очистка

- Созданные для обучения ресурсы стоят денег, если оставить их работающими. Удаляйте их столь же осознанно, как создавали.

```text
Delete the CloudFormation stacks.
```

Перевод запроса:

> Удали стеки CloudFormation.

АДАПТИРОВАТЬ: запрос не универсален, поскольку предполагает выбор CloudFormation в пункте 14. Переформулируйте его независимо от инструментов, например: «Удали инфраструктуру, которую мы создали для этого упражнения», либо оставьте CloudFormation как конкретный выбор примера.

Это минимальный заслуживающий доверия цикл. Настоящие продукты развиваются дальше.

## Дальнейшее развитие

- Ничто из перечисленного далее не рассмотрено в предыдущем руководстве: это то, чего ещё не хватает после запуска минимального цикла.
- Один экземпляр, развёрнутый вручную, и резервная копия, созданная вручную, подходят для обучения, но не выдерживают настоящей эксплуатации или реального инцидента.
- Каждый запрос ниже развивает уже принятое в руководстве решение — платформу, базу данных, конвейер развёртывания, — а не начинает что-то новое.

Эти запросы нужны, чтобы довести цикл до промышленного уровня, а не просто заставить его работать.

### 31. Управляемая среда выполнения

- Контейнер, запускаемый вручную, подходит для обучения; управляемая платформа выполняет перезапуски, размещение и масштабирование без вашего постоянного наблюдения.

```text
Evaluate managed runtimes for this container and recommend the simplest one that fits our scaling and budget needs.
```

Перевод запроса:

> Оцени управляемые среды выполнения для этого контейнера и порекомендуй самый простой вариант, подходящий нашим требованиям к масштабированию и бюджету.

Среда выполнения может масштабировать приложение, но данным всё равно нужен план на случай катастрофы.

### 32. Резервное копирование и восстановление

- Резервная копия, которую никто не восстанавливал, — это предположение, а не страховка.

```text
Add scheduled database backups. Restore the latest one into a fresh environment and confirm the data matches.
```

Перевод запроса:

> Добавь резервное копирование базы данных по расписанию. Восстанови последнюю копию в новой среде и подтверди, что данные совпадают.

Даже приложение с идеальными резервными копиями безопасно лишь настолько, насколько безопасна сеть, в которой оно доступно.

### 33. Сокращение публичной доступности

- База данных и стек наблюдаемости не должны быть доступны из публичного интернета: это нужно только приложению.

```text
Put the database and observability stack on a private network. Only the application should be publicly reachable.
```

Перевод запроса:

> Размести базу данных и стек наблюдаемости в частной сети. Публично доступным должно быть только приложение.

Приложение с безопасно организованным доступом всё ещё должно доказать, что выдерживает настоящую нагрузку.

### 34. Нагрузочное тестирование

- Корректная работа с одним пользователем ничего не говорит о работе с тысячей. Измерьте это прежде, чем настоящий трафик обнаружит предел.

```text
Load test the busiest endpoint and report throughput, latency, and error rate as concurrency increases.
```

Перевод запроса:

> Проведи нагрузочное тестирование самой загруженной конечной точки и сообщи пропускную способность, задержку и долю ошибок по мере увеличения числа параллельных запросов.

Когда пределы известны, релизы тоже можно начинать выпускать осторожнее.

### 35. Постепенная поставка

- Продвижение сборки сразу для 100% пользователей означает, что плохой релиз одновременно затронет всех. Канареечное развёртывание ограничивает масштаб последствий.

```text
Add canary deployment: route a small percentage of traffic to the new version and roll back automatically on errors.
```

Перевод запроса:

> Добавь канареечное развёртывание: направляй небольшой процент трафика на новую версию и автоматически откатывай её при ошибках.
