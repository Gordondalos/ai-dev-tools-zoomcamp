# План иллюстраций для статьи о полном цикле разработки

Используйте схемы, когда читателю нужно понять последовательность, зависимость или
архитектуру. Используйте скриншоты, когда визуальное подтверждение важнее
структуры. Каждая иллюстрация должна раскрывать мысль своего раздела, а не
повторять общий обзор целиком.

| Место в статье | Формат | Визуальное решение | Что нужно объяснить |
| --- | --- | --- | --- |
| Введение | Скриншот продукта | Покажите Snake Royale во время игры, с таблицей лидеров или режимом наблюдателя рядом с игровым полем. | Сразу дать читателям представление о приложении, которое они создадут. |
| Обзор | Схема рабочего процесса | Используйте готовую обзорную схему в три ряда: фронтенд, контракт API, бэкенд, соединение компонентов, постоянное хранение данных, контейнеры, AWS, CI/CD, общедоступное приложение. | Показать, почему важен порядок действий и как каждый этап создаёт основу для следующего. |
| Сначала фронтенд | Скриншот с пояснениями | Покажите работающий фронтенд с двумя небольшими выносками: «имитация бэкенда» и «центральный слой сервисов». Во второй небольшой вставке с деревом файлов можно показать `mock.ts`, `http.ts` и `index.ts`. | Подтвердить, что интерфейс работает ещё до появления бэкенда, и наглядно показать переключение сервисов. |
| Задаём ассистенту правила проекта | Иллюстрация к тексту | Покажите `AGENTS.md` в корне репозитория рядом с терминалом агента для программирования, который использует `uv` и фиксирует изменения в коммитах. Это должна быть композиция из файла и терминала, а не блок-схема. | Показать, что один небольшой файл задаёт повторяющиеся правила работы агента над проектом. |
| Спецификация между двумя сторонами | Схема контракта | Поместите `openapi.yaml` в центр, слой сервисов React слева, а маршруты FastAPI справа. Стрелки с обеих сторон должны указывать на контракт. | Показать, что фронтенд и бэкенд согласуют взаимодействие через один явно заданный документ. |
| Бэкенд на основе спецификации | Сравнительный скриншот | Разместите нужную часть `openapi.yaml` рядом со страницей `/docs` FastAPI для той же конечной точки. Выделите совпадающие путь, метод, запрос и ответ. | Показать, как письменный контракт соотносится с маршрутами, которые бэкенд действительно предоставляет. |
| Соединяем компоненты | Диаграмма последовательности запроса | Браузер → компонент React → HTTP-клиент слоя сервисов → маршрут FastAPI → ответ. Добавьте одну красную ветку несоответствия, возвращающую `422`, а затем исправление по `openapi.yaml`. | Показать обычный путь запроса и место, где происходит отладка интеграции. |
| Постоянное хранение данных | Схема эволюции | Покажите один и тот же интерфейс репозитория или хранилища, подключённый сначала к памяти, затем к SQLite, а потом к Postgres. Оставьте `DATABASE_URL` неизменным над тремя реализациями. | Показать, что интерфейс остаётся стабильным, пока меняется реализация хранилища. |
| Контейнеры | Схема сборки и выполнения | Слева покажите, как сборка Node создаёт статические файлы и как они попадают в образ Python. Справа покажите, как Docker Compose запускает приложение рядом с Postgres и именованным томом. | Объяснить и многоэтапный образ, и топологию среды выполнения, не смешивая их в текстовом описании. |
| Развёртывание | Архитектурная схема AWS | Браузер → общедоступный экземпляр EC2 с запущенным контейнером приложения → Aurora PostgreSQL. Соедините EC2 с Secrets Manager и обведите ресурсы AWS одной общей границей CloudFormation. | Показать, что развёртывается и какой сервис отвечает за данные и учётные данные. |
| Конвейер и отказ от постоянных ключей | Схема CI/CD | Начните с отправки изменений в `main`; разделите поток на тесты фронтенда и бэкенда; объедините его в интеграционные тесты; продолжите до развёртывания. Добавьте GitHub OIDC → AWS как путь аутентификации с краткосрочными учётными данными. | Показать граф зависимостей тестов и объяснить, почему постоянный ключ AWS не нужен. |
| Что мы оставили за рамками | Дорожная карта развития | Используйте простую лестницу или шкалу перспектив: CORS, постоянные сессии, миграции, управляемый хостинг, WebSockets. Не создавайте впечатления, что каждому приложению сразу нужны все эти шаги. | Показать, когда упрощения первой версии начинают иметь значение. |
| Что меняется после первой версии | Схема «до и после» | Слева: один человек задаёт по одному промпту за раз. Справа: спецификация → список задач → реализация → независимая проверка → конвейер. | Показать переход от исследовательской работы с промптами к воспроизводимому процессу разработки. |
| Далее в серии | Иллюстрация дорожной карты серии | Используйте три соединённые карточки: возможности агентов, безопасность и DevOps, собственный проект читателя с полным циклом разработки. | Дать представление об оставшихся модулях, не вводя ещё одну техническую архитектуру. |

## Рекомендуемый порядок подготовки

1. Сохраните обзорную схему, уже добавленную в статью.
2. Затем создайте схемы контракта API, контейнеров, AWS и CI/CD. Они дают
   наибольшую пользу для объяснения.
3. Сделайте скриншоты продукта, документации FastAPI и сервисов фронтенда в
   работающем репозитории Snake Royale.
4. Добавляйте дорожную карту развития и схему процесса «до и после» только в том
   случае, если статье всё ещё нужны дополнительные визуальные паузы.
5. Рассматривайте иллюстрации `AGENTS.md` и дорожной карты серии как необязательные улучшения.
