## Контейнеризация

При локальном запуске приложения нам нужно выполнить две команды: одну для фронтенда и одну для бэкенда.

Запустим их в двух отдельных терминалах:

```bash
# first terminal
cd frontend
npm run dev

# second terminal
make run
```

Итак, у нас есть два сервиса, и нам нужно развернуть их в рабочей среде. Можно подумать, что нам нужны два контейнера: один для фронтенда и один для бэкенда.

Во время разработки мы запускаем фронтенд как отдельный сервис, потому что используем Vite. Vite следит за кодом фронтенда и обновляет страницу, когда мы вносим изменения. Это очень удобно: изменения видны сразу.

В рабочей среде код фронтенда не меняется во время работы приложения. Мы собираем его один раз и получаем набор статических файлов HTML, CSS и JavaScript.

Это означает, что отдельный контейнер для фронтенда не нужен: эти файлы может отдавать бэкенд. Поэтому нам достаточно одного контейнера.

<figure>
  <img src="../../../articles/images/03-containerization.png" alt="Три этапа показывают раздельную работу фронтенда Vite и бэкенда FastAPI при разработке, сборку фронтенда в статические файлы и единый контейнер приложения, обслуживающий фронтенд и бэкенд в рабочей среде">
  <figcaption>При разработке фронтенд и бэкенд работают отдельно; в рабочей среде FastAPI отдаёт собранный фронтенд из одного контейнера</figcaption>
</figure>

Попросим помощника для программирования создать его:

```text
Create a Dockerfile that builds the frontend with Node, then builds a Python image with the backend and the frontend static files.

Backend should serve the frontend.
```

Перевод промпта:

> Создай Dockerfile, который собирает фронтенд с помощью Node, а затем собирает образ Python с бэкендом и статическими файлами фронтенда.
>
> Бэкенд должен отдавать фронтенд.

Получаем двухэтапную сборку Docker:

- Сначала используем образ Node.js для сборки фронтенда
- Затем собираем бэкенд и копируем только файлы фронтенда, без зависимостей Node.js

Посмотреть [Dockerfile можно здесь](https://github.com/alexeygrigorev/interview-canvas-share/blob/main/Dockerfile).

Соберём и запустим образ из корня репозитория:

```bash
docker build -t sdip:latest .

docker run --rm -p 8000:8000 \
  -v sdip-data:/data \
  -e SDIP_DATABASE_URL=sqlite:////data/sdip.db \
  --name sdip sdip:latest
```

Здесь мы указываем именованный том Docker `sdip-data`, в котором база SQLite будет сохраняться между запусками контейнера.

Откроем приложение по адресу [localhost:8000](http://localhost:8000) и проверим его:

- Создадим сессию собеседования
- Откроем ссылку для подключения в другом окне браузера
- Переместим элемент в окне кандидата
- Проверим, что интервьюер видит изменение


## Переход с SQLite на Postgres

SQLite очень удобна для локальной разработки. Она хранит данные в одном файле и не требует отдельного сервера базы данных.

Но в рабочей среде мы обычно используем Postgres или аналогичную базу данных.

Когда мы закладывали основу [в предыдущей статье](https://aishippingblog.com/p/build-and-ship-a-full-stack-app-with), мы попросили агента для программирования использовать SQLAlchemy.

Я сделал это специально, потому что знал: позже я перейду на Postgres.

Запустим Postgres локально:

```bash
docker run -d \
  --name interview-canvas-db \
  -e POSTGRES_USER=sdip \
  -e POSTGRES_PASSWORD=sdip \
  -e POSTGRES_DB=sdip \
  -p 5432:5432 \
  -v interview-canvas-pgdata:/var/lib/postgresql/data \
  postgres:16-alpine
```

Теперь можно попросить помощника использовать её:

```text
Add Postgres support to the backend.
```

Перевод промпта:

> Добавь поддержку Postgres в бэкенд.

Запустим бэкенд с подключением к Postgres из корня репозитория:

```bash
export SDIP_DATABASE_URL=postgresql://sdip:sdip@localhost:5432/sdip
make run
```

Когда всё будет готово, повторим проверку с двумя сессиями.

## Docker Compose

Раньше я запускал контейнер Postgres отдельной командой.
Но теперь поместим все сервисы, необходимые нашему приложению, в один файл Docker Compose.

С этим файлом всё приложение можно запустить одной командой `docker compose up`.

Попросим помощника реализовать это:

```text
Create docker-compose.yaml with two services: Postgres and the app.
```

Перевод промпта:

> Создай docker-compose.yaml с двумя сервисами: Postgres и приложением.

В файле задаётся база данных и добавляется проверка работоспособности, чтобы наше приложение ждало, пока Postgres будет готова принимать подключения.

Запустим:

```bash
docker compose up --build
```

В нашем случае приложение запускается по адресу [localhost:8100](http://localhost:8100).

## Интеграционные и сквозные тесты

Возможно, ИИ-помощник уже создал некоторые тесты бэкенда.

Если нет, попросим его создать интеграционные тесты:

```text
Create integration tests that run against docker-compose.yaml.
What scenarios should we test?
```

Перевод промпта:

> Создай интеграционные тесты, которые проверяют окружение из docker-compose.yaml.
> Какие сценарии следует проверить?

Мы добавили две вещи, которые потенциально могут сломаться, поэтому проверим и их. Убедимся, что:

- Фронтенд собирается корректно
- Бэкенд может взаимодействовать с Postgres

Попросим ИИ-помощника реализовать тест:

```text
Add an end-to-end test that runs against docker-compose.yaml.

Use Playwright to:

1. Log in as the interviewer (session 1).
2. Create an interview session.
3. Share the join link.
4. Join from a separate client as the candidate (session 2).
5. Change the canvas as the candidate (session 2).
6. Verify that the interviewer sees the change (session 1).

Put the tests in the e2e/ folder in the repository root.
```

Перевод промпта:

> Добавь сквозной тест, который проверяет окружение из docker-compose.yaml.
>
> Используй Playwright, чтобы:
>
> 1. Войти в систему как интервьюер (сессия 1).
> 2. Создать сессию собеседования.
> 3. Поделиться ссылкой для подключения.
> 4. Подключиться из отдельного клиента как кандидат (сессия 2).
> 5. Изменить холст от имени кандидата (сессия 2).
> 6. Убедиться, что интервьюер видит изменение (сессия 1).
>
> Помести тесты в папку e2e/ в корне репозитория.

После завершения мы сможем запускать тесты одной командой make:

```
make e2e
```


## Развёртывание в AWS

Теперь мы уверены, что приложение работает хорошо. Можно его развернуть.

Наше приложение работает в контейнере и нуждается только в Postgres, поэтому вариантов развёртывания много. Можно использовать Render, Railway, Fly.io или любую другую управляемую систему для контейнеров.

[В прошлом году мы разворачивали приложение на Render](https://github.com/DataTalksClub/ai-dev-tools-zoomcamp/tree/main/cohorts/2025/02-end-to-end), но в этом году я хочу развернуть его в AWS. Вам необязательно использовать AWS: вместо этого можно попросить помощника для программирования порекомендовать среду для вашего приложения.

Попросим помощника развернуть его:

```text
Deploy this application to AWS. Use AWS CloudFormation.
```

Перевод промпта:

> Разверни это приложение в AWS. Используй AWS CloudFormation.

Для этого вам нужен пользователь AWS. Обычно я создаю временного пользователя с правами администратора и слежу за каждым шагом агентов для программирования.

Мы используем [готовый шаблон CloudFormation](https://github.com/alexeygrigorev/interview-canvas-share/blob/main/deploy/aws/sdip-stack.yaml), чтобы запустить приложение, Postgres и Caddy на одном экземпляре EC2 и настроить HTTPS.

## CI/CD с GitHub Actions

Для развёртывания приложения мы использовали пользователя с правами администратора. Для первого развёртывания это допустимо, но только под тщательным наблюдением. Следующий шаг — настроить CI/CD и убрать этот доступ.

- Непрерывная интеграция (CI) означает, что каждый раз, когда мы вносим изменение и отправляем его на GitHub, автоматически запускаются все тесты, чтобы убедиться, что мы ничего не сломали.
- Непрерывное развёртывание (CD) означает автоматическое развёртывание этого изменения.

В GitHub для этого используется GitHub Actions.

Настроим его. При каждой отправке изменений в main мы хотим:

- запускать тесты фронтенда и бэкенда
- собирать контейнеры
- запускать интеграционные тесты
- запускать сквозные тесты
- если все тесты проходят, разворачивать новую версию

Для последнего шага раннеру, то есть процессу, который будет разворачивать приложение, понадобится доступ к нашей инфраструктуре AWS. Для этого мы будем использовать
OpenID Connect (OIDC): раннер примет роль с необходимыми разрешениями и обновит приложение.

<figure>
  <img src="../../../articles/images/03-ci-cd.png" alt="Отправка изменений в main запускает параллельно тесты фронтенда и бэкенда, затем собирает стек Docker Compose, запускает интеграционные и сквозные тесты и разворачивает приложение в AWS через OIDC">
  <figcaption>GitHub Actions параллельно запускает тесты фронтенда и бэкенда, проверяет весь стек, а затем выполняет развёртывание в AWS</figcaption>
</figure>

Создадим роль и рабочий процесс:

```text
Create a CI/CD pipeline that:

- runs backend and frontend tests in parallel
- builds the Docker Compose stack and runs integration and end-to-end tests against it
- deploys to AWS using a GitHub OIDC role
- validates that the deploy is successful by checking the health endpoint
```

Перевод промпта:

> Создай конвейер CI/CD, который:
>
> - параллельно запускает тесты бэкенда и фронтенда
> - собирает стек Docker Compose и запускает для него интеграционные и сквозные тесты
> - выполняет развёртывание в AWS с помощью роли GitHub OIDC
> - подтверждает успешность развёртывания, проверяя эндпоинт работоспособности

[Готовый рабочий процесс](https://github.com/alexeygrigorev/interview-canvas-share/blob/main/.github/workflows/ci.yml) использует для развёртывания роль AWS с ограниченными правами.

Измените что-нибудь в приложении, создайте коммит и отправьте изменения, чтобы увидеть, как они появляются в работающем приложении.

## Очистка ресурсов

Когда мы закончим, нужно удалить все ресурсы, созданные CloudFormation:

```bash
aws cloudformation delete-stack --stack-name sdip
aws cloudformation wait stack-delete-complete --stack-name sdip
```

Если вы создали запись DNS или переменные развёртывания GitHub, удалите и их: стек ими не управляет.

## Следующий шаг после развёртывания

Подведём итог тому, что мы уже сделали:

- Создали фронтенд-приложение на React
- Затем определили API между фронтендом и бэкендом с помощью спецификаций OpenAPI
- На основе спецификаций создали бэкенд
- После этого добавили в бэкенд поддержку базы данных с помощью SQLite и SQLAlchemy
- Чтобы упростить развёртывание приложения, поместили фронтенд и бэкенд в один контейнер. Бэкенд отдаёт фронтенд.
- Для перехода в рабочую среду заменили SQLite на Postgres.
- Затем упростили локальный запуск всех компонентов с помощью Docker Compose
- Когда всё оказалось в Compose, создали сквозной тест
- Взяли приложение, которое работало локально, и развернули его в AWS с помощью CloudFormation
- Наконец, создали конвейер развёртывания CI/CD, чтобы автоматически разворачивать каждое изменение.
