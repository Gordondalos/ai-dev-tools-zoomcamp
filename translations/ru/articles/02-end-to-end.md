# Создание и выпуск full-stack-приложения с ИИ-помощниками по программированию

Это вторая статья серии для [AI Dev Tools Zoomcamp](https://github.com/DataTalksClub/ai-dev-tools-zoomcamp), бесплатного курса, который мы проводим в DataTalks.Club.

В [первой статье](https://aishippingblog.com/p/ai-native-development-specifications) я рассказывал о превращении идеи в спецификацию. Спецификация — только начало. В этой статье мы с нуля создадим приложение целиком. Рассмотрим и фронтенд, и бэкенд, добавим базу данных и добьёмся того, чтобы приложение работало локально.

Мы создадим приложение для собеседований по проектированию систем.

Как интервьюер вы создаёте сессию и делитесь ссылкой с кандидатом. Он может создавать схемы в приложении, а вы видите изменения в реальном времени.

Оба фронтенда подключаются к одной комнате через WebSocket, поэтому изменения появляются
в обеих сессиях одновременно.
Бэкенд на FastAPI обрабатывает эти события и сохраняет их в SQLite.

## Обзор

Как и в [предыдущей статье](https://aishippingblog.com/p/ai-native-development-specifications), мы начинаем с идеи. Поскольку пока это лишь
идея, мы превращаем её в спецификацию с помощью ChatGPT.

После этого приступаем к разработке:

1. Генерируем фронтенд, который использует заглушки вызовов бэкенда.
2. Определяем контракт между бэкендом и фронтендом, создавая спецификации OpenAPI на основе сервисного слоя фронтенда.
3. Реализуем бэкенд на FastAPI, подключаем его к фронтенду и тестируем приложение.
4. Добавляем постоянное хранение данных с помощью SQLite и SQLAlchemy.

На каждом этапе мы получаем что-то конкретное, что можно проверить:

- Сначала создаём спецификацию и убеждаемся, что она отражает то, что мы хотим построить.
- Затем по спецификации создаём прототип фронтенда, с которым можно взаимодействовать. Мы используем заглушки вызовов бэкенда, чтобы проверить идею.
- После этого подключаем фронтенд к бэкенду. Начинаем с хранилища в памяти,
  чтобы убедиться, что связь между фронтендом и бэкендом работает.
- Наконец, добавляем базу данных, чтобы приложение сохраняло состояние после перезапуска.

В результате у нас будет работающее локальное приложение, готовое к развёртыванию.

## Начните со спецификации

Прежде чем создавать фронтенд, нужно точно описать приложение. Если этого не сделать, мы получим что-то работающее, но не то, что нам нужно.

Для нашего приложения нужно определить:

- кто создаёт сессию собеседования;
- как к ней присоединяется кандидат;
- какие компоненты можно размещать на холсте;
- как оба человека видят изменения в реальном времени.

Это называется «разработкой на основе спецификаций». Мы не будем долго останавливаться на этой теме, потому что ей была посвящена предыдущая статья [Разработка с ИИ в основе процесса: спецификации, проектирование циклов и графов](https://aishippingblog.com/p/ai-native-development-specifications).

Для создания спецификации я всегда использую ChatGPT в режиме диктовки. На этом этапе дайте помощнику как можно больше информации.

## Сначала фронтенд

Теперь у нас есть спецификация, но это лишь текст. Дальше можно действовать несколькими способами:

- Сосредоточиться на слое базы данных, определить сущности и пройти весь путь вверх через бэкенд к фронтенду.
- Или начать с описания OpenAPI, определить взаимодействие бэкенда и фронтенда, а затем разрабатывать их независимо.
- Или сначала сосредоточиться на фронтенде, а затем создать всё остальное.

Все эти подходы имеют смысл, и у каждого есть свои плюсы и минусы.

Для простых проектов, которые вы разрабатываете в одиночку, я рекомендую начинать с фронтенда. Вы сможете быстро оценить, двигаетесь ли в правильном направлении и способно ли приложение решить вашу проблему.

Рассматривайте это как способ проверить идею и спецификацию, прежде чем создавать остальные части приложения.

На этом этапе я использую [Lovable](https://lovable.dev/), который генерирует приложение на React по
одному промпту. Replit, v0 и Bolt — похожие инструменты, которые тоже можно использовать.

Можно также сразу начать с помощников по программированию и попросить их создать приложение на React или на любой другой нужной вам технологии.

Я использую Lovable, потому что он создаёт очень приятный дизайн. Кроме того, я не фронтенд-разработчик и мало знаю о мире фронтенда. Lovable делает за меня технологический выбор, в осмысленности которого я уверен, тогда как агент для программирования может выбрать что-то произвольное.

Теперь откройте любой выбранный инструмент и дайте ему такой промпт:

```text
Create a system design interview application. 

[Paste the ChatGPT-generated specification here.]

Centralize every backend call in one services layer, and create a mock
implementation of it so the whole app runs without a real backend.

Add tests.
```

> **Перевод промпта:**
>
> Создай приложение для собеседований по проектированию систем.
>
> [Вставьте сюда спецификацию, созданную ChatGPT.]
>
> Собери все обращения к бэкенду в одном сервисном слое и создай его
> реализацию-заглушку, чтобы всё приложение работало без настоящего бэкенда.
>
> Добавь тесты.

Эта часть очень важна:

> Собери все обращения к бэкенду в одном сервисном слое и создай его
> реализацию-заглушку, чтобы всё приложение работало без настоящего бэкенда.

Без неё агент может сделать что-то произвольное, а здесь мы явно указываем, что
хотим сервис-заглушку. Позже он станет единой точкой интеграции фронтенда с бэкендом. А поскольку мы используем заглушку, всё будет работать с самого начала.

## Перенос фронтенда в проект

Далее можно клонировать репозиторий локально. Для дальнейшей работы над проектом мне нужна такая структура:

```text
/backend     # backend application and its tests
/docs        # supporting documentation
/frontend    # frontend application
AGENTS.md    # instructions for coding agents
openapi.yaml # API agreement
```

> **Перевод пояснений к структуре:**
>
> /backend — приложение бэкенда и его тесты.
> /docs — вспомогательная документация.
> /frontend — приложение фронтенда.
> AGENTS.md — инструкции для агентов по программированию.
> openapi.yaml — соглашение об API.

Создадим эти папки и переместим всё, что относится к фронтенду, в "frontend", а созданную спецификацию — в "/docs/spec.md".

После перемещения файлов закоммитьте изменения.

На этом этапе также нужно запустить приложение локально и проверить, что всё работает
так, как вы хотите. Если нет, используйте агента для программирования, чтобы исправить проблемы.

Чтобы запустить проект, экспортированный из Lovable:

```bash
cd frontend
npm i
npm run dev
```

## Спецификации OpenAPI

При создании фронтенда мы попросили ИИ-помощника поместить всё в централизованный
сервисный слой. Позже мы заменим его настоящими вызовами бэкенда.

Но сейчас нужно определить спецификацию — соглашение между фронтендом и бэкендом. Для этого мы используем [OpenAPI](https://learn.openapis.org/introduction.html).

Эта спецификация явно описывает конечные точки, пути, тела запросов и ответов, а также правила аутентификации.

<figure>
  <img src="../../../articles/images/02-openapi-contract.png" alt="Фронтенд и бэкенд опираются на общий контракт OpenAPI">
  <figcaption>OpenAPI — явный контракт, общий для фронтенда и бэкенда</figcaption>
</figure>

Создадим его:

```text
Read the frontend's API client in frontend/

Create openapi.yaml at the repository root.

Specify the backend this frontend expects:
every endpoint, method, path, request body, response body, and which
endpoints need authentication.
```

> **Перевод промпта:**
>
> Прочитай API-клиент фронтенда в frontend/
>
> Создай openapi.yaml в корне репозитория.
>
> Опиши бэкенд, который ожидает этот фронтенд:
> каждую конечную точку, метод, путь, тело запроса, тело ответа и укажи,
> каким конечным точкам нужна аутентификация.

Этот шаг можно пропустить. Но я бы не рекомендовал.

Он занимает несколько минут, но даёт много преимуществ.

Бэкенд получает точную цель, а не выводится из
кода фронтенда. Так мы не только экономим токены, но и получаем ясное
представление о том, что именно требуется от бэкенда.

Можно посмотреть получившийся [openapi.yaml](https://github.com/alexeygrigorev/interview-canvas-share/blob/main/openapi.yaml).

## Бэкенд

Теперь у нас есть спецификация OpenAPI, и мы можем использовать этот файл для создания бэкенда. Для этого возьмём Python и FastAPI.

Когда я начинаю с фронтенда, то использую заглушку бэкенда, а затем заменяю её настоящим. Точно так же для бэкендов на FastAPI я начинаю с заглушки базы данных, которую заменяю позже.

Я делаю это потому, что хочу убедиться в работоспособности соединения фронтенда и бэкенда. Пока взаимодействие не отлажено, я не беспокоюсь о постоянном хранении данных.

Попросим помощника по программированию реализовать это:

```text
Build a FastAPI backend in backend/ that implements the openapi.yaml spec.
Use an in-memory store and seed it with data so the frontend has something to show.
Add authentication with hashed passwords and bearer tokens for the endpoints
that need it.
Split the code into modules - routers, models, store, auth
Write tests
```

> **Перевод промпта:**
>
> Создай в backend/ бэкенд на FastAPI, который реализует спецификацию openapi.yaml.
> Используй хранилище в памяти и заполни его данными, чтобы фронтенду было что показывать.
> Добавь аутентификацию с хешированием паролей и bearer-токенами для конечных точек,
> которым она нужна.
> Раздели код на модули: routers, models, store, auth.
> Напиши тесты.

## Makefile

Когда всё готово, можно запустить приложение. Для FastAPI команда обычно выглядит примерно так:

```bash
cd backend
uv run uvicorn backend.main:app --reload --port 8091
```

Я буду использовать порт 8091, но вы можете заменить его любым другим.

Мне всегда трудно запоминать эти команды, поэтому я прошу помощника по программированию создать Makefile:

```text
Create a Makefile so I can easily run it.
```

> **Перевод промпта:**
>
> Создай Makefile, чтобы я мог легко запускать приложение.

Тогда для запуска достаточно:

```bash
make run
```

Когда приложение запущено, откройте в браузере http://localhost:8091/docs. Вы увидите
спецификацию OpenAPI реализованного бэкенда.

Её можно сравнить с исходной спецификацией. С этого момента исходный `openapi.yaml` нам больше не нужен: достаточно того, который генерирует FastAPI.

## База данных

На этом этапе у нас есть работающее приложение с фронтендом и бэкендом. Они могут взаимодействовать друг с другом. Но поскольку настоящей базы данных пока нет, при перезапуске бэкенда все данные теряются.

Исправим это:

```text
Replace the in-memory store with a database. Use SQLite and SQLAlchemy
Use an environment variable to configure which DB the server should connect to
Make it database-agnostic - later we will add support for other databases (e.g. postgres)
```

> **Перевод промпта:**
>
> Замени хранилище в памяти базой данных. Используй SQLite и SQLAlchemy.
> Используй переменную окружения, чтобы задавать, к какой БД должен подключаться сервер.
> Сделай реализацию независимой от конкретной базы данных: позже мы добавим поддержку других баз, например postgres.

<figure>
  <img src="../../../articles/images/02-backend-sqlite.png" alt="Пользователь взаимодействует с фронтендом, который обращается к бэкенду FastAPI с базой данных SQLite">
  <figcaption>SQLite заменяет хранилище в памяти, не меняя остальной процесс работы приложения</figcaption>
</figure>

В этом промпте есть несколько важных частей:

- Во-первых, я прошу использовать SQLite. Это очень удобная и лёгкая база данных для локального тестирования приложения.
- В какой-то момент для продакшена вам захочется перейти на другую базу данных, например Postgres. SQLAlchemy делает этот переход очень простым.
- Но мы также говорим об этом явно, чтобы в первой версии агент не использовал возможности, специфичные для SQLite.

## Готово к развёртыванию

Теперь у нас есть работающее приложение:

- мы превратили идею в спецификацию;
- создали фронтенд;
- определили контракт API;
- реализовали бэкенд по контракту;
- соединили их;
- добавили SQLite для постоянного хранения данных.

Но это приложение пока работает только локально. Теперь нужно его развернуть.
Этим мы займёмся в следующей статье. Мы возьмём то, что разработали здесь, и превратим это в развёрнутый сервис.

Мы:

- упакуем фронтенд и бэкенд в контейнеры;
- добавим интеграционные тесты для полного сценария работы приложения;
- настроим CI для автоматического запуска проверок;
- запустим Postgres с Docker Compose;
- добавим миграции базы данных;
- развернём приложение в общедоступной среде;
- настроим CD для развёртывания изменений после успешного прохождения проверок.

## Пошаговый подход

На этом практическом занятии мы создали работающее приложение с помощью пошагового подхода.
В конце каждого шага у нас было что-то работающее:

- понятная спецификация;
- работающий прототип фронтенда с заглушкой бэкенда;
- правильно интегрированный бэкенд с заглушкой базы данных;
- полноценное постоянное хранение данных с SQL.

На каждом шаге мы начинали новую сессию и направляли агента

## Далее в серии

Оставшиеся модули продолжают работу над тем же приложением:
