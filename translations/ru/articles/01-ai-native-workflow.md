# Разработка с ИИ в основе процесса: спецификации, проектирование циклов и графов

Это первая статья серии по материалам
[AI Dev Tools Zoomcamp](https://github.com/DataTalksClub/ai-dev-tools-zoomcamp),
бесплатного курса, который мы проводим в DataTalks.Club.

В этом году я решил провести эксперимент и опубликовать конспекты курса
в виде серии статей на Substack. Я планирую выпускать по одной самостоятельной статье на модуль,
начиная с первого: рабочих процессов разработчика, в основе которых лежит ИИ.

Агенты для программирования теперь пишут код быстрее, чем я успеваю его читать.

Когда мы даём агенту задачу, он может быстро её реализовать.
Но если задача расплывчата, агент заполняет пробелы собственными предположениями.
Слабый агент, который нас неправильно понял, пишет пятьдесят строк неработающего кода. Сильный
агент, который нас неправильно понял, создаёт восемь файлов, связывает их между собой и добавляет
тесты, которые успешно проходят. Код работает, но это не то, что нам было нужно.

Мы больше не тратим основную часть времени на набор текста. Мы тратим её на то, чтобы точно сказать,
чего хотим, и проверить полученный результат.

В этой статье я покажу, как сформулировать запрос конкретно, чтобы агентам
не пришлось гадать. Затем мы разобьём запрос на задачи и распределим их
между менеджером продукта, разработчиком и QA-инженером. Наконец, мы
выполним все задачи из бэклога с помощью цикла.

Мы рассмотрим такие темы:

- разработка на основе спецификаций;
- проектирование контекста;
- проектирование циклов;
- проектирование графов.

Мы возьмём намеренно расплывчатую идею проекта: инструмент для еженедельной обратной связи
по проектам. В ней не сказано, кто оставляет обратную связь, кто её получает и что
означает слово «проекты».

Готовый результат можно посмотреть в
[репозитории `retroloop`](https://github.com/alexeygrigorev/retroloop).

## Спецификации раньше кода

Нужно понять, что мы хотим создать, прежде чем агент напишет первую
строку кода. Мы должны подробно всё продумать и дать явные
инструкции. Если мы это сделаем, агент создаст что-то близкое к тому, чего мы
хотим.

Мы называем это «разработкой на основе спецификаций». Мы начинаем со
спецификации, убеждаемся, что она соответствует нашему замыслу, и только потом
пишем по ней код.

В нашем примере «инструмент для еженедельной обратной связи по проектам» многое
неясно.

- Кто будет пользоваться этим инструментом?
- Какую проблему они будут решать?
- Как они будут им пользоваться?

Если не уточнить эти вещи и сразу передать идею агенту для программирования,
он сам заполнит пробелы.

Когда я попросил Claude Code реализовать этот проект, единственным моим промптом было
«инструмент для еженедельной обратной связи по проектам». Он придумал
[`weekly-feedback`](https://github.com/DataTalksClub/ai-dev-tools-zoomcamp/tree/main/01-ai-native-workflow/weekly-feedback),
инструмент командной строки для отслеживания еженедельного состояния проектов. Он фиксирует успехи,
проблемы, препятствия и следующие шаги. Агент также создал документацию и покрыл
приложение 62 тестами, которые все успешно проходят.

![CLI-инструмент weekly-feedback, созданный одним запросом](../../../articles/images/01-wrong-implementation.png)

Всё работает отлично, но это далеко от того, что мне было нужно.
Мне нужен был веб-инструмент для командных ретроспектив, который собирает обратную связь
от команд в формате «Начать / Прекратить / Продолжить». Я сам был виноват в том, что
не сказал об этом Claude.

## Начните с чат-помощника

Вместо того чтобы сразу давать промпт помощнику по программированию, я начинаю в чате
и обсуждаю идею. Для этого я использую ChatGPT в режиме
диктовки.

Я начинаю с той же расплывчатой идеи:

```text
I want to build a tool for weekly feedback for projects.

Help me set the scope for this project precisely. I want to brainstorm with you
and understand how the tool should work. Give me options.

Ask me one question at a time and keep your output short.
```

> **Перевод промпта:**
>
> Я хочу создать инструмент для еженедельной обратной связи по проектам.
>
> Помоги мне точно определить границы этого проекта. Я хочу обсудить с тобой идеи
> и понять, как должен работать инструмент. Предложи варианты.
>
> Задавай мне по одному вопросу и отвечай кратко.

Так мы можем использовать ИИ как партнёра для обсуждения идей и точно выяснить,
чего хотим:

- Кто оставляет обратную связь? Все участники команды.
- Какой формат они используют? «Начать / Прекратить / Продолжить».
- Обратная связь анонимная? По умолчанию имена видны, но участники могут
  остаться анонимными.
- Что люди видят до раскрытия обратной связи? Только свои карточки.
- Как ведущий раскрывает обратную связь? Все карточки появляются
  одновременно.
- Что происходит дальше? Команда группирует карточки, затем каждый участник отдаёт три
  голоса за темы для обсуждения, причём одной теме можно отдать несколько голосов.
- Что фиксирует команда? Решения и задачи по итогам обсуждения.
- Может ли ведущий добавить запись? После встречи можно загрузить аудио, видео или
  расшифровку, но встроенная запись не входит в первую
  версию.

Когда мы заканчиваем, я прошу файл со всеми требованиями:

```text
Save everything to a markdown file that I can download.
```

> **Перевод промпта:**
>
> Сохрани всё в Markdown-файл, который я смогу скачать.

Скачайте файл и сохраните его под именем `plan.md`.

## Подготовка проекта

Создайте проект на основе этой спецификации:

```bash
mkdir project-name
cd project-name

git init
```

Скопируйте файл `plan.md`:

```bash
mkdir -p _docs
mv ~/Downloads/plan.md _docs/plan.md
git add _docs/plan.md
git commit -m "Add project plan"
```

Вы можете найти
[файл `plan.md`](https://github.com/alexeygrigorev/retroloop/blob/711c33cc5b6b/_docs/plan.md)
этого проекта в репозитории Retroloop.

Я стараюсь делать коммиты как можно чаще, после каждого значимого решения. По
этим коммитам можно посмотреть, что изменил агент. Если что-то работает
неправильно, мы легко вернёмся к последнему исправному состоянию.

## Выбор стека и архитектуры

Во время обсуждения идеи мы не выбирали технологический стек.

Попросите агента для программирования предложить несколько вариантов:

```text
Read _docs/plan.md. Propose multiple options for the tech stack and
explain each option.

Don't write code yet.
```

> **Перевод промпта:**
>
> Прочитай _docs/plan.md. Предложи несколько вариантов технологического стека и
> объясни каждый из них.
>
> Пока не пиши код.

Он предлагает несколько вариантов и объясняет компромиссы каждого из них.

Я выбираю Django, потому что знаю его достаточно хорошо, чтобы проверить результат. Вы же
можете выбрать любую технологию, с которой вам удобно работать. Можно и не
иметь предпочтений, а позволить агенту выбрать то, что, по его мнению, подойдёт лучше всего.

## Превращение решений в бэклог

Теперь, когда мы определились с технологическим стеком, можно попросить агента разложить
спецификацию на задачи и создать бэклог:

```text
Create a backlog with tasks in _docs/tasks.md.

Each task should be small enough to finish in one session, and
independent enough that I could hand it to someone who has not read
the others.

Use this template for each task:

## <number>. <title>
Goal: <one line>
Description: <two or three sentences on what the task involves>

The first task should be setting up an empty project with a passing test.

Don't write code yet.
```

> **Перевод промпта:**
>
> Создай бэклог с задачами в _docs/tasks.md.
>
> Каждая задача должна быть достаточно небольшой, чтобы выполнить её за одну сессию, и
> достаточно независимой, чтобы я мог передать её человеку, который не читал
> остальные задачи.
>
> Используй для каждой задачи такой шаблон:
>
> **<номер>. <название>**
> Цель: <одна строка>
> Описание: <два-три предложения о том, что включает задача>
>
> Первой задачей должна быть настройка пустого проекта с проходящим тестом.
>
> Пока не пиши код.

Он создал такой файл
[`tasks.md`](https://github.com/alexeygrigorev/retroloop/blob/711c33cc5b6b/_docs/tasks.md).

Просмотрите задачи и попросите агента объединить слишком мелкие или разбить
те, которые не укладываются в одну сессию.
Мы хотим создать MVP — первую версию приложения. Если что-то выходит за рамки вашего
представления об MVP, уберите это.

Когда задачи вас устроят, перенесите их в трекер задач. Я использую для этого
GitHub Issues.

Попросите агента сделать это:

```text
Create a public GitHub repo for this project.
Move each task from _docs/tasks.md into a GitHub issue.
```

> **Перевод промпта:**
>
> Создай для этого проекта публичный репозиторий GitHub.
> Перенеси каждую задачу из _docs/tasks.md в отдельную задачу GitHub Issues.

Для этого нужно авторизоваться в инструменте командной строки `gh` и
подключить репозиторий к удалённому репозиторию GitHub.

С этого момента задачи GitHub Issues становятся основным источником задач и единственным активным
бэклогом. Файл `_docs/tasks.md` нам больше не нужен.

Получившийся проект можно посмотреть здесь:
[`retroloop`](https://github.com/alexeygrigorev/retroloop).

## Проектирование контекста

Теперь у репозитория есть бэклог. Однако, когда мы начинаем новую сессию,
агент не знает, какую задачу мы имеем в виду. Ему каждый раз приходится выяснять это заново.

Такие сведения мы помещаем в `AGENTS.md`, который агенты для программирования вроде Codex или OpenCode читают
при запуске новой сессии.

Claude Code читает `CLAUDE.md`, а я использую нескольких помощников по программированию и хочу,
чтобы мой рабочий процесс не зависел от конкретного инструмента.

Поэтому я также создаю `CLAUDE.md` с единственной строкой:

```markdown
@AGENTS.md
```

Она указывает Claude прочитать `AGENTS.md`.

Это называется проектированием контекста. При проектировании промптов мы управляем одним
сообщением в одной сессии. При проектировании контекста мы управляем тем, что агенты знают
в начале новой сессии и какую информацию могут найти во время
работы. Мы включаем полезные факты и рабочие правила, которые иначе пришлось бы
выяснять заново.

## `AGENTS.md`

Чтобы этот контекст был доступен в каждой новой сессии, создайте `AGENTS.md`:

```text
Commands

- `uv sync` - install dependencies
- `uv run pytest` - the whole suite
- `uv run pytest tests/test_home.py` - one test file

Rules

- Dependencies are added in `pyproject.toml`. Do not add one without
  asking
- Commit regularly
```

> **Перевод инструкций:**
>
> Команды
>
> - `uv sync` — установить зависимости.
> - `uv run pytest` — весь набор тестов.
> - `uv run pytest tests/test_home.py` — один тестовый файл.
>
> Правила
>
> - Зависимости добавляются в `pyproject.toml`. Не добавляй зависимость без
>   разрешения.
> - Регулярно делай коммиты.

## Другие документы

Помимо `AGENTS.md`, в моих проектах обычно есть ещё несколько Markdown-документов.

Главный из них — `process.md`, в котором я описываю организацию работы.
Он мог бы быть частью `AGENTS.md`, но я храню его отдельно.

Создайте `_docs/process.md`:

```markdown
- Tasks are GitHub issues, one at a time
- Read the acceptance criteria before starting and before closing
- Commit regularly
```

> **Перевод инструкций:**
>
> - Задачи находятся в GitHub Issues, работай с ними по одной.
> - Читай критерии приёмки перед началом работы и перед закрытием задачи.
> - Регулярно делай коммиты.

По мере работы над проектом я могу создавать и другие документы, например:

- `testing-guidelines.md` — правила тестирования;
- `design-system.md` — чтобы интерфейс не менялся произвольно от сессии к сессии;
- `api.md` — описание того, каким должен быть API.

Я храню их вместе в `_docs/` и ссылаюсь на них из `AGENTS.md`:

```markdown
Documents

- `_docs/process.md` - how work is organized
- Before writing tests, read `_docs/testing-guidelines.md`
- For anything touching the UI, read `_docs/design-system.md`
```

> **Перевод инструкций:**
>
> Документы
>
> - `_docs/process.md` — как организована работа.
> - Перед написанием тестов прочитай `_docs/testing-guidelines.md`.
> - Для всего, что затрагивает интерфейс, прочитай `_docs/design-system.md`.

Агент читает `AGENTS.md` в начале каждой сессии, поэтому знает, где
найти правила процесса, тестирования и дизайна, если они понадобятся.

Таким образом, он загрузит дизайн-систему только для задачи по интерфейсу, а
правила тестирования — только для задачи по тестированию.
Загружая каждый документ лишь тогда, когда он нужен, мы сохраняем
`AGENTS.md` коротким, продолжая добавлять в проект письменный контекст.

Эти документы постоянно развиваются, и я часто их обновляю. Если во время программирования мне нужно
поправить агента, я могу попросить его изменить документы.
В следующий раз он уже будет знать, что мне нужно, и мне не придётся исправлять его снова.

Можно использовать такой промпт:

```text
Based on the corrections I made, find the relevant documents
and update them.

Commit the current work before changing the documents.
```

> **Перевод промпта:**
>
> На основе моих поправок найди соответствующие документы
> и обнови их.
>
> Перед изменением документов закоммить текущую работу.

## Запуск первой задачи

Когда `AGENTS.md` и `process.md` готовы, можно начать новую сессию и попросить
агента выполнить первую задачу:

```text
Implement task 1.
```

> **Перевод промпта:**
>
> Выполни задачу 1.

Для этого проекта агент создаёт приложение Django, зависимости и
успешно проходящий тест.

## Уточнение задач: агент — менеджер продукта

У нас есть бэклог задач, но они недостаточно конкретны.

Мы уже обсуждали эту проблему: если задача сформулирована неточно, агент
заполнит пробелы в ходе реализации. Мы рискуем потратить время
и токены на то, что нам не нужно.

Вместо этого следует попросить ИИ-помощника заполнить пробелы до написания
какого-либо кода. Затем мы проверим спецификацию, исправим её и передадим агенту
для реализации.

Этот процесс называется «грумингом»: мы уточняем задачу, делая её более конкретной.
После этого разработчик может реализовать её, не задав ни одного вопроса.

В настоящих командах эту работу обычно выполняют менеджеры продукта. Здесь мы создадим команду
агентов, и первой определим роль менеджера продукта, PM.

Создайте документ:

```text
_docs/team/
  pm.md
```

Внутри напишите описание агента — менеджера продукта:

```markdown
You're a Product Manager

You groom a task before anyone implements it.

- Read the issue as written
- Rewrite it using the template in `_docs/task-template.md`
- Make the acceptance criteria checkable - someone should be able to
  point at the screen and say yes or no
- Think about the edge cases the person who filed it did not consider
- Do not write any code

Definition of done:

- The issue has all four sections filled in
- Every acceptance criterion can be checked by looking at the result
- Everything moved out of scope links to a follow-up issue
- An engineer who has never spoken to you could implement it from the
  issue and the documents it links

If something does not belong in this task, do not silently drop it.
File a follow-up issue and list it under out of scope with a link to
that issue, so it is clear what was moved and where it went.
```

> **Перевод инструкций:**
>
> Ты менеджер продукта.
>
> Ты уточняешь задачу, прежде чем кто-либо начнёт её реализовывать.
>
> - Прочитай исходное описание задачи.
> - Перепиши его по шаблону из `_docs/task-template.md`.
> - Сделай критерии приёмки проверяемыми: человек должен иметь возможность
>   указать на экран и сказать «да» или «нет».
> - Продумай граничные случаи, которые не учёл автор задачи.
> - Не пиши код.
>
> Критерии готовности:
>
> - В задаче заполнены все четыре раздела.
> - Каждый критерий приёмки можно проверить, посмотрев на результат.
> - Всё, что вынесено за рамки задачи, ссылается на отдельную задачу для последующей работы.
> - Разработчик, который никогда с тобой не общался, может реализовать задачу по её
>   описанию и документам, на которые в нём есть ссылки.
>
> Если что-то не относится к этой задаче, не отбрасывай это молча.
> Создай отдельную задачу для последующей работы и укажи её в разделе «Вне рамок задачи» со ссылкой,
> чтобы было ясно, что и куда перенесено.

Уточнённая задача состоит из четырёх разделов:

1. Цель — одно-два предложения о том, что должно стать верным после выполнения.
2. Критерии приёмки — утверждения, которые можно проверить.
3. Вне рамок задачи — чего это изменение не должно делать.
4. Ограничения — файлы, за пределы которых не следует выходить, библиотеки, которые следует или
   не следует использовать, и прежние решения, которым нужно следовать.

Сохраним шаблон задачи в `_docs/task-template.md`:

```markdown
## Goal

One or two sentences on what should be true when this is done.

## Acceptance criteria

- [ ] A statement you can check by looking at the result
- [ ] One line per case, including the awkward ones

## Out of scope

- Something that does not belong in this task, moved to #TASK-NUMBER

## Constraints

- Files this should stay inside
- Libraries to use
- Guidelines to follow
```

> **Перевод шаблона:**
>
> **Цель**
>
> Одно-два предложения о том, что должно стать верным после выполнения.
>
> **Критерии приёмки**
>
> - [ ] Утверждение, которое можно проверить, посмотрев на результат.
> - [ ] По одной строке на каждый случай, включая неудобные.
>
> **Вне рамок задачи**
>
> - То, что не относится к этой задаче и перенесено в #TASK-NUMBER.
>
> **Ограничения**
>
> - Файлы, рамками которых следует ограничиться.
> - Библиотеки, которые нужно использовать.
> - Правила, которым нужно следовать.

Уточнять придётся каждую задачу, поэтому добавим это в `process.md`:

```markdown
Roles

- PM - grooms a task before anyone implements it, follows _docs/team/pm.md
```

> **Перевод инструкций:**
>
> Роли
>
> - PM — уточняет задачу до начала реализации, следует _docs/team/pm.md.

Теперь можно начать новую сессию и попросить агента уточнить задачу:

```text
Groom issue #4
```

> **Перевод промпта:**
>
> Уточни задачу #4.

Когда он закончит, проверьте результат.

На этапе уточнения исправить недопонимание дешевле всего: задача занимает
один абзац, а поправка — одно предложение. Если обнаружить то же
недопонимание после реализации, потребуется переписывать код.

## Проектирование циклов

После уточнения одной задачи можно попросить агента уточнить остальные:

```text
Groom all GitHub issues. Process one issue at a time.
```

> **Перевод промпта:**
>
> Уточни все задачи GitHub Issues. Обрабатывай по одной задаче за раз.

В целом это сработает, но в какой-то момент агент может остановиться. Он может сказать: «Я
уточнил задачи 1, 2 и 3. Продолжать?»

Ответ почти всегда «да», но агент остановился и ждёт,
когда мы скажем это явно. Во многих случаях мне нужно, чтобы агент продолжал
автоматически.

Для этого можно задать агенту цель:

```text
/goal groom all issues
```

> **Перевод промпта:**
>
> /goal уточни все задачи

Команда `/goal` будет побуждать агента продолжать, так что нам не придётся делать
это вручную. Вместо этого мы передаём эту обязанность управляющей оболочке —
системе вокруг агента, такой как Claude Code или Codex. Когда агент останавливается,
оболочка проверяет, выполнено ли условие. Если нет, она
возобновляет работу.

![Цель побуждает агента продолжать](../../../articles/images/01-goal-is-not-met.png)

Этот подход называется «проектированием циклов». Он похож на цикл `while`:
мы повторяем работу, пока не будет выполнено условие.

При проектировании циклов система запускает агента для программирования снова и снова,
вместо того чтобы мы управляли им вручную, промпт за промптом.

В работе с агентами для программирования есть несколько уровней «проектирования»:

- Проектирование промптов — что мы говорим при взаимодействии с агентом.
- Проектирование контекста — что агент знает до начала работы и что может
  получить во время сессии.
- Проектирование циклов — когда он прекращает работу.
- Проектирование графов — кто что делает, если агентов несколько; это мы
  обсудим позже.

В июне 2026 года Эдди Османи опубликовал
[эссе о проектировании циклов](https://addyo.substack.com/p/loop-engineering),
которое дало подходу название, а Питер Штайнбергер выразил идею одним
предложением:

> [Перестаньте писать промпты своим агентам и начните проектировать циклы,
> которые будут делать это за вас.](https://x.com/steipete/status/2063697162748260627)

Циклу нужно условие остановки: проверяемое утверждение, которое сообщает оболочке,
когда остановиться. Для `/goal groom all issues` условие остановки — «все задачи
уточнены». После каждого запуска агента оболочка проверяет, выполнено ли это
условие, и возобновляет работу агента, если нет.

Условие остановки должно быть таким, чтобы модель могла его оценить. «Все задачи
уточнены», «все тесты проходят» и «ни в одном файле не больше 200 строк» — проверяемые условия, а
«сделай код лучше» — нет. Если условие остановки нельзя проверить, агент
может остановиться слишком рано или работать бесконечно.

Claude Code и Codex предоставляют цикл `/goal` по умолчанию.
Если ваша оболочка его не предоставляет, вы можете реализовать его самостоятельно
с помощью хуков остановки.

## Реализация: агент-разработчик

После уточнения задачи её можно передать разработчику — агенту, который
будет писать код.

Определите вторую роль:

```text
_docs/team/
  software-engineer.md
```

Поместите внутрь такое описание:

```markdown
You're a Software Engineer

You implement one groomed task at a time.

- Read the issue and implement what it describes
- Implement against the acceptance criteria, do not change them
- Stay inside the files and constraints the issue names
- Write tests for what you built
- Do not close the issue
- Commit regularly

Definition of done:

- Every acceptance criterion in the issue is implemented
- Tests are written for the new behaviour, and the whole suite passes
- The work is committed
- The issue is still open, with a comment saying what you did

If an acceptance criterion is wrong, impossible, or contradicts
another one, create a comment on the issue about it.
```

> **Перевод инструкций:**
>
> Ты разработчик программного обеспечения.
>
> Ты реализуешь по одной уточнённой задаче за раз.
>
> - Прочитай задачу и реализуй то, что в ней описано.
> - Реализуй функциональность в соответствии с критериями приёмки, не меняй их.
> - Не выходи за рамки файлов и ограничений, указанных в задаче.
> - Напиши тесты для того, что создал.
> - Не закрывай задачу.
> - Регулярно делай коммиты.
>
> Критерии готовности:
>
> - Каждый критерий приёмки из задачи реализован.
> - Для нового поведения написаны тесты, и весь набор тестов проходит.
> - Работа закоммичена.
> - Задача остаётся открытой, в ней есть комментарий с описанием сделанного.
>
> Если критерий приёмки ошибочен, невыполним или противоречит
> другому критерию, оставь об этом комментарий в задаче.

Добавьте ещё одну строку в `process.md`:

```markdown
Roles

- PM - grooms a task before anyone implements it, follows _docs/team/pm.md
- Engineer - implements one groomed task, follows _docs/team/software-engineer.md
```

> **Перевод инструкций:**
>
> Роли
>
> - PM — уточняет задачу до начала реализации, следует _docs/team/pm.md.
> - Engineer — реализует одну уточнённую задачу, следует _docs/team/software-engineer.md.

Затем попросите агента выполнить задачу в новой сессии:

```text
Implement issue #2
```

> **Перевод промпта:**
>
> Реализуй задачу #2.

Разработчик останавливается, когда код написан, а его собственные тесты проходят. Пока
рано утверждать, что задача реализована правильно, поэтому нужно её проверить.

## Тестирование: агент — QA-инженер

Когда один и тот же агент пишет код и оценивает его, он проверяет собственную домашнюю работу.

Если спросить: «Это правильно?», мы получим уверенное «да», но агент мог
пропустить множество граничных случаев.

В реальном мире мы просим других людей проверить нашу работу. У нас есть ревью
кода, а во многих командах — выделенные QA-инженеры, которые сосредоточены на том,
чтобы код был надёжным.

Поэтому мы тоже добавим в нашу команду QA-инженера.

Добавьте третью роль:

```text
_docs/team/
  qa-engineer.md
```

Описание:

```markdown
You're a QA Engineer

You check finished work against the issue that specified it.

- Read the acceptance criteria from the issue
- Check each one against what the code actually does
- Run the tests, and say which ones you ran
- Look for the cases the criteria describe but the tests do not cover
- Do not fix anything you find. Report it by creating a comment

Your output is a verdict: PASS or FAIL. It is FAIL if a single
acceptance criterion fails. Post it as a comment on the issue:

## QA: FAIL

- [x] A visitor can create an account with a username and password - PASS
- [ ] A duplicate username shows a visible error - FAIL
      Submitted an existing username and received an unhandled error

Tests: `uv run pytest`, 18 passed, 0 failed

Definition of done:

- The comment starts with PASS or FAIL
- Every acceptance criterion has a verdict against it
- Every FAIL says what you did and what happened
- The test command and its result are included
- Nothing in the code was changed

Ignore what the implementation says it does. Only the acceptance
criteria and the running code count.
```

> **Перевод инструкций:**
>
> Ты QA-инженер.
>
> Ты проверяешь выполненную работу на соответствие задаче, в которой она была описана.
>
> - Прочитай критерии приёмки в задаче.
> - Сопоставь каждый из них с тем, что код делает на самом деле.
> - Запусти тесты и укажи, какие именно ты запустил.
> - Ищи случаи, описанные в критериях, но не покрытые тестами.
> - Ничего из найденного не исправляй. Сообщи о проблемах в комментарии.
>
> Твой результат — вердикт: PASS или FAIL. Результат — FAIL, если не выполнен хотя бы один
> критерий приёмки. Опубликуй его комментарием к задаче:
>
> **QA: FAIL**
>
> - [x] Посетитель может создать учётную запись с именем пользователя и паролем — PASS.
> - [ ] При повторяющемся имени пользователя появляется видимая ошибка — FAIL.
>       Отправлено существующее имя пользователя; получена необработанная ошибка.
>
> Тесты: `uv run pytest`, 18 пройдено, 0 провалено.
>
> Критерии готовности:
>
> - Комментарий начинается с PASS или FAIL.
> - Для каждого критерия приёмки указан вердикт.
> - Для каждого FAIL описано, что ты сделал и что произошло.
> - Указаны команда запуска тестов и её результат.
> - В коде ничего не изменено.
>
> Игнорируй то, что реализация утверждает о своей работе. Учитывай только критерии
> приёмки и работающий код.

Примечание: возможно, вам придётся адаптировать эту роль под свой проект, если вы не используете `uv`
и `pytest`.

И последняя строка в `process.md`:

```markdown
Roles

- PM - grooms a task before anyone implements it, follows _docs/team/pm.md
- Engineer - implements one groomed task, follows _docs/team/software-engineer.md
- QA - checks the result against the acceptance criteria, follows _docs/team/qa-engineer.md
```

> **Перевод инструкций:**
>
> Роли
>
> - PM — уточняет задачу до начала реализации, следует _docs/team/pm.md.
> - Engineer — реализует одну уточнённую задачу, следует _docs/team/software-engineer.md.
> - QA — проверяет результат по критериям приёмки, следует _docs/team/qa-engineer.md.

Затем в новой сессии попросите:

```text
Test issue #2
```

> **Перевод промпта:**
>
> Протестируй задачу #2.

Если мы получаем `PASS`, отлично. Если получаем `FAIL`, это тоже полезно:
мы обнаружили регрессию. Тогда мы начинаем новую сессию разработчика, передаём ему комментарий QA
и просим исправить проблему. Повторяем процесс, пока QA не выдаст `PASS`.

## Проектирование графов

У нас есть три роли:

- Менеджер продукта уточняет задачу.
- Разработчик реализует её.
- QA-инженер тестирует её и выдаёт `PASS` или `FAIL`.

Если QA выдаёт `FAIL`, разработчику придётся переделать реализацию. В противном случае задача
завершена.

Этот процесс можно представить в виде графа:

![Уточнение, реализация, тестирование и повтор при неудаче](../../../articles/images/01-agent-workflow.png)

Если у нас есть оркестратор, который запускает этих агентов автоматически, вместо того чтобы
мы делали это вручную, получается «проектирование графов». Мы задаём граф,
узлами которого являются специализированные агенты, и описываем, как работа переходит от одного
к другому.

Самое раннее явное использование этого термина я нашёл в статье Джоша К. Симмонса от 4 июля 2026 года: [Этап проектирования графов](https://www.drjoshcsimmons.com/writing/we-are-entering-the-graph-engineering-phase).

Питер Штайнбергер вызвал более широкое обсуждение в
[публикации от 18 июля](https://x.com/steipete/status/2078277297791189132), спросив,
не сместилось ли обсуждение с циклов на графы.
Несколько часов спустя Хэмел Хусейн использовал выражение
[«проектирование графов»](https://x.com/HamelHusain/article/2078346425621237935)
в заголовке статьи.

В самой статье Хэмел разместил лишь GIF с надписью «хватит»,
но термин понравился людям, и его стали использовать для оркестрации нескольких агентов.

Впрочем, я бы не назвал это новой идеей, и проектирование циклов определённо никуда
не делось. Даже с графами нам всё ещё нужен цикл, который двигает работу вперёд и координирует
её между несколькими агентами с разными ролями.

## Оркестратор

Чтобы это реализовать, нам нужен оркестратор.

Опишите его в `process.md`:

```markdown
Orchestrator

The main session is the orchestrator. It launches the PM, the engineer
and QA as subagents. It does not groom, implement or test itself.

Lifecycle

1. Pick the next open issue from the backlog
2. PM grooms it
3. Engineer implements it
4. QA verifies it
5. On FAIL, back to step 3 with the QA comment as input
6. On PASS, close the issue
7. Repeat until the backlog is empty

Rules

- Do not skip step 2
- The engineer does not close the issue
- QA does not fix the code, only outputs PASS or FAIL
- The orchestrator closes the issue only after QA outputs PASS
```

> **Перевод инструкций:**
>
> Оркестратор
>
> Главная сессия — это оркестратор. Она запускает PM, разработчика
> и QA как субагентов. Сама она не уточняет задачи, не реализует и не тестирует их.
>
> Жизненный цикл
>
> 1. Выбрать следующую открытую задачу из бэклога.
> 2. PM уточняет её.
> 3. Разработчик реализует её.
> 4. QA проверяет её.
> 5. При FAIL вернуться к шагу 3, передав комментарий QA на вход.
> 6. При PASS закрыть задачу.
> 7. Повторять, пока бэклог не опустеет.
>
> Правила
>
> - Не пропускай шаг 2.
> - Разработчик не закрывает задачу.
> - QA не исправляет код, а только выдаёт PASS или FAIL.
> - Оркестратор закрывает задачу только после того, как QA выдаст PASS.

Теперь можно начать новую сессию и запустить цикл:

```text
/goal work through the backlog
```

> **Перевод промпта:**
>
> /goal выполни все задачи из бэклога

Агент читает `AGENTS.md`, находит `process.md`, следует жизненному циклу
и распределяет работу между агентами согласно документам в `_docs/team/`.

Поскольку мы используем это вместе с целью, оркестратор работает, пока условие
не будет выполнено.

Результат можно посмотреть в [`retroloop`](https://github.com/alexeygrigorev/retroloop).

Примечание: этот подход требует значительно больше времени и токенов, чем простой цикл
с одним разработчиком. Во многих случаях такая сложность не нужна.
Часто достаточно простого промпта или цикла.

Я применял этот подход во многих проектах, включая
[сайт AI Shipping Labs](https://aishippinglabs.com/).

Я описываю его в статье
[Я создал команду ИИ-агентов для разработки программного обеспечения](https://aishippingblog.com/p/i-built-an-ai-agent-team-for-software).
Здесь я изложил её содержание в виде практического руководства.
