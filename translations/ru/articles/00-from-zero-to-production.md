# От нуля до продакшена с ИИ-агентами для программирования

[AI Dev Tools Zoomcamp](https://github.com/DataTalksClub/ai-dev-tools-zoomcamp)
— бесплатный курс, который мы проводим в DataTalks.Club.

В этой серии мы с помощью ИИ-агентов для программирования создаём приложение, проходя весь путь от идеи до приложения, готового к работе в продакшене.

Я показал, как сделать это в три этапа:

- [Этап 1: Разработка](https://aishippingblog.com/p/build-and-ship-a-full-stack-app-with) — придумать идею, создать фронтенд и бэкенд и запустить их локально.
- [Этап 2: Развёртывание](https://aishippingblog.com/p/deploy-a-full-stack-app-with-ai-coding) — подготовить приложение к тестированию и развёртыванию и настроить CI/CD.
- [Этап 3: Эксплуатация](https://aishippingblog.com/p/devops-and-observability-for-an-ai) — добавить среды разработки и продакшена, собирать метрики, логи и трассировки и поручить ИИ-агентам реагировать на инциденты.

В этой статье я соберу всё в одном месте, чтобы вы могли использовать её как справочник при разработке своих проектов. Я не буду подробно разбирать каждый шаг, но дам промпты, с помощью которых можно пройти весь путь создания проекта, готового к продакшену, просто следуя этой статье.

В предыдущих статьях я старался не привязываться к конкретным инструментам, но использовал в промптах FastAPI, AWS, CloudFormation и другие технологии. Здесь я не предполагаю использование какого-либо определённого языка программирования, фреймворка, базы данных, облака или инструмента наблюдаемости. Вместо этого я покажу, как принимать эти решения с помощью ИИ.

Каждый шаг здесь — это промпт, который вы вводите своему помощнику по программированию. Можно выбрать любого помощника, это неважно. В большинстве случаев полезно начинать новую сессию для каждого шага. Тогда в контексте агента останется только важное и он сможет выполнить работу быстрее и лучше.


## Разработка

На этапе разработки мы:

- превращаем исходную идею в спецификацию;
- создаём фронтенд;
- создаём бэкенд;
- соединяем их.


### 1. Спецификация

Если дать агенту для программирования расплывчатую идею, он заполнит пробелы собственными предположениями и вы получите приложение, которое вам не нужно.

Лучше предельно чётко определить, чего вы хотите, и зафиксировать это в документе под названием «спецификация».

Для этого я обычно использую ChatGPT: открываю его в режиме диктовки, выговариваю всё, что думаю о своей идее, а затем мы уточняем её, пока не станет ясно, как всё может выглядеть.

Можно начать обсуждение с ИИ-помощником с такого промпта:

```text
I want to build a tool for forming study groups.

Help me set the scope for this project precisely. I want to brainstorm with you and understand how the tool should work. Give me options.

Ask me one question at a time and keep your output short.
```

> **Перевод промпта:**
>
> Я хочу создать инструмент для формирования учебных групп.
>
> Помоги мне точно определить границы этого проекта. Я хочу обсудить с тобой идеи и понять, как должен работать инструмент. Предложи варианты.
>
> Задавай мне по одному вопросу и отвечай кратко.

В конце попросите помощника собрать итоги обсуждения в Markdown-документ.

Создайте пустую папку для проекта и сохраните спецификацию в `_docs/specs.md`.

Используйте этот документ для создания фронтенда.

### 2. Сначала фронтенд, с заглушками

Я создаю фронтенд раньше бэкенда, чтобы быстро проверить идею. Это самый дешёвый способ: вы создаёте интерфейс, по которому можно кликать, и проверяете его на тестовых данных. Если он выглядит так, как вы хотите, можно продолжать.

Введите это в своём помощнике по программированию или в инструменте вроде Lovable, v0 или Bolt.new:

```text
Create a system design interview application.

[Paste the ChatGPT-generated specification here.]

Centralize every backend call in one services layer, and create a mock implementation of it so the whole app runs without a real backend.

Add tests.
```

> **Перевод промпта:**
>
> Создай приложение для собеседований по проектированию систем.
>
> [Вставьте сюда спецификацию, созданную ChatGPT.]
>
> Собери все обращения к бэкенду в одном сервисном слое и создай его реализацию-заглушку, чтобы всё приложение работало без настоящего бэкенда.
>
> Добавь тесты.

Сохраните код фронтенда в каталоге `frontend/`.

Когда вы доработаете фронтенд и он вам понравится, наступит время определить, как он будет взаимодействовать с бэкендом.

### 3. Ручной тест

Придумайте тест, с помощью которого сможете проверять работоспособность приложения. Это должна быть последовательность действий, позволяющая убедиться, что приложение работает так, как вы хотите.

Для приложения, которое помогает находить товарищей по учёбе, она может выглядеть примерно так:

1. Открыть главную страницу и зарегистрироваться.
2. Создать учебную группу.
3. Создать в ней мероприятие.
4. Поделиться мероприятием.
5. Записаться на мероприятие из другой сессии браузера.
6. Проверить, что запись видна в первой сессии.

Можно придумать этот сценарий с помощью ИИ, но запомните его и, возможно, тоже сохраните в `_docs`.


### 4. AGENTS.md

AGENTS.md загружается в контекст агента каждый раз, когда вы начинаете новую сессию. В него можно добавить всё, что вы считаете важным для своего приложения. Пока добавим туда одну строку:

```
Make focused, regular commits and explain your decisions in the commit messages so we can use them as logs
```

> **Перевод инструкции:**
>
> Регулярно делай коммиты, посвящённые отдельным изменениям, и объясняй свои решения в сообщениях коммитов, чтобы мы могли использовать их как журнал.

### 5. Схема OpenAPI

Наш фронтенд использует тестовые данные, но работает так, как нам нужно. Ранее мы попросили помощника собрать все будущие вызовы бэкенда в одном месте. Теперь воспользуемся этим, чтобы создать спецификацию API. По ней мы определим взаимодействие фронтенда и бэкенда:

```text
Read the frontend's API client in frontend/

Create openapi.yaml at the repository root that defines every endpoint, method, path, request body, response body, and which endpoints need authentication.
```

> **Перевод промпта:**
>
> Прочитай API-клиент фронтенда в frontend/
>
> Создай в корне репозитория openapi.yaml, который определяет каждую конечную точку, метод, путь, тело запроса, тело ответа и указывает, каким конечным точкам требуется аутентификация.

Теперь у нас есть спецификация бэкенда, и мы можем его создать.

### 6. Выбор стека бэкенда

Прежде чем приступить к разработке, нужно решить, какие технологии вы хотите использовать для этого приложения.

Попросите помощника по программированию помочь:

```text
Based on openapi.yaml, propose 2-3 backend stack options. Describe pros and cons for each. Recommend one.
```

> **Перевод промпта:**
>
> На основе openapi.yaml предложи 2–3 варианта стека бэкенда. Опиши плюсы и минусы каждого. Порекомендуй один из них.

Можно оспорить предложение ИИ-помощника и задать ему вопросы или просто принять предложенный вариант.

В конце сохраните результаты в `_docs/stack.md`.

### 7. Бэкенд

Мы выбрали технологии, так что создадим с их помощью бэкенд.

Как мы создавали фронтенд с заглушками вызовов бэкенда, так можем создать и бэкенд с заглушкой базы данных. Сначала сосредоточьтесь на том, чтобы интеграция фронтенда и бэкенда работала, а затем подключайте настоящую базу данных.

```text
Build backend in backend/ based on `_docs/stack.md` that implements the openapi.yaml spec.

Use an in-memory store and seed it with data so the frontend has something to show.

Add authentication with hashed passwords and bearer tokens for the endpoints that need it.

Write tests.
```

> **Перевод промпта:**
>
> На основе `_docs/stack.md` создай в backend/ бэкенд, который реализует спецификацию openapi.yaml.
>
> Используй хранилище в памяти и заполни его данными, чтобы фронтенду было что показывать.
>
> Добавь аутентификацию с хешированием паролей и bearer-токенами для конечных точек, которым она нужна.
>
> Напиши тесты.

### 8. Makefile

Мне всегда трудно запомнить, как запускать бэкенд, запускать фронтенд, устанавливать зависимости и выполнять другие действия. Для этого я обычно использую Makefile, чтобы можно было просто ввести:

```
make backend
```

И бэкенд запустится. Создадим себе Makefile:

```text
Create a Makefile so I can easily run the application.
```

> **Перевод промпта:**
>
> Создай Makefile, чтобы я мог легко запускать приложение.

### 9. Соединение фронтенда и бэкенда

Мы создали бэкенд, но фронтенд всё ещё использует тестовые данные. Соединим их:

```text
Switch the frontend to use the real backend client.
```

> **Перевод промпта:**
>
> Переключи фронтенд на использование клиента настоящего бэкенда.

Используйте подготовленный ранее тестовый сценарий, чтобы убедиться, что всё работает.

На этом этапе может потребоваться несколько итераций. Проверяйте приложение и просите агента исправлять обнаруженные проблемы, пока оно не заработает правильно.

### 10. База данных

Настоящей базы данных у нас пока нет. Добавим её. Для локальной разработки я обычно использую SQLite, поэтому использую её и здесь, но вы можете заменить её чем-то другим.

```text
Replace the in-memory store with a database. Use SQLite with an ORM, so later we can easily switch to a different database.
```

> **Перевод промпта:**
>
> Замени хранилище в памяти базой данных. Используй SQLite с ORM, чтобы позже мы могли легко перейти на другую базу данных.

Вместо SQLite вашему приложению может понадобиться что-то другое, так что можно обсудить это с помощником по программированию до реализации.

После завершения используйте тестовый сценарий и повторяйте цикл исправлений, пока всё не заработает полностью.


## Развёртывание

Наше приложение работает локально. Отлично. Развернём его, чтобы им могли пользоваться другие:

- упакуем в контейнер;
- развернём в облаке;
- автоматизируем развёртывание с помощью CI/CD.

### 11. Контейнеризация

Нужно поместить приложение в контейнер, чтобы затем для его развёртывания можно было использовать любую систему управления контейнерами.

В локальной среде у нас два процесса: один для фронтенда, другой для бэкенда. Их нужно запускать отдельно. На практике фронтенд обычно компилируют в статические файлы, которые раздаёт бэкенд.

Поэтому вместо отдельных контейнеров для фронтенда и бэкенда мы создадим один, который обслуживает и то и другое:

```text
Create a Dockerfile that builds the frontend with Node, then builds backend.
Backend should serve the frontend.
```

> **Перевод промпта:**
>
> Создай Dockerfile, который собирает фронтенд с помощью Node, а затем собирает бэкенд.
> Бэкенд должен раздавать фронтенд.

Соберите и запустите образ, затем проверьте весь процесс с помощью тестового сценария и вносите исправления, пока всё не заработает.

### 12. База данных для продакшена

На предыдущем этапе, при разработке, я использовал SQLite. Она помогает сохранять локальную конфигурацию лёгкой, но это не та база данных, которую мы можем использовать в продакшене. Обычно мы используем что-то вроде Postgres.

Можно попросить агента выбрать лучшую базу данных для вашего случая, но, скорее всего, это будет Postgres.

Так что добавим её:

```text
Add Postgres support to the backend.
```

> **Перевод промпта:**
>
> Добавь в бэкенд поддержку Postgres.

Используйте тестовый сценарий, чтобы убедиться, что приложение работает.

### 13. Docker Compose

Для более удобного управления локальной средой разработки со всеми сервисами мы используем docker compose.

Попросим агента описать её:

```text
Create docker-compose.yaml with two services: database and the app.
```

> **Перевод промпта:**
>
> Создай docker-compose.yaml с двумя сервисами: базой данных и приложением.

Запустите её с помощью `docker compose up` и проверьте.

### 14. Интеграция

Возможно, к этому моменту у вас уже есть тесты. ИИ-помощникам по программированию предписано их создавать. Но, возможно, в вашем проекте их всё ещё нет.

Попросим помощника создать их явно.

Нам также нужна особая категория тестов — интеграционные. Они проверяют, что взаимодействие бэкенда и базы данных работает правильно.

Можно также попросить помощника помочь подобрать подходящие тестовые сценарии для набора тестов:

```text
Create integration tests that run against docker-compose.yaml.
What scenarios should we test?
```

> **Перевод промпта:**
>
> Создай интеграционные тесты, которые запускаются для docker-compose.yaml.
> Какие сценарии нам следует проверить?

### 15. Сквозной тест

Интеграционные тесты проверяют, что бэкенд может подключиться к базе данных. Сквозные тесты проверяют весь путь от пользователя до бэкенда: от браузера к фронтенду, от фронтенда к бэкенду и от бэкенда к базе данных.

До сих пор мы выполняли эти проверки вручную. Теперь автоматизируем их.

```text
Add an end-to-end test that runs against docker-compose.yaml.

Use Playwright to:

1. <Describe the first step>
2. <Describe the second step>
3. ...

Put the tests in the e2e/ folder in the repository root.
```

> **Перевод промпта:**
>
> Добавь сквозной тест, который запускается для docker-compose.yaml.
>
> Используй Playwright, чтобы:
>
> 1. <Опишите первый шаг>
> 2. <Опишите второй шаг>
> 3. ...
>
> Помести тесты в папку e2e/ в корне репозитория.

Теперь нам не нужно повторять эту проверку вручную при каждом изменении.

### 16. Стек для развёртывания

Теперь приложение работает локально и хорошо протестировано. Пора его развернуть. Но где? Вариантов много. Выберем тот, который подходит нам лучше всего.

Спросите агента для программирования:

```text
Propose 2-3 ways to deploy the application. Compare cost, complexity and other factors.

<List any other constraints that you have>
```

> **Перевод промпта:**
>
> Предложи 2–3 способа развернуть приложение. Сравни стоимость, сложность и другие факторы.
>
> <Перечислите любые другие имеющиеся ограничения>

Полезно также использовать инструмент «инфраструктура как код» (IaC) для управления облачными ресурсами.

```
I want to use an infrastructure-as-code tool for managing my infra. What are my options?
```

> **Перевод промпта:**
>
> Я хочу управлять своей инфраструктурой с помощью инструмента «инфраструктура как код». Какие у меня есть варианты?

Возможно, выбранный вами способ развёртывания не поддерживает инструменты «инфраструктура как код». В таком случае просто двигайтесь дальше.

### 17. Развёртывание

Теперь, когда стек выбран, выполним развёртывание.

Попросите агента:

```text
Deploy this application to <Selected option>.
```

> **Перевод промпта:**
>
> Разверни это приложение в <Выбранный вариант>.

Если применимо, добавьте:

```
use <IaC tool> for managing the infrastructure
```

> **Перевод инструкции:**
>
> Используй <Инструмент IaC> для управления инфраструктурой.

### 18. Конвейер CI/CD

Несколько раз можно выполнить развёртывание вручную, но мы хотим автоматизировать его. Для этого нужен CI/CD:

- CI — непрерывная интеграция: запуск тестов при каждой отправке изменений в git.
- CD — непрерывное развёртывание: автоматическое развёртывание после успешного прохождения тестов.

```text
Create a CI/CD pipeline that:

- runs backend and frontend tests in parallel
- builds the Docker Compose stack and runs integration and end-to-end tests against it
- deploys the application
- validates that the deploy is successful by checking the health endpoint
```

> **Перевод промпта:**
>
> Создай конвейер CI/CD, который:
>
> - параллельно запускает тесты бэкенда и фронтенда;
> - собирает стек Docker Compose и запускает для него интеграционные и сквозные тесты;
> - развёртывает приложение;
> - проверяет успешность развёртывания, обращаясь к конечной точке проверки работоспособности.

Вероятно, вы храните код на GitHub, так что, скорее всего, будете использовать GitHub Actions. Если он вам не нравится, обсудите с ИИ выбор другого варианта.

Мы успешно развернули приложение, но ещё не закончили. Нужно лучше подготовить его к продакшену.

## Эксплуатация

Чтобы лучше подготовить приложение к продакшену, нужно добавить несколько вещей:

- создать среды разработки и продакшена;
- собирать метрики, логи и трассировки;
- настроить оповещения;
- поручить обработку оповещений ИИ-агенту.

Сделаем это.

### 19. Вторая среда

Сейчас каждая отправка изменений сразу обновляет развёрнутое приложение. Но что, если в изменениях есть ошибка, которую мы пропустили?

Чтобы избежать этого, у нас будет две среды:

- Dev: среда для тестирования. Сюда мы развёртываем приложение при каждой отправке изменений.
- Prod: среда, которой пользуются настоящие пользователи. Мы переносим релиз из dev в prod только после того, как убедимся, что он работает правильно.

Если используется «инфраструктура как код», настроить это очень просто. Если нет, пусть этим займётся агент.

Попросите:

```text
Create a second, independent copy of our infrastructure. We will use the copy as production, and the existing infrastructure as a dev environment.
```

> **Перевод промпта:**
>
> Создай вторую, независимую копию нашей инфраструктуры. Копию мы будем использовать как продакшен, а существующую инфраструктуру — как среду разработки.

### 20. Процесс ручного переноса релиза

Теперь при каждой отправке изменений мы автоматически выпускаем код в среду разработки. Настроим ручной перенос релиза из dev в prod:

```text
Create a manual GitHub Actions workflow that promotes the dev version to production.
```

> **Перевод промпта:**
>
> Создай запускаемый вручную процесс GitHub Actions, который переносит версию из dev в продакшен.

### 21. Разделение сборки и развёртывания

Возможно, в вашем CI/CD сборка и развёртывание происходят на одном этапе. У меня такое было при развёртывании на AWS EC2.

Это антипаттерн. Мы хотим собрать образ только один раз, сначала развернуть его в среде разработки и, если всё работает нормально, использовать его же в продакшене.

Если у вас эти шаги не разделены, разделим их. Если не уверены, можно спросить ИИ.

Попросите:

```text
Currently we build the image during the deploy stage.

Split it into two stages:

- Build: build the image and push it to a container registry
- Deploy: pull the image from the registry and serve it

The manual prod promotion CI/CD workflow pulls the currently deployed dev image to prod.

Tag each image using the YYYYMMDD-HHMMSS-shortsha pattern (e.g. "20260818-163457-83242da")
```

> **Перевод промпта:**
>
> Сейчас мы собираем образ на этапе развёртывания.
>
> Раздели его на два этапа:
>
> - Сборка: собрать образ и отправить его в реестр контейнеров.
> - Развёртывание: скачать образ из реестра и запустить его для обслуживания запросов.
>
> Запускаемый вручную процесс CI/CD для переноса в prod скачивает в prod образ, который сейчас развёрнут в dev.
>
> Помечай каждый образ тегом по шаблону YYYYMMDD-HHMMSS-shortsha, например "20260818-163457-83242da".

В зависимости от того, где вы развёртываете приложение, могут понадобиться разные реестры контейнеров. Обсудите это с ИИ, если не уверены, что выбрать и как всё настроить.

### 22. Наблюдаемость. Инструментирование с OpenTelemetry

Наше приложение развёрнуто в продакшене и обслуживает настоящих пользователей. Но мы не знаем, насколько надёжно оно работает.

Для этого нужны данные. Они называются телеметрией, и мы будем собирать метрики, логи и трассировки. Отраслевой стандарт — OpenTelemetry, так что, вероятно, вы будете использовать его.

```text
Instrument the backend with OpenTelemetry.

Include in the telemetry:

- service name
- environment
- deployed version
```

> **Перевод промпта:**
>
> Инструментируй бэкенд с помощью OpenTelemetry.
>
> Включи в телеметрию:
>
> - имя сервиса;
> - среду;
> - развёрнутую версию.

«Инструментировать» бэкенд означает добавить в приложение код для сбора телеметрии. Но её также нужно где-то сохранять.

### 23. Выбор бэкенда для наблюдаемости

Другие полностью управляются поставщиком, но за них придётся платить. Некоторые решения, допускающие самостоятельное размещение, предлагают щедрый бесплатный тариф.

```text
<If you have any preferences add them here>
```

> **Перевод промпта:**

> <Если у вас есть предпочтения, добавьте их здесь>

### 27. Оповещение

Мы не можем постоянно следить за метриками на дашборде. Вместо этого можно настроить оповещение, которое будет срабатывать каждый раз, когда значение метрики окажется слишком низким или слишком высоким.

```text

Include the service, environment, deployed version, owner, and dashboard URL in the alert.
```

> **Перевод промпта:**
>

> Включи в оповещение сервис, среду, развёрнутую версию, ответственного и URL дашборда.

Полезно также отслеживать коды ошибок 5xx и отправлять оповещение для каждой ошибки либо настроить порог, подходящий вашему приложению. Обсудите настройку с ИИ-помощником.

### 28. Дежурный агент

Теперь оповещения приходят на почту или в Slack. Но на них по-прежнему нужно реагировать.

Можно поручить ИИ следить за оповещениями и исправлять ошибки по мере их возникновения.

Настроим это.

```text
Add an on-call-engineer/ directory with a script that connects to the observability alerts API.

When an alert fires, wake up an on-call agent that you run in headless mode, and pass all the alert details. The on-call agent should be able to resolve the issue autonomously and commit the fix.
```

> **Перевод промпта:**
>
> Добавь каталог on-call-engineer/ со скриптом, который подключается к API оповещений системы наблюдаемости.
>
> Когда срабатывает оповещение, запускай дежурного агента в режиме без интерфейса и передавай ему все сведения об оповещении. Дежурный агент должен уметь самостоятельно решить проблему и закоммитить исправление.

Агент должен:

- сначала разобраться в проблеме;
- воспроизвести сбой;
- вносить исправление только в том случае, если оно небольшое, протестировано и закоммичено в отдельную ветку.

Дайте дежурному инженеру такие инструкции:

```
You are the on-call engineer for this repository. An alert just fired.

Investigate the root cause. Read the code and reproduce the failure.
If you find a real bug, make the smallest correction, run the backend tests,
and commit the fix with a clear message.
If the alert is a false positive, explain why and do not change the code.
```

> **Перевод инструкций:**
>
> Ты дежурный инженер этого репозитория. Только что сработало оповещение.
>
> Выясни первопричину. Прочитай код и воспроизведи сбой.
> Если найдёшь настоящую ошибку, внеси минимальное исправление, запусти тесты бэкенда
> и закоммить исправление с понятным сообщением.
> Если оповещение ложное, объясни почему и не меняй код.
