# Заметки по проверке схем для статей

В этих заметках зафиксированы исправления, сделанные при проверке статьи 3, включая
дополнительные правки, обнаруженные при рендеринге. Используйте их и для схем в будущих статьях.

## Рабочий процесс

- Зафиксируйте текст практикума в коммите, прежде чем редактировать его. Последующие визуальные изменения
  оставляйте незакоммиченными, чтобы их было легко проверить.
- Меняйте текст статьи как можно меньше. Подписи должны передавать главную
  мысль в общем виде и содержать только те детали, которые нужны для понимания иллюстрации.
- Храните редактируемый JSON рядом с каждым созданным SVG и PNG. Заново создавайте оба
  формата после последнего изменения исходника.
- Просматривайте каждый PNG в полном разрешении и дорабатывайте всё, что
  формально отображается корректно, но всё ещё выглядит неуклюже.
- Используйте критерии оценки схем и независимую визуальную проверку. Не оценивайте иллюстрацию
  на 10/10, не указав, что именно было проверено.

## Компоновка и соединительные линии

- Выравнивайте равноправные карточки точно по строкам и столбцам. Делайте одинаковые промежутки и соблюдайте
  единый размер карточек; равноправные карточки никогда не должны различаться по размеру. Карточка основания или верхняя
  карточка на всю ширину, охватывающая соседние карточки (как в многоуровневой схеме следующих шагов), несёт намеренный
  смысл и допустима, но не более одной на иллюстрацию.
- Предпочитайте прямые горизонтальные или вертикальные стрелки. Если поток должен повернуть, используйте
  чёткий изгиб под углом 90 градусов вместо наклонного отрезка. Используйте кривые только
  тогда, когда они существенно проясняют связь.
- Делайте стрелки достаточно длинными, чтобы их было легко читать, а для одинаковых связей используйте
  одинаковую длину стрелок.
- Подводите стрелки к видимым линиям отдельных значков, а не к прозрачным
  границам значков. Соединительные линии браузера, пользователя, базы данных и тома должны визуально
  касаться соответствующих символов.
- Используйте отдельные боковые точки привязки, когда два входа ведут в одну карточку, чтобы наконечники стрелок
  не перекрывались.
- Используйте пунктирные линии для второстепенных управляющих действий и пунктирные границы для
  обозначения инфраструктуры или среды выполнения, содержащей компоненты.

## Значки и границы

- Соблюдайте одинаковую толщину линий значков. Символы браузера и базы данных не должны
  выглядеть тяжелее или легче остальных элементов схемы.
- Для развёртывания в AWS используйте значок AWS, а не GitHub.
- Показывайте работающий сервис Postgres в виде карточки контейнера. Показывайте постоянное хранилище
  `pgdata` в виде цилиндра базы данных. Не добавляйте второй цилиндр, дублирующий
  сервис Postgres.
- Используйте одно и то же условное обозначение цилиндра для постоянных томов во всей
  статье.
- Показывайте CloudFormation как контекст управления в подписи границы EC2, а не как
  обычный узел среды выполнения.
- Помещайте компоненты, которые работают вместе, внутрь пунктирной границы контейнера или
  экземпляра.

## Приёмы для отдельных иллюстраций

### Разработка и продакшен

- Объясните, почему на первый взгляд выбраны два контейнера, прежде чем упрощать схему: при разработке
  фронтенд и бэкенд работают как отдельные сервисы, потому что сервер разработки Vite
  поддерживает процесс работы над фронтендом. В продакшене фронтенд представляет собой статические
  файлы, которые отдаёт FastAPI, поэтому React и FastAPI используют один общий контейнер
  приложения.
- Сделайте три этапа визуально различимыми и используйте длинные стрелки с равномерными промежутками.
- Подпишите цилиндр SQLite как базу данных в этом архитектурном представлении;
  том хранения — деталь реализации, а не отдельный компонент.

### Docker Compose и Postgres

- Визуально не меняйте приложение, показывая, как SQLite заменяется
  сервисом Postgres и постоянным томом.
- Делайте стрелки перехода достаточно длинными, чтобы они были очевидны, и последовательно используйте
  цилиндр для обозначения тома.

### Процесс тестирования Playwright

- Отделите автоматизацию от трафика приложения: пунктирные линии идут от верхней
  и нижней сторон Playwright к левым сторонам двух браузерных сессий.
- Сплошные линии идут от правой стороны каждого браузера к верхней и нижней сторонам
  общей комнаты.
- Проведите эти четыре связи симметрично, с изгибами под углом 90 градусов. Соединение общей
  комнаты с FastAPI оставьте горизонтальным, а FastAPI с Postgres — строго вертикальным.

### Развёртывание в AWS

- Поместите Caddy, приложение, Postgres и `pgdata` внутрь одной пунктирной границы
  EC2. Caddy обрабатывает HTTPS перед приложением.
- Используйте карточку контейнера для Postgres и цилиндр для `pgdata`.

### CI/CD

- Используйте горизонтальный поток, чтобы сэкономить место по вертикали. Покажите параллельные тесты фронтенда и бэкенда,
  затем проверки всего стека и после них развёртывание.
- Делайте стрелки достаточно крупными, чтобы их было легко читать, сохраняйте выравнивание заголовков карточек и используйте
  значок AWS только в узле развёртывания в AWS.

### Итоговая архитектура

- Не смешивайте шаги реализации из статьи с итоговой архитектурой.
- Покажите две отдельные браузерные сессии, затем Caddy, один компактный контейнер
  приложения `React + FastAPI`, Postgres и том `pgdata` внутри границы управляемого
  EC2.
- Не включайте подробности WebSocket в эту итоговую иллюстрацию, если они не помогают
  читателю понять конечное состояние.

### Следующий урок

- Расположите пользователя по центру между двумя целями его действий, а не просто по центру холста.
  Покажите отправку пользователем изменений в main и ручное продвижение в продакшен в виде пунктирных стрелок
  действий одинаковой длины.
- Соедините окружения разработки и продакшена пунктирной линией без наконечника.
  Пунктирная стрелка действия пользователя показывает, кто выполняет продвижение.
- Разделите эксплуатацию на отдельные области `Observe` и `Respond` («Наблюдение» и «Реагирование»).
- Покажите цепочку: продакшен → коллектор → наблюдаемость → оповещения → ИИ-агент, а затем
  пунктирный путь исправления обратно к коду.
- Выровняйте код и ИИ-агента в одном столбце, продакшен и коллектор — в другом,
  и соблюдайте выравнивание внутри каждого ряда.
