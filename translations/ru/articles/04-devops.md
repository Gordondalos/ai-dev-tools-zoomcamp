## Среды разработки и эксплуатации

Когда мы отправляем код, изменения развёртываются автоматически и сразу становятся доступны. Это допустимо, когда работа над проектом только начинается. Но с появлением настоящих пользователей нам нужно действовать осторожнее и проверять, не привели ли изменения к регрессиям.

Чтобы избежать этой проблемы, обычно создают две копии одной и той же среды:

- Dev (development, среда разработки): среда для внутренних проверок работоспособности. Обычно в ней запускается самая свежая версия проекта, а при каждой отправке изменений они автоматически развёртываются в этой среде.
- Prod (production, рабочая среда): то, с чем работают наши пользователи. Мы не хотим автоматически разворачивать там каждое изменение и хотим лучше контролировать этот процесс.

<figure>
  <img src="../../../articles/images/04-dev-prod-environments.png" alt="Отправка изменений автоматически запускает развёртывание в среде разработки, а ответственный за релиз вручную переносит проверенный релиз в рабочую среду">
  <figcaption>Среда разработки получает каждую отправку изменений, прошедшую тесты. Рабочая среда получает только релиз, перенесённый вручную</figcaption>
</figure>


Поскольку раньше мы описали инфраструктуру в виде кода, бо́льшую его часть можно использовать повторно. Скорее всего, понадобится изменить некоторые параметры, например размер машины, на которой работает приложение, но большинство ресурсов останется прежним.

Попросим помощника для программирования создать копию существующей среды и назвать её «production»:

```text
Create a second, independent copy of our infrastructure. We will use the copy as production, and the existing infrastructure as a dev environment.
```

Перевод промпта:

> Создай вторую, независимую копию нашей инфраструктуры. Мы будем использовать копию как рабочую среду, а существующую инфраструктуру — как среду разработки.

Когда рабочая среда будет готова, обновим CI/CD. При каждой отправке изменений будем разворачивать их только в dev. Для рабочей среды предусмотрим ручное действие, которое возьмёт текущее содержимое среды разработки и перенесёт, то есть применит, его в рабочей среде.

```text
Create a manual GitHub Actions workflow that promotes the dev version to production.
```

Перевод промпта:

> Создай запускаемый вручную рабочий процесс GitHub Actions, который переносит версию из среды разработки в рабочую среду.

<figure>
  <img src="../../../articles/images/04-manual-production-deploy.png" alt="Запускаемый вручную рабочий процесс развёртывания в рабочей среде с флажком подтверждения и необязательным тегом релиза">
  <figcaption>Человек подтверждает развёртывание в рабочей среде и может выбрать релиз для переноса</figcaption>
</figure>

Теперь у нас две среды.


## Репозиторий контейнеров

В нашем текущем конвейере образ Docker собирается на этапе развёртывания. Я разворачиваю приложение на EC2, выполняя скрипт сборки на машине, а затем запускаю образ в Docker.

Это антипаттерн.

У такого подхода несколько проблем:

1. Этап развёртывания на самом деле состоит из двух действий: сборки и развёртывания. Если сборка завершилась ошибкой, развёртывание не должно происходить, поэтому лучше разделить эти шаги.
2. Когда мы переносим версию из dev в рабочую среду, приходится собирать её заново. За это время многое могло измениться, поэтому сборка не будет идентична версии в dev, а это может вызвать проблемы.

Поэтому разделим этап развёртывания на два отдельных шага:

- Соберём образ и загрузим его в реестр контейнеров
- При развёртывании загрузим этот образ из реестра

При переносе в prod мы просто загрузим туда тот же образ.

В AWS в качестве реестра можно использовать [Amazon ECR](https://aws.amazon.com/ecr/). Можно также отправлять образы в Docker Hub или другой реестр контейнеров, если вы работаете не в AWS и в вашем облаке нет специального сервиса для этого.

<figure>
  <img src="../../../articles/images/04-build-once.png" alt="Пользователь отправляет изменение, после чего CI/CD выполняет отдельные этапы сборки и развёртывания; тег версии передаётся этапу развёртывания и запускаемому вручную выпуску в prod, который обновляет рабочую среду">
  <figcaption>В CI/CD сборка и развёртывание — отдельные этапы. Тег версии поступает в среду разработки через этап развёртывания и в запускаемый вручную выпуск для рабочей среды.</figcaption>
</figure>

Реализуем это:

```text
Currently we build the image during the deploy stage.

Split it into two stages:

- Build: build the image and push it to a container registry (ECR)
- Deploy: pull the image from the registry and serve it

The manual prod promotion CI/CD workflow pulls the currently deployed dev image to prod.

Tag each image using the YYYYMMDD-HHMMSS-shortsha pattern (e.g. "20260818-163457-83242da")
```

Перевод промпта:

> Сейчас мы собираем образ на этапе развёртывания.
>
> Раздели его на два этапа:
>
> - Сборка: собрать образ и отправить его в реестр контейнеров (ECR)
> - Развёртывание: загрузить образ из реестра и запустить его для обслуживания запросов
>
> Запускаемый вручную рабочий процесс CI/CD для переноса в prod загружает в prod образ, который в данный момент развёрнут в dev.
>
> Присваивай каждому образу тег по шаблону YYYYMMDD-HHMMSS-shortsha, например "20260818-163457-83242da".

Теперь этап сборки создаёт образ с тегом, а этап развёртывания разворачивает его в dev. Мы можем проверить приложение в dev и, когда позже перенесём его в рабочую среду, будем уверены, что это в точности тот же образ.

## Наблюдаемость

Наличие двух сред помогает избежать случайного попадания кода с ошибками в рабочую среду. Но инциденты всё равно будут происходить, и нам нужно обнаруживать их и реагировать как можно быстрее.

Для этого нужна наблюдаемость. «Наблюдаемость» означает сбор информации о приложении, позволяющей
понимать его поведение. Благодаря ей, когда что-то ломается, мы можем быстро найти проблему.

Мы обеспечиваем наблюдаемость, добавляя мониторинг в приложения. Как минимум нужно собирать основные метрики производительности: загрузку процессора, использование памяти и число запросов в секунду (RPS).

Если мы видим, что загрузка процессора и использование памяти растут, а RPS падает, возможно, что-то не так.

Одной этой информации недостаточно. Она не объясняет, что произошло внутри запроса и почему это приводит к ошибкам или снижению производительности. Для этого нужно собирать больше данных.

## OpenTelemetry

[OpenTelemetry](https://opentelemetry.io/docs/), часто сокращаемый до OTel, — отраслевой стандарт телеметрии.

Телеметрия — это вся информация, которую выдаёт приложение:

- Метрики: число запросов в секунду, задержка ответа и число ошибок
- Логи: записи отдельных событий с отметками времени, например сообщения об ошибке или неудавшегося запроса к базе данных
- Трассировки: все шаги, называемые «спанами», которые проходит один запрос через всё приложение

Метрики дают конкретные числа, логи — подробности, а трассировки показывают путь запроса со всеми его шагами.


<figure>
  <img src="../../../articles/images/04-observability-pipeline.png" alt="От приложения отходят три ветви с примерами телеметрии: временной ряд метрики, запись лога с отметкой времени и каскадная диаграмма трассировки">
  <figcaption>Метрики показывают измерения во времени, логи фиксируют отдельные события, а трассировки показывают спаны одного запроса</figcaption>
</figure>


OTLP — протокол, который приложения используют для отправки этой телеметрии.

Для многих популярных библиотек сбор телеметрии можно включить буквально несколькими строками кода. Этот процесс называется «инструментированием»: добавлением сбора телеметрии в приложение. Автоматическое инструментирование позволяет инструментировать библиотеки вроде FastAPI, не меняя их код.

<figure>
  <img src="../../../articles/images/04-instrumenting-fast-api.png" alt="Код Python, настраивающий метаданные ресурса OpenTelemetry, поставщик трассировок и экспортёр OTLP для сервиса FastAPI">
  <figcaption>Инструментирование FastAPI настраивает метаданные сервиса и экспортирует трассировки по OTLP</figcaption>
</figure>

Сделаем это. Попросим агента для программирования:

```text
Instrument the backend with OpenTelemetry.

Include in the telemetry:

- service name
- environment
- deployed version
```

Перевод промпта:

> Инструментируй бэкенд с помощью OpenTelemetry.
>
> Включи в телеметрию:
>
> - имя сервиса
> - среду
> - развёрнутую версию

Теперь приложение формирует телеметрию и экспортирует её по OTLP. Осталось
решить, куда её отправлять и где хранить, а также как её просматривать. Сделаем это сейчас.

## Коллекторы OTel

Мы экспортируем телеметрию по OTLP, но она нигде не сохраняется. Для этого разместим
[OpenTelemetry Collector](https://opentelemetry.io/docs/collector/)
между приложением и системами хранения.

Для этой задачи доступно множество сервисов. Спросите своего ИИ-помощника и выберите вариант, который лучше всего подходит вашему приложению.

В нашем случае я буду использовать:

- Prometheus для метрик
- Loki для логов
- Tempo для трассировок
- Grafana для дашбордов

Раньше я никогда не использовал Loki или Tempo, но когда сказал своему агенту для программирования, что хочу использовать Prometheus и Grafana, он предложил добавить также Loki и Tempo.

Реализуем это:

```text
Add an OpenTelemetry Collector.

Create "observability/" directory with Docker Compose for:

- OpenTelemetry Collector
- Prometheus
- Loki
- Tempo
- Grafana

Keep this as a separate Compose project from the application stack.
```

Перевод промпта:

> Добавь OpenTelemetry Collector.
>
> Создай каталог "observability/" с Docker Compose для:
>
> - OpenTelemetry Collector
> - Prometheus
> - Loki
> - Tempo
> - Grafana
>
> Оформи это как отдельный проект Compose, независимый от стека приложения.


Теперь у нас есть инфраструктура наблюдаемости, и мы готовы создать дашборд.

## Метрики

Метрики — это числовые измерения, собираемые во времени. Они могут показывать текущее значение, например число активных участников, или подсчитывать события за интервал, например созданные комнаты или ошибки за последние пять минут.

Для System Design Canvas полезными могут быть следующие измерения:

- Общее число комнат для собеседований
- Число активных комнат и активных участников
- Число элементов на холстах во всём приложении
- Задержка распространения изменений: сколько времени проходит с момента, когда я добавляю элемент на холст, до момента, когда вы его видите
- Число ошибок

Начнём собирать некоторые из них:

```text
Track these application metrics:

- interview rooms created
- active interview participants
- canvas elements created
- failures in component creation

Include the environment and deployed version.
```

Перевод промпта:

> Отслеживай следующие метрики приложения:
>
> - созданные комнаты для собеседований
> - активные участники собеседований
> - созданные элементы холста
> - сбои при создании компонентов
>
> Включи среду и развёрнутую версию.

Теперь у нас есть данные, и их можно показать на дашборде:

```text
Add a Grafana panel with these metrics.
Make it possible to filter by environment and deployed version
```

Перевод промпта:

> Добавь панель Grafana с этими метриками.
> Предусмотри фильтрацию по среде и развёрнутой версии.

Запустите всё локально и проверьте: откройте наше приложение, создайте комнату, добавьте элемент на холст и убедитесь, что он появился в Grafana.

## Развёртывание стека наблюдаемости

Если вы используете тот же стек, что и я, то есть Prometheus, Grafana и остальные сервисы, нам придётся самостоятельно разворачивать их и управлять ими.

Если вы используете управляемый сервис, совместимый с OTel, например CloudWatch, Grafana Cloud, Datadog или Sentry, этот шаг можно пропустить.

Итак, если вы повторяете мои действия, развернём наш стек:

```text
Deploy the observability stack. It should be separate from the application stack.
Connect both development and production to it.
```

Перевод промпта:

> Разверни стек наблюдаемости. Он должен быть отделён от стека приложения.
> Подключи к нему и среду разработки, и рабочую среду.

После завершения можно открыть Grafana и выполнить ту же проверку, которую мы проводили локально.


<figure>
  <img src="../../../articles/images/04-build-once-observability.png" alt="Рабочий процесс с однократной сборкой дополнен OTel, подключённым к среде разработки и рабочей среде; коллектор отправляет метрики в Prometheus, логи в Loki, а трассировки в Tempo для дашбордов Grafana">
  <figcaption>Среда разработки и рабочая среда экспортируют телеметрию через OTel. Коллектор отправляет метрики в Prometheus, логи в Loki и трассировки в Tempo, а Grafana читает все три источника.</figcaption>
</figure>

Примечание: здесь мы разворачиваем Grafana и другие сервисы с открытым доступом из интернета, поэтому к ним может обратиться кто угодно. На практике чувствительные ресурсы, такие как сервисы наблюдаемости и базы данных, размещают в частных сетях, ограничивают сетевой доступ и требуют аутентификацию, чтобы доступ имели только авторизованные пользователи.

## Оповещения

У нас есть дашборды, но мы не можем постоянно следить за ними, чтобы замечать падение или слишком сильный рост метрик. Когда это происходит, нужна система, которая отправляет оповещение о случившемся.



```text
Add an actionable alert for repeated canvas component-creation failures.

Use a threshold and duration that represent real user impact. Include the
service, environment, deployed version, owner, and dashboard URL in the alert.
```

Перевод промпта:

> Добавь оповещение о повторяющихся сбоях создания компонентов холста, по которому можно принять меры.
>
> Используй порог и длительность, соответствующие реальному влиянию на пользователей. Включи
> в оповещение сервис, среду, развёрнутую версию, ответственного и URL дашборда.

## Дежурный инженер

Теперь, когда у нас есть оповещения, нужно на них реагировать. В компаниях обычно есть дежурный инженер. Это инженер, который получает оповещение, когда что-то случается. Ему нужно разобраться в происходящем и найти быстрое решение, которое устранит проблему.

Когда метрика достаточно долго находится за пределами своего порога, срабатывает оповещение, и дежурный инженер его получает.

Наш ИИ-помощник может стать дежурным инженером и, если что-то произойдёт, попытаться исправить ситуацию. В реальных сценариях ИИ-агенты на дежурстве также должны понимать, достаточно ли серьёзна проблема, чтобы передать оповещение дежурному инженеру-человеку.

В нашем случае мы этого делать не будем. Мы реализуем систему, которая проверяет наличие оповещений в системе наблюдаемости, и если что-то происходит, запускается сессия агента, который пытается решить проблему.


```text
Add an on-call-engineer/ directory with a script that polls the observability
alert API every minute.

When an alert fires, pass the alert details to a headless coding agent.
```

Перевод промпта:

> Добавь каталог on-call-engineer/ со скриптом, который каждую минуту опрашивает API оповещений
> системы наблюдаемости.
>
> Когда срабатывает оповещение, передавай его подробности агенту для программирования, работающему без интерактивного интерфейса.

В результате у нас есть фоновый процесс, который опрашивает систему на наличие оповещений и при срабатывании одного из них запускает сессию агента.

В моём случае у агента был такой промпт:

Для этого агента стоит ограничить доступ необходимым минимумом: кодом, логами и метриками, нужными для расследования. Найдя исправление, он сохраняет его коммитом в отдельной ветке, чтобы дальше его обработали обычные процессы ревью и CI/CD. Можно также явно разрешить ему запускать ручное развёртывание в prod, если вы доверяете своему процессу.

```text
You are the on-call engineer for this repository. An alert just fired.

Investigate the root cause. Read the code and reproduce the failure.
If you find a real bug, make the smallest correction, run the backend tests,
and commit the fix with a clear message.
If the alert is a false positive, explain why and do not change the code.
```

Перевод промпта:

> Ты дежурный инженер этого репозитория. Только что сработало оповещение.
>
> Выясни первопричину. Изучи код и воспроизведи сбой.
> Если найдёшь настоящую ошибку, внеси минимальное исправление, запусти тесты бэкенда
> и сохрани исправление коммитом с понятным сообщением.
> Если оповещение ложное, объясни почему и не меняй код.

Это небольшой скрипт для проверки концепции. В реальности ваша система, вероятно, будет выглядеть так:

- Срабатывает оповещение и отправляется через SNS или аналогичный сервис.
- Lambda реагирует на это оповещение и запускает контейнерную задачу.
- Задача запускает Codex или Claude в режиме без интерактивного интерфейса.
- После завершения сессии логи сохраняются, а вычислительные ресурсы освобождаются.

## Добавление ошибки

Мы хотим проверить, что эта система работает, поэтому запустим агента для программирования и попросим его добавить ошибку или найти уже существующую.

```text
Introduce a realistic bug in canvas component creation.

For some requests, creating a component should fail even though the existing
tests pass. Keep the failure reproducible so we can test that the bug causes
an alert and the on-call response.
```

Перевод промпта:

> Добавь реалистичную ошибку в создание компонентов холста.
>
> Для части запросов создание компонента должно завершаться сбоем, хотя существующие
> тесты проходят. Сделай сбой воспроизводимым, чтобы мы могли проверить, что ошибка вызывает
> оповещение и реакцию дежурного.

Здесь цель — отладить процесс и убедиться, что наш дежурный инженер действительно просыпается и решает проблему.

После нескольких итераций у нас появляется дежурный инженер, который просыпается при оповещении и пытается устранить проблему.

## Следующие шаги после этого модуля

Мы начали с идеи, а теперь наша система гораздо ближе к готовности к эксплуатации. Но здесь я смог лишь кратко затронуть самые важные концепции.

Для настоящего приложения в рабочей среде нужно учесть ещё многое:

- Здесь я разворачиваю приложение на EC2, запуская shell-скрипт на экземпляре. Для проверки концепции это допустимо, но для рабочей среды очень проблематично. Используйте систему управления контейнерами, например ECS или её альтернативу.
- Иногда потребуется откатить изменение, перенесённое в prod. Попросите агента упростить эту операцию.
- Используйте управляемый сервис баз данных.
- Регулярно создавайте резервные копии базы данных. Лучше всего хранить их вне стека инфраструктуры как кода и иметь несколько независимых копий.
- Проверьте, что действительно можете использовать эти резервные копии в полностью заново созданном стеке.
- Размещайте внутренние сервисы и ресурсы в частных подсетях внутри VPC и ограничивайте сетевой доступ к ним.
- Если приложению нужно обрабатывать большой объём трафика, изучите масштабирование и балансировку нагрузки. Системы управления контейнерами упрощают управление этим.
- Попросите Fable или GPT-5.6-Sol Max, а лучше обоих, проверить ваш код на уязвимости безопасности. Сделайте это несколько раз.
