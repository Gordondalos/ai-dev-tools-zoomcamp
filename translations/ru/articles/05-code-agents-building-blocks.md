## От Markdown-файлов к навыкам и субагентам

В первой части курса, [AI-native-разработка: спецификации, проектирование циклов и графов](https://aishippingblog.com/p/ai-native-development-specifications), мы затронули и навыки, и субагентов, но я не дал им явных определений.

В частности, мы создали несколько документов:

- `_docs/process.md` и другие документы проекта содержали
  переиспользуемые инструкции (см. [здесь](https://github.com/alexeygrigorev/retroloop/tree/main/_docs))
- `_docs/team/pm.md`, `_docs/team/software-engineer.md` и
  `_docs/team/qa-engineer.md` описывали специализированные роли для субагентов (см. [здесь](https://github.com/alexeygrigorev/retroloop/tree/main/_docs/team)).

Я хотел обсуждать общие принципы и не сосредотачиваться на механике какой-то конкретной реализации.

Мы не определяли их явно, потому что ассистенту для программирования можно сказать:

```
Implement feature #101 following _docs/process.md
```

Перевод промпта:

> Реализуй функцию #101, следуя _docs/process.md

Он прочитает документ и выполнит описанные в нем шаги.

Или можно указать роль агента в начале сессии:

```text
You're a QA engineer. Your role is defined in `_docs/team/qa-engineer.md`. Review work for task #101.
```

Перевод промпта:

> Ты QA-инженер. Твоя роль определена в `_docs/team/qa-engineer.md`. Проверь работу по задаче #101

Еще лучше — попросить его запустить субагента с этой ролью:

```text
Start a QA engineer subagent. The role is defined in `_docs/team/qa-engineer.md`. Review work for task #101.
```

Перевод промпта:

> Запусти субагента — QA-инженера. Роль определена в `_docs/team/qa-engineer.md`. Проверь работу по задаче #101

Это сработает. Ассистент для программирования просто прочитает файл и выполнит задачу.

Но если явно определить эти сущности как навыки и субагентов, вы сможете использовать их эффективнее. В этой статье я покажу, как это сделать.

Начнем с навыков.

## Строительный блок 1: навыки

Навык — это структурированный набор инструкций для повторяемой процедуры.

Если для выполнения задачи нужно придерживаться определенной последовательности действий, эти шаги можно описать в навыке. Позже вы сможете попросить агента выполнить задачу с помощью этого навыка. Он прочитает файл и выполнит описанные в нем шаги.


### Мои навыки

Я активно использую навыки.

Например, один из моих навыков предназначен для выпуска новой версии Python-пакета. Я поддерживаю много Python-библиотек, которые нужно регулярно обновлять и публиковать. О том, как я это делаю, я рассказываю в статье [Мой конвейер выпуска Python-библиотек в PyPI](https://aishippingblog.com/p/my-pypi-release-pipeline-for-python).

Это процесс из нескольких шагов:

- Запустить тесты
- Обновить версию в pyproject.toml
- Отправить код на GitHub с тегом
- Проверить, что CI публикует пакет

Если я хочу выпустить новую версию [minsearch](https://aishippingblog.com/p/minsearch-the-small-search-library), мне не хочется каждый раз описывать эти шаги. Вместо этого я описываю их в [навыке release](https://github.com/alexeygrigorev/.agents/blob/main/skills/release/SKILL.md) и просто говорю:

```text
release a new version
```

Перевод промпта:

> Выпусти новую версию

Агент понимает, что мне нужно, читает навык и выполняет описанные в нем шаги.

<figure>
  <img src="../../../articles/images/05-release-skill.png" alt="Запрос на выпуск minsearch побуждает агента для программирования загрузить навык release и подготовить версию 0.2.0">
  <figcaption>Агент распознает запрос на выпуск и загружает подходящий навык без явной команды использования навыка</figcaption>
</figure>

Внутри навык представляет собой Markdown-файл, который выглядит так:

```markdown
---
name: release
description: Release a new version of the current project
---

Release

1. Inspect the project and determine its package registry.
2. Run the tests and other required checks.
3. Bump the version in the source of truth.
4. Commit the change and push a version tag.
5. Verify that the CI publishing job succeeds.
```

Перевод промпта:

> описание — «Выпустить новую версию текущего проекта»; заголовок — «Выпуск».
>
> 1. Изучи проект и определи его реестр пакетов.
> 2. Запусти тесты и другие обязательные проверки.
> 3. Повысь номер версии в основном источнике данных о версии.
> 4. Создай коммит с изменением и отправь тег версии.
> 5. Убедись, что задание публикации в CI завершилось успешно.

Главное отличие обычного Markdown-файла, который мы использовали раньше, от навыка заключается в том, что навык обнаруживается автоматически.

Я могу сказать:

```
Make a release. The process is described in _docs/release.md
```

Перевод промпта:

> Сделай выпуск. Процесс описан в _docs/release.md

И это точно сработает. Агент прочитает файл и выполнит описанные в нем шаги.

Но с навыками мне не нужно указывать, какой файл использовать. При запуске агент для программирования загружает список навыков в свой контекст. Когда мне нужно выпустить библиотеку, он видит, что для этого есть навык, и использует его.

Навык — это Markdown-документ, но для автоматического обнаружения нужно соблюдать соглашение:

- Он должен содержать секцию frontmatter с именем и описанием
- Он сохраняется в `.agents/skills/<NAME>/SKILL.md` 

Вот и все — остальное на ваше усмотрение. Можно также добавить другие Markdown-документы или скрипты в тот же каталог, где находится `SKILL.md`, и описать, как агент должен их использовать.

В [спецификации Agent Skills](https://agentskills.io/specification)
эта структура и формат описаны подробнее.

Если хотите лучше разобраться, как работают навыки, лучший способ — создать небольшого агента для программирования с навыками. На практическом занятии AI Shipping Labs
[Создание агента для программирования с инструментами, навыками и PydanticAI](https://aishippinglabs.com/workshops/coding-agent-v2) я показываю, как это сделать. Сначала мы изучаем агентов и вызовы функций, а затем разбираемся, как реализовать специальную функцию для загрузки навыков.


### Глобальные навыки

Некоторые навыки нужны во всех ваших проектах. Но другие требуются только для работы в отдельном проекте. 

Примеры глобальных навыков:

- Я использую [release](https://github.com/alexeygrigorev/.agents/tree/main/skills/release) для выпуска новой версии библиотеки, [init-library](https://github.com/alexeygrigorev/.agents/tree/main/skills/init-library) для создания каркаса новой библиотеки или [create-github-repo](https://github.com/alexeygrigorev/.agents/tree/main/skills/create-github-repo) для создания репозитория GitHub
- Также я использую [fetch-youtube](https://github.com/alexeygrigorev/.agents/tree/main/skills/fetch-youtube),
  [fetch-loom](https://github.com/alexeygrigorev/.agents/tree/main/skills/fetch-loom)
  и [fetch-zoom](https://github.com/alexeygrigorev/.agents/tree/main/skills/fetch-zoom),
  чтобы получать записи или расшифровки для анализа агентом.
- Для создания диаграмм у меня есть навык [diagram-creator](https://github.com/alexeygrigorev/.agents/tree/main/skills/diagram-creator).

Я использую эти навыки в нескольких проектах, поэтому лучше сделать их глобальными: тогда любой агент на моем компьютере сможет их увидеть и использовать.

Чтобы создать глобальные навыки, нужно поместить их в 

- `~/.codex/skills` для Codex
- `~/.claude/skills` для Claude
- у других ассистентов для программирования похожая структура

Я использую нескольких ассистентов и хочу, чтобы у всех были одни и те же навыки. Поэтому я храню одну основную копию навыков в своем
[репозитории `agents`](https://github.com/alexeygrigorev/.agents), а затем создаю символические ссылки на них из `~/.codex/skills`, `~/.claude/skills` и других мест. 


### Навыки для конкретного проекта

Однако большинство навыков не полезны глобально — они относятся к конкретному проекту.

Например, в моих проектах:

- [Платформа управления курсами](https://github.com/DataTalksClub/course-management-platform/tree/main/.agents/skills)
  имеет навык [incident-response](https://github.com/DataTalksClub/course-management-platform/tree/main/.agents/skills/cmp-incident-response). Каждый раз при появлении оповещения он знает, как расследовать и устранить проблему, подобно тому, что мы рассмотрели в [статье 4](https://aishippingblog.com/p/devops-and-observability-for-an-ai).
- [FAQ DataTalks.Club](https://github.com/DataTalksClub/faq/tree/main/.agents/skills)
  содержит навыки для получения вопросов по курсам из Slack и превращения повторяющихся
  вопросов в записи FAQ.

Они работают так же, как глобальные навыки, но размещаются в корне проекта:

- `./.agents/skills/` для всех ассистентов, кроме Claude
- `./.claude/skills/` для Claude Code

Раздражает, что у Claude свой формат — как и с `CLAUDE.md`.

Я решаю эту проблему, создавая символическую ссылку из `.claude/skills/` на `.agents/skills/`.

Надеюсь, Anthropic начнет прислушиваться к пользователям и тоже примет соглашение `.agents`, чтобы я наконец мог удалить все эти символические ссылки.


### Создание навыков

Не нужно создавать эти навыки вручную. Ассистенты для программирования знают формат, поэтому можно попросить их создать навыки.

Но я не просто начинаю сессию со слов «создай навык для выпуска новой версии этой библиотеки». Обычно я сначала выполняю задачу вместе с агентом и смотрю, где его нужно поправить.

Мы работаем вместе, пока задача не будет выполнена, а затем в конце я говорю:

```text
Save this as a skill. Cover the workflow we followed and keep all the corrections I made in mind, so the next agent can do the task correctly from the start.

This skill is specific to this project, so don't create a global skill.
```

Перевод промпта:

> Сохрани это как навык. Опиши рабочий процесс, которому мы следовали, и учти все мои исправления, чтобы следующий агент мог с самого начала выполнить задачу правильно.
>
> Этот навык относится только к данному проекту, поэтому не создавай глобальный навык

Если не добавить последнюю строку, Codex создаст глобальный навык, поэтому мне всегда приходится ее добавлять. У других агентов я такого поведения не замечал.

Улучшение существующего навыка устроено так же. Я запускаю навык и, если вижу, что где-то требуется мое вмешательство, поправляю агента. В конце сессии прошу обновить процесс в навыке, чтобы в следующий раз мне не пришлось делать это снова.

## Строительный блок 2: субагенты

Большинство ассистентов для программирования позволяют запустить одну сессию внутри другой. Агентов, созданных таким способом, мы называем «субагентами».

### Контекст сессии

Контекст сессии — это вся информация агента о текущей задаче и обо всех выполненных им действиях.

Он включает:

- Файл AGENTS.md
- Определения навыков и инструментов
- Все файлы, которые он прочитал
- Весь код, который он прочитал и написал
- Весь текст, который вы ему отправили, и весь текст, который он выдал

Это много информации. По мере удлинения сессии агент начинает «забывать» то, что было в начале. Это называется «деградацией контекста».

Поэтому для каждой задачи я начинаю новую сессию, посвященную только ей. В статье [От идеи до продакшена за 28 промптов](https://aishippingblog.com/p/from-idea-to-production) я показываю шаги, необходимые для доведения идеи до продакшена, и рекомендую начинать новую сессию для каждого шага.

Кроме того, текущий контекст влияет на будущие действия агента. Если агент реализовал функцию, не стоит просить его тестировать ее в том же окне. История реализации сделает агента предвзятым, и он может пропустить некоторые проверки. Вместо этого лучше начать свежую сессию и попросить агента проверить работу там.

### Команда агентов

Именно так мы поступили в первой части курса, [AI-native-разработка: спецификации, проектирование циклов и графов](https://aishippingblog.com/p/ai-native-development-specifications). Мы определили несколько ролей для нашей команды агентов:

- Менеджер продукта (PM) — превращает необработанные входящие запросы в спецификации
- Инженер-программист (SWE) — реализует задачу на основе спецификаций
- QA-инженер (QA) — проверяет, что задача реализована правильно

Каждый из этих агентов работает в отдельной сессии. Контекст SWE никогда не попадает в сессию QA, поэтому QA-инженер может тестировать систему независимо.

Если у меня есть уже проработанная задача #101 и я хочу ее реализовать, я могу начать новую сессию и сказать:

```text
You're a software engineer agent. Your role is described in `_docs/team/swe.md`. Work on issue #101.
```

Перевод промпта:

> Ты агент — инженер-программист. Твоя роль описана в `_docs/team/swe.md`. Работай над задачей #101

Но вместо этого я могу запустить его как субагента:

```text
Launch a subagent to implement #101. Follow the process.
```

Перевод промпта:

> Запусти субагента для реализации #101. Следуй процессу


<figure>
  <img src="../../../articles/images/05-subagent-general.png" alt="Ассистент для программирования показывает основную сессию с субагентом общего назначения, который в фоне реализует задачу 101">
  <figcaption>Основная сессия может продолжать работу, пока субагент в фоне выполняет отдельную задачу</figcaption>

Он создаст нового агента с пустым контекстом (плюс AGENTS.md) и автоматически передаст ему примерно такой промпт:

```
You're a software engineer. Your role is defined in `_docs/team/swe.md`.
Your task is to work on issue #101. Follow the process in `_docs/process.md`.
```

Перевод промпта:

> Ты инженер-программист. Твоя роль определена в `_docs/team/swe.md`.
> Твоя задача — работать над задачей #101. Следуй процессу из `_docs/process.md`

В некоторых ассистентах для программирования можно также заглянуть внутрь сессий субагентов. В других вы будете знать только, что субагент что-то делает, но не будете знать, что именно.


### Определение субагентов

Ассистент для программирования может прочитать определение агента из Markdown-документа (например, `_docs/team/swe.md`) и запустить субагента.

Как и в случае с навыками, можно создать переиспользуемое, автоматически обнаруживаемое определение субагента.

Например, для инженера-программиста определение может выглядеть так:

```markdown
---
name: software-engineer
description: Use this agent to execute a well-scoped coding assignment.
---

Implement the assigned task, add or update tests, run the project checks, and
report the files changed and any remaining risks. Do not expand the scope.
```

Перевод промпта:

> описание — «Используй этого агента для выполнения четко ограниченного задания по программированию».
>
> Реализуй назначенную задачу, добавь или обнови тесты, запусти проверки проекта и сообщи об измененных файлах и оставшихся рисках. Не расширяй объем задачи.

Или даже так:

```markdown
---
name: software-engineer
description: Use this agent to execute a well-scoped coding assignment.
---

Read your role definition from _docs/team/swe.md
```

Перевод промпта:

> описание — «Используй этого агента для выполнения четко ограниченного задания по программированию».
>
> Прочитай определение своей роли в _docs/team/swe.md.


Эти определения размещаются в:

- `.agents/agents/<NAME>.md` или 
- `.claude/agents/<NAME>.md` для Claude

Можно также определять субагентов глобально, но мне это никогда не требовалось. Мои субагенты всегда относятся к конкретному проекту.

Теперь можно попросить:

```
Launch software engineer for #101
```

Перевод промпта:

> Запусти инженера-программиста для #101

И он запустит агента — инженера-программиста.

Обратите внимание: в некоторых агентах для программирования, например Claude, придется перезапустить сессию, чтобы обнаружить только что определенного агента.

### Сессия-оркестратор

Когда вы начинаете использовать субагентов, основная сессия становится оркестратором.

Допустим, у нас есть процесс, описанный в `process.md`:

- PM прорабатывает задачу.
- SWE реализует ее.
- QA проверяет ее.
- Если задача проходит проверку, QA выдает `PASS`; иначе — `FAIL`.
- Если он выдает `FAIL`, SWE должен дорабатывать реализацию, пока QA ее не примет.

Так мы создаем граф.

<figure>
  <img src="../../../articles/images/01-agent-workflow.png" alt="PM прорабатывает задачу, инженер реализует ее, а QA либо завершает задачу, либо возвращает не прошедшую проверку работу инженеру">
  <figcaption>Рабочий процесс из части 1 — это граф: PM передает задачу разработчику, QA закрывает прошедшую проверку работу, а неудачные проверки возвращают ее на доработку</figcaption>
</figure>

Что-то должно обеспечивать соблюдение этой последовательности. Обычно для этого мы используем основную сессию программирования.

Если описать процесс в документе `process.md` и сослаться на него в `AGENTS.md`, можно попросить:

```text
Implement #101.
```

Перевод промпта:

> Реализуй #101

Агент автоматически проведет #101 по последовательности PM -> SWE -> QA, каждый шаг будет выполняться в собственном свежем контексте, а оркестратор проследит, чтобы при `FAIL` задача вернулась к SWE, который устранит проблемы.

## Параллельное выполнение

В первой статье я показал только последовательное выполнение этого процесса, и иначе выполнить его нельзя: мы всегда должны соблюдать последовательность PM -> SWE -> QA.

Но можно параллельно заниматься несколькими независимыми задачами.

Наш основной агент уже является оркестратором, поэтому он может запускать нескольких субагентов параллельно. Однако нужно убедиться, что агенты не мешают друг другу.

Для этого мы используем рабочие деревья Git:

- Для каждой новой задачи создаем отдельное рабочее дерево Git
- Агенты независимо работают в этих рабочих деревьях
- В каждом рабочем дереве проходит весь цикл PM -> SWE -> QA
- Когда цикл завершен и задача выполнена, оркестратор сливает изменения обратно в main (как вариант, можно завести агента для разрешения конфликтов)
- Рабочее дерево удаляется

Здесь роль оркестратора уже не ограничивается запуском субагентов по порядку.

Ему также нужно:

- Отслеживать статус каждой задачи
- Планировать работу агентов
- Создавать рабочие деревья и сливать изменения из них
- Предотвращать логические конфликты, выбирая задачи, которым не требуется работать с одними и теми же файлами


<figure>
  <img src="../../../articles/images/05-parallel-worktrees.png" alt="Оркестратор распределяет независимые задачи по изолированным рабочим деревьям, числом до пяти, а затем по одной сливает одобренные ветки в main">
  <figcaption>Агенты параллельно работают в изолированных рабочих деревьях, а оркестратор управляет проверкой и порядком слияния</figcaption>
</figure>

Чтобы это настроить, я помещаю в файл `process.md` примерно следующее:

```text
Work in isolated git worktrees and run up to five agents in parallel.

You are the orchestrator. Your job is to:

- Split the backlog into independent issue tracks.
- Give each agent a separate worktree and clear file ownership.
- Keep the agent slots full while eligible work remains.
- Send completed work to a fresh reviewer.
- Return review findings to the correct implementer.
- Merge approved work into the main branch one issue at a time.
- Coordinate the work. Never implement the issues yourself.
```

Перевод промпта:

> Работай в изолированных рабочих деревьях Git и запускай до пяти агентов параллельно.
>
> Ты оркестратор. Твоя работа:
>
> - Разделить бэклог на независимые потоки задач.
> - Выделить каждому агенту отдельное рабочее дерево и четко определить, за какие файлы он отвечает.
> - Занимать все доступные слоты агентов, пока остается подходящая работа.
> - Отправлять завершенную работу новому проверяющему.
> - Возвращать замечания по проверке соответствующему исполнителю.
> - Сливать одобренные изменения в основную ветку по одной задаче за раз.
> - Координировать работу. Никогда не реализовывать задачи самостоятельно

Именно этот подход я использую в большинстве своих проектов.

## Итоги

- Используйте навык, когда повторяете одну и ту же последовательность действий.
- Используйте субагента, когда задаче нужен отдельный контекст или специализированная роль.
- Используйте основную сессию как оркестратор, когда нескольким агентам нужно следовать процессу.
- Используйте рабочие деревья Git, когда независимые задачи нужно выполнять параллельно.
