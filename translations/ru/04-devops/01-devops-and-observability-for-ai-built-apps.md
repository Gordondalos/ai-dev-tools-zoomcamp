# DevOps и наблюдаемость приложений, созданных с помощью ИИ

[Оригинал материала](https://github.com/Gordondalos/ai-dev-tools-zoomcamp/blob/b47dff65161c878d095e288e9f9e5b907f5aa3c6/04-devops/01-devops-and-observability-for-ai-built-apps.md)

Модуль 3 заканчивается приложением, которое автоматически развёртывается после успешного прохождения тестов. Это делает его доступным в сети, но не позволяет понять, продолжает ли оно работать.

Если важный эндпоинт начинает возвращать `500`, нужно узнать, что пользователи столкнулись с проблемой, найти неудачные запросы, связать их с развёртыванием, которое привело к сбою, и решить, что делать дальше. CI/CD доставляет плохой релиз столь же эффективно, как и хороший.

В этом модуле мы выстроим цикл, закрывающий этот пробел:

```text
change
→ observe user impact
→ alert with context
→ investigate from evidence
→ authorize a bounded response or escalate
→ verify recovery
→ audit the code and the response trail
```

Перевод схемы:

> изменение → наблюдение за влиянием на пользователей → оповещение с контекстом → расследование на основе диагностических данных → разрешение ограниченных действий по реагированию или эскалация → проверка восстановления → аудит кода и истории реагирования

Мы также включим в этот цикл агента в качестве первой линии поддержки. Он запускается автоматически по сигналу оповещения, изучает сохранённый пакет диагностических данных и код, а затем предлагает действие. При этом он не получает учётные данные с общим доступом к production. Модель оценивает уверенность в решении, а код вне модели обеспечивает соблюдение разрешений.

Конкретный стек: OpenTelemetry передаёт данные в Prometheus, Loki и Tempo, поверх которых работает Grafana, а обработчик инцидентов запускает Codex или Claude Code в режиме без интерактивного интерфейса. Эти продукты можно заменить. Главное, что стоит усвоить, — границы между диагностическими данными, рассуждением, разрешением на действие и проверкой результата.

Вы научитесь:

- Выяснять, на какие вопросы о сбое после развёртывания у вас нет ответов, и понимать, почему одних графиков загрузки CPU недостаточно для наблюдаемости
- Инструментировать один эндпоинт от начала до конца с помощью OpenTelemetry: собирать метрики, трассировки и структурированные логи без утечки секретов
- Настраивать конвейер телеметрии: OpenTelemetry Collector передаёт данные в Prometheus, Loki и Tempo, а Grafana позволяет просматривать их вместе
- Создавать одно оповещение, отражающее реальное влияние на пользователей и запускающее локальный обработчик инцидента
- До подключения модели собирать ограниченный, воспроизводимый пакет диагностических данных с помощью разрешённых запросов только для чтения
- Запускать по оповещению агента для программирования (Codex или Claude Code) без интерактивного интерфейса, предоставляя ему доступ к развёрнутым системам только для чтения и изолированное рабочее дерево для предлагаемого исправления
- Разрешать развёртывание только для изменений из разрешённого списка и после успешных тестов, а затем использовать Docker Compose; передавать проблему на следующий уровень, если эти проверки не пройдены
- Проводить регулярные проверки безопасности, сочетающие детерминированный сканер (Semgrep), проверку моделью и подтверждение человеком
- Рассматривать сам обработчик инцидентов как поверхность атаки: учитывать его возможности, учётные данные и происхождение компонентов (Snyk Agent Scan)

Для домашнего задания используйте отдельный [стартовый проект Order Tracker](https://github.com/alexeygrigorev/order-tracker). Можно также выполнить упражнение на приложении, которое вы развернули в [модуле 3](../03-deployment/01-test-containerize-and-deploy-an-ai-assisted-app.md).

Краткое содержание модуля: сопроводительная статья подготавливает развёрнутое приложение к промышленной эксплуатации: разделяет dev и prod, собирает логи, метрики и трассировки и настраивает оповещения о влиянии на пользователей. Затем она запускает небольшого экспериментального агента в роли дежурного по инцидентам: получив оповещение, он исследует первопричину, воспроизводит сбой и фиксирует исправление в коммите. В этом прототипе нет списков разрешённых действий, эскалации и проверки восстановления, необходимых для production. Уроки самого модуля добавляют эти защитные механизмы.

[Читать статью: «DevOps и наблюдаемость приложения, созданного с помощью ИИ»](https://aishippingblog.com/p/devops-and-observability-for-an-ai)

Именно здесь начинается [модуль 5](../05-agent-capabilities/README.md). Каждая возможность, которую вы там добавляете агенту для программирования, должна быть отражена в такой же таблице возможностей, какую вы здесь составляете для обработчика инцидентов.

<a id="where-the-other-tools-fit"></a>

## Место остальных инструментов

Когда проблемы определены, становится понятно, где использовать остальные инструменты:

- **HolmesGPT** и **K8sGPT** собирают эксплуатационные данные, которые модель может объяснить. Это тот же подход, что и у нашего обработчика инцидентов, но для прохождения курса знание Kubernetes не требуется.
- **PR-Agent** применяет проверку моделью на этапе pull request.
- **Semgrep MCP** подключает детерминированное сканирование к агенту.
- **Snyk Agent Scan** инвентаризирует цепочку поставок расширений агента.
- **LiteLLM** добавляет шлюз для маршрутизации запросов к моделям, управления ключами, бюджетами и логами, когда нескольким приложениям или провайдерам нужна единая политика.
- **Ollama** запускает модели локально, когда этого требуют ограничения на размещение данных.
- **garak** тестирует сами LLM-приложения, к которым наше приложение не относится.

Локальная модель не делает рабочий процесс автоматически конфиденциальным: по-прежнему важны хост, сеть, история промптов, локальные логи, аутентификация эндпоинтов и качество модели. Шлюз централизует политику доступа к моделям, но не превращает слабый процесс реагирования на инциденты в надёжный.

<a id="non-goals"></a>

## Что не входит в модуль

В этом модуле намеренно не рассматриваются:

```text
SLOs, error budgets, and burn-rate alerts
synthetic monitoring, real-user monitoring, and profiling
sampling, retention, and observability cost control
canary and progressive delivery, feature flags, chaos testing
on-call ownership, incident command, blameless postmortems
SBOMs, build provenance, signing, penetration testing
```

Перевод списка:

> - Целевые показатели уровня обслуживания (SLO), бюджеты ошибок и оповещения о скорости их расходования
> - Синтетический мониторинг, мониторинг реальных пользователей и профилирование
> - Выборочное сохранение телеметрии, сроки её хранения и контроль затрат на наблюдаемость
> - Канареечные и постепенные релизы, флаги функциональности и хаос-тестирование
> - Ответственность дежурных, координация реагирования на инциденты и разборы инцидентов без поиска виноватых
> - Перечни компонентов ПО (SBOM), сведения о происхождении сборки, подписание и тестирование на проникновение

Эти темы исключены не потому, что они неважны, а потому, что отвлекали бы от основного цикла. В заключительном разделе статьи предлагается порядок их добавления, начиная с SLI и SLO для наиболее важного пользовательского сценария.

<a id="module-deliverable-operations-and-security-report"></a>

## Результат работы по модулю: отчёт об эксплуатации и безопасности

Примените материал модуля к Order Tracker или собственному приложению:

```text
observability/
  collector.yaml
  compose.yaml
  dashboard.json
  alerts.yaml

incident-response/
  collect-evidence.sh
  test-incident.sh
  responder-task.md
  response.schema.json
  autonomy-policy.yaml
  runbooks/verify-recovery.sh
  incidents/

security-audit/
  audit-brief.md
  findings.schema.json
  capability-table.md
  runs/

docs/operations-and-security-report.md
```

По одному идентификатору инцидента читатель отчёта должен суметь восстановить:

- развёрнутую версию и влияние на пользователей
- оповещение и изученные диагностические данные
- использованные модель и конфигурацию, а также предложенное действие
- решение, принятое политикой разрешений, и фактически выполненную команду
- проверку восстановления либо пакет данных для эскалации
- связанные результаты проверки безопасности и решение человека по ним

Основной принцип: модель может рассуждать; система должна наблюдать, разрешать действия, проверять результат и сохранять историю.
